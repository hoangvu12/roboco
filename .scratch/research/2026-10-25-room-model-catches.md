# Research: room-model catches — stress-testing "rooms" before the design interview

Date: 2026-10-25 · Scope: roboco @ `758394bab` (main), zeron mirror @ `911ec56e4` (zeron/main). Follow-up to `.scratch/research/2026-10-25-multi-engine-chats-and-taildrop.md` (same sha; nothing landed since).

The concept under test: a room is a named membership space hosted by ONE engine (host owns the member list as engine-local data; natural host = the always-on headless Linux server). Desktop joins as an ENGINE member; phone joins as CLIENT-only member. One invite ⇒ introduced to every engine member; native clients connect peer-to-peer (phone dials each member's tailcat tunnel); the host is a lobby (guest list + introductions), never a traffic relay for native clients; browsers keep using the host's `/tailcat-relay/{id}`. Non-goals under discussion: delegated introduction while a member engine is offline, cross-engine revocation, room-level chat sharing.

This pass hunts the catches. Every claim carries a source; speculation is marked.

---

## C1 — Phone cost of N engines

What the phone holds per paired engine today (all verified):

| Resource | Per engine | Source |
| --- | --- | --- |
| Tailcat tunnel | 1 in-process Go client (`libroboco_tailcat.so` handle; one shared Go runtime for the whole process — "a Go runtime cannot be torn down, so every successful load stays … for the process lifetime") with its own loopback TCP listener, magicsock UDP socket, and DERP connection while no direct path exists | `crates/mobile-client/src/tailcat.rs:163-170`, `adapters/roboco-tailcat/capi/handles.go:16-49` (handle table, N clients in one runtime), `adapters/roboco-tailcat/adapter.go:245-260` (per-client loopback listener) |
| WebSocket connections | feed WS + "calls" WS ("Calls connection: opened with the feed, supervised independently" — a second dial) + 1 pre-authenticated spare while foreground + 1 transcript WS per open chat | `crates/mobile-client/src/engines/link.rs:283-290, 427, 349`, `handle.rs:384-413` |
| Health probes | `EngineInfo` RPC every **5 s** per engine, unconditionally while the link is up (timer in the steady loop; also re-dials the calls connection when missing) | `link.rs:472-483`, `timings.rs:64-65, 109` (`probe_every: 5 s`) |
| WS keepalives | **both ends ping every 15 s** (`PING_INTERVAL = 15 s` in the shared pump; each direction arms its own interval); verified — the previous research's "15 s pings" is right | `crates/rpc/src/pump.rs:30, 245, 272` |
| Transcript lag checks | `EngineInfo` on each open transcript connection every 10 s | `timings.rs:73-74, 111-112` |
| Reconnect backoff | 500 ms → ×2 → 15 s cap, 0–255 ms jitter, reset after a 10 s-lived connection — per engine | `timings.rs:50-52, 104, 125-183` |
| Cache storage | `engine-cache-v1/{engineId}/` — rows.json + sidebar.json + up to 100 transcripts, pruned to 100 **per engine** at startup ("keep the 100 most recently modified transcripts; the desktop has no bound") | `crates/mobile-client/src/cache.rs:9-22, 249-274`, `crates/engine-client/src/cache.rs:42-52` |

Aggregate behavior in N:

- **App start / foreground:** supervisors spawn in a loop (parallel, not serialized — `crates/mobile-client/src/lib.rs:305-308`), each dialing through `spawn_blocking` tunnel opens that **block up to ~20 s** ("the library pings the engine, up to ~20 s", `tailcat.rs:124-131`; adapter `context.WithTimeout(..., 20 s)`, `adapter.go:239`). N engines ⇒ N concurrent Go client handshakes (DERP bootstrap + netcheck + disco) on app open. `on_foreground` fans one command to every engine at once (`lib.rs:760-778`).
- **Network change:** `set_network_changed` sends a `Verify` to every Tailcat route at once (`lib.rs:740-748`); each failing probe tears and rebuilds that engine's tunnel (route rules in `route.rs:96-113`, `link.rs:510-520`). So one network flap = N parallel 4 s wake-probes + up to N tunnel rebuilds — the reconnect storm is real, though each engine's backoff is independent and jittered.
- **Stay connected in background (ADR 0010):** the service keeps feed + calls per engine alive with the 15 s pings and 5 s probes ("the engine's 15 s pings keep the sockets busy"; "Stay connected costs some battery, which the setting's footer says"). A room multiplies this linearly: N engines ⇒ 2N live WS + N tunnels + 12N `EngineInfo` calls/min. On `dataSync` (API 35+) the linger type gets 6 h/24 h; `specialUse` (stay-connect) is unlimited — `docs/adr/0010` — but the traffic is per engine. Battery impact of N×(radio wakeups per 5-15 s) on cellular is **speculation** (no measurement in repo); the mechanism is grounded.
- **The one superlinear component (C6-adjacent, verified):** every feed frame from any engine calls `publish(ctx)` (`link.rs:890`), which rebuilds the whole `FleetSnapshot` — `engine_snapshot_of` **deep-clones every engine's rows + sidebar** (`lib.rs:1091-1110, 1159-1172`) — and the workspace store re-derives the full merged snapshot on every fleet change plus a 1 s tick (`workspace/mod.rs:164-181`, `timings.rs:90, 118`). So a frame from engine i costs O(all N engines' rows) in clones + re-derive; N engines streaming ⇒ O(N²) row work. At N=2-3 this is invisible; at room scale (5-10 engines) every frame pays 5-10× clones (**speculation on the threshold**, the scaling is fact).
- Memory: Go runtime is shared; per-tunnel cost is one tailcat client (magicsock + wireguard-go device + listeners). No `.so` size or RSS measurement exists in this checkout (no built artifacts; no Go module cache) — **unmeasured, speculation: order of MB per tunnel**.
- Phone cache growth is bounded per engine (100 transcripts) but transcripts can be MB-scale (the 7.6 MB reset example, `docs/reference/remote-access.md` §Transcript resume), so worst-case storage is N × 100 × transcript-size.

Verdict: costs are linear per engine (sockets, probes, cache) with one quadratic seam (fleet publish/derive). None of it blocks the concept; all of it should shape defaults (probe cadence, stay-connect scope, maybe a room member cap).

## C2 — Host engine load & state

- **Relay persistence is unbounded and never evicted.** Each minted browser relay creates `data_dir/tailcat-relays/{uuid}/tailcat/clients/{uuid}/` holding `connect.json` — **the member's tc address, i.e. a secret embedding the pre-shared key, written 0600** — plus the relay's own private client key (`crates/engine/src/tailcat.rs:309-345` `state_dir` + `write_private`; `tailcat_relay.rs:189-205`). `grep remove_dir|evict|ttl` over `tailcat_relay.rs`: no hits. No TTL, no cap, no forget path — room growth makes the dir grow without bound, each entry a live secret.
- **Every relay is a child process, and a host restart re-spawns all of them.** The engine-side `TailcatClient` runs the `roboco-tailcat connect` **subprocess** (`tailcat.rs:339-341` `AdapterChild::spawn`), and `restore_from_disk` re-opens every persisted relay at boot (`tailcat_relay.rs:46-80`, wired in `lib.rs:786-793`). N browser relays ever minted ⇒ N Go processes running on the host forever, all re-spawned at restart (RSS per process unmeasured — **speculation: tens of MB**; the per-process fact is grounded). The "session process hygiene" reaper work (`03800d7c7`) covers harness sessions, not relays.
- **Browser traffic concentration is exactly as stated:** `serve_relay_websocket` is a bidirectional byte pump — every browser byte for member B transits the host's tunnel to B (`tailcat_relay.rs:232-338`). With browsers in a room, the host carries all bytes for all members; bandwidth is linear in browser usage and the host is a single point of failure for browser reachability.
- **The member list is a new durable store — conventions exist, two of them.** Today the engine persists: `pairing.sqlite3` (the ONLY rusqlite user in `crates/engine/src`; schema via `CREATE TABLE IF NOT EXISTS`, no migration machinery — `pairing.rs:44-53`); engine-local SQLite snapshots + command ledger with an **ordered, transactional migration list** (`crates/sync/src/store.rs:34-63, 587-605`); and additive JSON settings (`engine_settings.rs:1-25`, "Additive only (ADR 0005): every field carries `#[serde(default)]`"). A members table can follow either precedent; the cheap path is a pairing.rs-style IF-NOT-EXISTS table in the same `pairing.sqlite3` (same data domain: who is allowed in), the robust path is a migration-listed store. What it touches: a new store module + admin/watch RPCs + tests; no existing table changes.
- **Engine-as-client is a new dependency direction.** `crates/engine` does not depend on `roboco-engine-client` (only `crates/ui` and `crates/mobile-client` do — `crates/ui/Cargo.toml:61`, `crates/mobile-client/Cargo.toml:22`); the host's only outbound client behavior today is the raw tungstenite pipe in `tailcat_relay.rs:16-17` (`connect_async`, no RPC client). An engine member that joins/heartbeats the host as a *client* (engine-as-member per the concept) would be the first engine embedding the client stack — new architecture, needs an ADR (this was flagged in the previous research as the B2 ADR; the room makes it load-bearing for every member, not just the hub).

## C3 — Member liveness catch

Today the host has **no signal at all** about other engines: "an engine knows nothing about other engines" (previous research, from `docs/reference/remote-access.md` §Using several engines — client-side list). `WatchConnectivity` is engine-local harness-CLI state per chat (`doc_host.rs:1074-1079`), and the relay registry has no probe loop (`tailcat_relay.rs` has no timered code). Every option is new code with measurable cost:

| Option | What it takes | Cost | Source for the mechanism |
| --- | --- | --- | --- |
| (a) Host probes members | Host keeps (or opens) a tailcat client per member and disco-pings it: the adapter's probe is a ~3 s end-to-end disco ping, **not** `Client.Ping` ("after the first handshake it returns without waiting for an ack" — the probe must be the 3 s health ping) | N tunnels (or N×20 s opens) on the host + N probes per interval; the relay state dirs of C2 become per-member, not per-browser | `adapters/roboco-tailcat/adapter.go:392-420` (probe + `Client.Ping` caveat), `adapter.go:266-282` (timeouts) |
| (b) Members heartbeat the room | Each member engine makes an authenticated call to the host every T | N calls/T **plus** the engine-as-client machinery (C2's new dependency direction) on every member; the host can reuse the existing `last_seen` pattern — `paired_sessions.last_seen` is already stamped on every authenticate | `crates/engine/src/pairing.rs:129-140` |
| (c) Client dials and self-reports | Phone reports reachability of members it has dialed | Only covers members the phone actually uses; host aggregates gossip = complexity; "online" becomes "online for that phone" | `lib.rs:700-748` (the phone already tracks per-engine link state) |

Learning about a new engine joining later: a `WatchMembers`-style stream on the host is the natural shape, and it rides the phone's **existing** feed WS — cheap. The mechanism generalizes: the phone's feed multiplexes 5 streams (`FEED_STREAMS`, `engines/mod.rs:322-328`) and already tolerates a stream an old engine doesn't serve ("`unknown method` marks one stream unsupported … it never tears the feed down", `link.rs:292-296`). Catch: `FEED_STREAMS` is a fixed const array — adding a 6th stream is a code change on every client (phone, desktop, web), not just the host. The desktop learns via its registry's own watch; member *engines* learning of new members again requires engine-as-client (b).

## C4 — Security catches

**(a) Host = trust concentration.**
- Member enumeration is already half-exposed: `GET_REMOTE_ACCESS` returns the host's **full session list** — id, label, created, last_seen, revoked state — to any paired client (`crates/engine/src/remote_access.rs:368-375`; served on the paired listener, previous research Q3). Labels are device names ≤256 bytes, no control chars (`pairing.rs:189-196`). A room member sees every other member's label and last-seen today, before any room code exists.
- Introduction blast radius: "join with one invite ⇒ introduced to every engine member" means the room invite's blast radius equals the union of all members' reachability. Today reachability is per-engine and per-invite; there is no ACL granularity anywhere in the pairing model ("Paired clients have the full engine capability surface", `rpc.rs:49`) — a room cannot offer "member but not introducible" without inventing a new scoping concept, because sessions are deliberately unscoped.
- Adding arbitrary engines: minting relays/invites requires holding a member invite (secrets) or an admin RPC on the target engine — also reachable by any paired client (`rpc.rs:1428-1447`); the room's guest list does not change that exposure, it centralizes it.
- Relay id squatting: `/tailcat-relay/{id}` (routed at `crates/engine/src/listener.rs:142-168`, no ownership check) proxies bytes to the member listener for **any** paired WS client that guesses a live UUID; the downstream still demands B's session credential on the first Auth frame, so this is a "byte-pipe to a listener that requires auth" — low severity, but it means relay ids are capability-ish handles (`tailcat_relay.rs:232-338`, `serve_relay_websocket`).
- **The invite-mint RPC mutates the target's saved exposure settings.** `CreateTailcatInvite` does not merely mint — it force-enables Tailcat and **persists the setting change**: `settings.enabled = true; settings.transport = Tailcat; bind = 127.0.0.1:0; save()` (`crates/engine/src/remote_access.rs:390-421`). Any paired client (today) or credential-holding host (under delegation, C4b) can flip a member's remote access from off to on remotely. In a room this is an escalation primitive, not a convenience.

**(b) Delegated minting = a new class of secret-at-rest (the sharp one).** Today's invariant: servers persist **only SHA-256 verifiers** — "only verifiers are persisted" (`pairing.rs:1-2`), `verifier()` hashes with a domain tag (`pairing.rs:172-181`) — and every *usable* secret lives on its owner: the client holds the session credential (phone: Keystore AES-GCM, `PairedEngineStore.kt:22-50`); the engine's tailcat state is its own key (`tailcat.rs:309-345`). Delegated introduction while a member is offline requires the host to be able to act **as a client of that member** — i.e. the member must leave a usable (never-expiring, full-surface: `pairing.rs:94-127` mints unscoped sessions; `rpc.rs:49`) bearer credential **on the host machine**. Concretely, the host would store the member's session credential (43-char base64url secret, `pairing.rs:163-170`) alongside the relay's `connect.json`. That is strictly worse than today in two ways: (1) a *usable* secret for engine B sits on machine A, so compromising the host compromises every delegating member's full RPC surface (today a host compromise yields only tunnel keys, which still demand a session credential); (2) it breaks the verifier-only server invariant that the whole pairing design rests on. The existing precedent is narrow: the relay stores the member's *address* (transport secret) but never a session credential — it hands the grant to the caller and stays a byte pipe (`tailcat_relay.rs:222-231`).

**(c) Invite secrecy (ADR 0008).** A room invite itself can be an ordinary pairing link/invite to the host — same grammar, same 0600/never-logged/shape-only-error rules (`crates/proto/src/tailcat.rs:1-8`, ADR 0008) — no violation there. The catch is **quantity and lifetime of derived secrets**: to introduce members while they're online, the host must hold each member's introduction invite (address + single-use pair code — both secrets), and pair codes have a **hard 1–3600 s TTL** (`pairing.rs:15, 65-66`; `create_tailcat_invite` enforces the same, `remote_access.rs:390-391`). So the host cannot stash a long-lived stock of invites; it must either hold live credentials (b) or members must continuously refresh stashed invites (C3's heartbeat, with secret churn every ≤1 h). Also each `/tailcat-relay/` dir is a 0600 secret on disk (C2) — room growth multiplies secret-at-rest surface on the host.

**(d) Revocation duality.** `RevokePairingSession` revokes **one session on the engine it's called on** (`remote_access.rs` revoke → `pairing.rs:145-152`); sessions live until revoked and nothing propagates. Leaving a room can be client-driven today — the phone already has best-effort `revoke_own_session` per engine (3 s timeout, errors swallowed, `lib.rs:580-610`) — so "leave" = forget + N best-effort revokes the *phone* drives. A host-side KICK cannot reach the phone's sessions on member engines without delegated admin on every member (usable credentials again — same class as (b), multiplied by member count). Cross-engine revocation is a non-goal in the concept precisely because it would require this; the catch to record is that a kicked member's credentials **remain valid on every member engine until individually revoked** — the room gates future introductions, not existing sessions.

## C5 — Wire/compat/quality catches

- **Unknown-method UX:** new RPC methods need no capability string (gate catalogue, `docs/reference/remote-access.md` §When a change needs a capability); old engines answer `unknown method: X` (`crates/rpc/src/lib.rs:287-288, 398`). On the phone that maps to `ClientError::Unsupported` — "The engine does not support this method: {method}" (`engines/handle.rs:440-451`). Catch: there is **no feature-level advertisement for new methods** — the client must probe, catch the error, and hide the room UI itself; a host one version behind shows a per-call error toast, not a graceful "rooms unavailable" state, unless the client implements the hiding. Streams degrade gracefully (`link.rs:292-296`); unary room calls do not.
- **Version skew:** phone pairs with a new host + old member engines is fine by construction — member engines just see ordinary clients (introduction = redeem + WS, unchanged wire). The member-side catches: `CreateTailcatInvite` **silently enables and persists Tailcat remote access** on a member that never turned it on (`remote_access.rs:400-406` — "remote access is off by default", `docs/reference/remote-access.md` line 3; a surprising settings mutation the room would invoke routinely), it needs the adapter binary present on the member (`remote_access.rs:396`, source builds run `cargo xtask tailcat-adapter`, remote-access.md §Tailcat transport), and the member must be **online** for the route to come up — the room fixes *discovery*, not *reachability of offline members* (the desktop-asleep problem persists for the desktop's own engine).
- **Glossary collision, documented not vibes:** CONTEXT.md's Registry entry explicitly lists **"registry room" on the avoid list** (`CONTEXT.md:125-126`). Upstream zeron's "rooms" meant replicated Loro documents over the edge — "ChatClient: joins a ChatRoom DO", "the per-profile workspace registry room" (`git show zeron/main:crates/sync/src/lib.rs:1-9`), and `AGENTS.md` forbids restoring "sync rooms" in upstream ports. A Roboco "room" is a membership group with **zero** data sharing — the same word upstream used for the exact opposite architecture. No user-facing "room" strings exist today (grep over `crates/ui`, `web/packages/app`, Android strings: only code comments like "breathing room"), so the word is free — but it will read as "sync room" to anyone who knows zeron, and CONTEXT.md already rejected it once.
- **Sidebar/presentation:** spaces are per-engine and the sidebar already merges all paired engines' chats "with device labels" (`docs/reference/remote-access.md` §Using several engines); the phone merges engine streams into one workspace snapshot (`workspace/mod.rs:1-14`). A room is a cross-engine grouping layered into the same sidebar — a third noun (room) above device and space, where "Space" already means "folder on a device" (`CONTEXT.md:128-131`) and "Device" means "machine you can drive" (`CONTEXT.md:132-134`). The collision isn't technical, it's vocabulary + visual hierarchy; the glossary needs the entry before the UI ships.

## C6 — Other catches

- **Transcript resume over N engines:** mechanically unaffected — digests are per-engine deterministic and resume is per-chat (`docs/reference/remote-access.md` §Transcript resume). Two soft catches: chats spread across engines you rarely open are always cold (full reset, the 7.6 MB class), and the phone's resume state is capped at 100 transcripts **per engine** (LRU, `cache.rs:20-22`), so a room of quiet engines evicts each other's resume state only via per-engine LRU (not cross-engine) — fine, but "the room made my chat lose resume" will *feel* true at 100+ chats per engine.
- **Join atomicity:** a room join = N introductions, each consuming a **single-use** pair code (`pairing.rs:94-127` — redeem deletes the code in-transaction). An interrupted join leaves sessions minted on some member engines while the UI says "failed"; cleanup is per-engine forget + best-effort `revoke_own_session` (`lib.rs:580-610`). No atomic multi-engine operation exists or is cheap to build; the join flow needs explicit partial-failure UX.
- **Room record on the phone:** `PairedEngine` is a UniFFI-generated Kotlin data class (`uniffi.roboco_core.PairedEngine`, `EngineMetaJson.kt:44-56`) — adding a room field touches the FFI surface, every construction site, and the Android metadata codec. The codec is lenient and additive-safe ("unknown keys are ignored", `EngineMetaJson.kt:62-72`), so old installs reading new metadata is fine; the FFI struct change still forces a coordinated core+app release (they ship together — same APK — so this is an annoying rebuild, not a skew).
- **ScopedId seams:** `engine:v1:<engineKey,rawId>` scoping is per-engine and rooms sit above it — grouping doesn't break it. The wall appears only if room UX ever passes an id owned by one engine to another: the client-side wire boundary **rejects** foreign-engine identities ("Request identity belongs to another engine", `crates/engine-client/src/routing.rs:31-35`), and cross-engine anchors are already treated as absent (move_pin: "anchors from other engines count as absent", `lib.rs:879-890`). Any "fork/share this chat into that member's engine" feature hits this by design (ADR 0004) — the room must not promise it.
- **Notification fan-out:** already fleet-aware and mostly aggregate — the driver keys baselines `(engine id, chat id)`, run activity is "the aggregate working/awaiting" across every engine, and per-chat Done/Failed/Input notifications follow the shared rule (`notify.rs:1-40`). Link-lost events are per-engine but gated ("≥ 4 s … while one of the engine's chats was Working when it dropped", `notify.rs:23-26`) — idle engines don't fan out. The catch at room scale is many simultaneous Done notifications (one per finished chat) — bounded by run count, not engine count.
- **Steady-state CPU on the phone:** see C1's superlinear publish/derive seam — the 1 s workspace tick re-derives the whole merged fleet every second regardless of activity (`timings.rs:117`, `workspace/mod.rs:164-181`); row counts, not engine count, drive it, but every engine's row set is in the derive.

## Catches ranked by severity

**Blocking (design must resolve before build):**

1. **The lobby-only / no-delegation / offline-introduction triangle is unsatisfiable with today's primitives.** Pair codes die within 1 h max (`pairing.rs:15, 65-66`), so a host can't hold a stash of member invites for offline members; introducing an offline member requires either a usable credential on the host (delegation — the rejected non-goal, C4b) or relaying the member's traffic (contradicts "never a traffic relay"). Pick two of the three, or invent new token semantics (short-lived delegated introduction tokens, a new scoping concept pairing has never had — `rpc.rs:49`).
2. **Engine-as-client becomes load-bearing for every member.** No engine embeds the client stack today (`crates/engine` has no `roboco-engine-client` dependency; the host's only outbound behavior is a raw tungstenite pipe, `tailcat_relay.rs:16`). Members that join, heartbeat, and self-publish invites are engines acting as clients — new durable state, new dependency direction, new ADR (previously flagged for the hub only; the room spreads it to all engine members).
3. **Delegated minting, if chosen, breaks the verifier-only server invariant.** A usable, never-expiring, full-surface session credential stored on the host is a strictly worse secret-at-rest class than anything today (C4b) — host compromise escalates from "tunnel keys" to "every delegating member's full RPC surface". If the room needs offline introduction, prefer purpose-built short-lived introduction tokens over raw session credentials.

**Annoying (engineering cost, not design blockers):**

4. Host relay dirs are unbounded secrets with no eviction, one Go subprocess each, all re-spawned at host restart (C2).
5. Per-frame fleet snapshot rebuild + workspace re-derive is O(N engines' rows) per frame from any engine — quadratic in aggregate as N grows (C1/C6).
6. Phone steady-state cost: 12N `EngineInfo` probes/min + 2N WS × 15 s pings + N tunnels; network change fans N parallel 20 s tunnel rebuilds; stay-connected multiplies the background cost (C1).
7. `GET_REMOTE_ACCESS` already enumerates all paired sessions (labels, last-seen) to any member — the room's guest list is half-public before it exists (C4a).
8. Join is non-atomic across single-use codes; interrupted joins leave orphan sessions needing per-engine cleanup (C6).
9. `CreateTailcatInvite` force-enables and persists a member's remote-access settings from off to on — an escalation primitive the room would invoke routinely (C4a/C5); new-method UX on old hosts is a raw error toast unless every client implements hiding (C5).
10. "Room" is on CONTEXT.md's avoid list ("registry room") and meant the opposite (replicated Loro sync rooms) upstream; the sidebar gains a third grouping noun over device and space (C5).
