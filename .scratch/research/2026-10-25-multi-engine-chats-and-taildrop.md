# Research: spawn chats on other engines + taildrop-style file sending

Date: 2026-10-25 · Scope: roboco @ `758394bab` (main), zeron mirror @ `911ec56e4` (zeron/main), tailcat upstream HEAD `52fbad323e9d` (2026-10-07; our pin `fd101889796a` is behind, see Q3).

The ask: (1) a client — typically the Android phone — paired with one engine should create and drive chats that live on **other** engines without repeating the per-engine pairing dance; (2) Taildrop-style file drops phone → engine. Ground rules: ADR 0004 (data is engine-local, no cross-engine sync, ever), ADR 0008 (Tailcat = account-free transport; invites/addresses are secrets), ADR 0009 (Android pairs per engine, one connection per engine, disposable cache), `docs/reference/remote-access.md` (paired-engine list is client-side state; an engine knows nothing about other engines).

## Q1 — How Tailscale Taildrop works, and what's borrowable

### The protocol (tailscale.com + tailscale/tailscale source)

Taildrop is **not** a new transfer protocol — it is "direct HTTP POST to the peer, over the tailnet, with a staging inbox". The Tailscale KB describes it as "files sent over encrypted peer-to-peer connections, using the fastest available path" (tailscale.com/kb/1106/taildrop, "Taildrop lets you send files between your personal devices"). Every claim below is from source at upstream HEAD:

| Stage | What happens | Source |
| --- | --- | --- |
| Target discovery | Sender asks tailscaled (localapi) for file targets; each target = the peer's netmap entry + **`PeerAPIURL`** (`http://<peer-api-ip:port>`) — the peer's PeerAPI base, discovered from the control plane, not dialed blind | `feature/taildrop/ext.go` `FileTargets()` (`PeerAPIBase(p)`); `client/tailscale/apitype/apitype.go` `FileTarget{Node, PeerAPIURL}` |
| Availability gate | Target status: `Offline`, `MissingCap`, `OwnedByOtherUser`, `NoPeerAPI`, `Available` — same-user peers only, or explicit `FileSharingTarget` peer capability | `feature/taildrop/ext.go` `taildropTargetStatus()` |
| Send (CLI/GUI) | `PUT /localapi/v0/file-put/{stableID}/{name}` (single) or `POST /localapi/v0/file-put/{stableID}` with `multipart/form-data` (first part = JSON manifest of `OutgoingFile`s, then one part per file) | `feature/taildrop/localapi.go` `serveFilePut`, doc comment at top |
| Wire transfer | tailscaled reverse-proxies the body as **`PUT http://peer/v0/put/{filename}`** — plain HTTP over the WireGuard data plane, via `PeerAPITransport()` (dials the peer's Tailscale IP through magicsock: direct UDP when traversal works, DERP otherwise) | `feature/taildrop/localapi.go` `singleFilePut` (`NewSingleHostReverseProxy` + `PeerAPITransport`); `net/tsdial/tsdial.go` `PeerAPITransport/PeerAPIHTTPClient` |
| Resume | Before PUT, sender GETs `/v0/put/{name}`: receiver replies with a JSON stream of **64 KiB block SHA-256 checksums** of its partial file; sender skips matching blocks and PUTs the remainder with a **`Range`** header and offset-adjusted Content-Length | `feature/taildrop/localapi.go` `singleFilePut` (GET-then-PUT); `feature/taildrop/resume.go` (`blockSize = 64<<10`, `blockChecksum{checksum, algo:"sha256", size}`) |
| Receive | Receiver's PeerAPI handles `GET|PUT /v0/put/{baseName}`; writes to `<name>.<clientID>.partial` in the inbox dir (keyed by `Client-Id` header), returns `409`/`400`/`403` on conflict/invalid/forbidden names | `feature/taildrop/peerapi.go` `handlePeerPut*`; `feature/taildrop/send.go` `PutFile` (offset, length, partial naming) |
| Staging & sweep | Partial and deleted-marker files are swept **after 1 hour** (`deleteDelay = time.Hour`) — the KB's "a transfer can be resumed for up to an hour after it failed" | `feature/taildrop/delete.go:20-22`; KB §Resume interrupted transfers |
| Fetch | `tailscale file get [--wait|--loop|--conflict=skip\|overwrite\|rename] <dir>` lists `WaitingFile`s (localapi), moves them out of the inbox, deletes; OS clients integrate (macOS → `~/Downloads` after enabling Sharing in System Settings, Windows Explorer integration, iOS/Android share sheet) | `cmd/tailscale/cli/file.go` `fileGetCmd`/`receiveFile`; KB §Client setup/§Receive |
| Offline target | **No offline staging in the data plane.** The CLI warns "is reportedly offline; trying anyway" after 3 s of zero bytes and just attempts the PUT (if the peer is truly unreachable it fails; resume happens when both are back, within the 1-hour partial window) | `cmd/tailscale/cli/file.go` `runCp` (`warnTimer`, "reportedly offline; trying anyway"); `file.go` `getTargetStableID` |
| Limits | No protocol size cap (streaming PUT); multi-file via multipart; single-user personal devices only; alpha feature gated per-tailnet ("Send Files" admin toggle) | KB §Enable Taildrop / §Send files |

DERP fallback is *transport-level*, invisible to Taildrop: when NAT traversal fails, the same PeerAPI HTTP bytes ride the DERP relay ("DERP … fill the same role as TURN … Tailscale private keys never leave the node … [a DERP server] just blindly forwards already-encrypted traffic"; tailscale.com/blog/how-tailscale-works, §Encrypted TCP relays (DERP)). The sender does not choose or know.

### What's borrowable for Roboco — the direct answer

**The vendored tailcat adapter exposes no raw peer-to-peer addressing usable as a direct file channel.** It "intentionally provides only one fixed Tailcat application port backed by one exact IPv4 loopback target … does not install a VPN, execute commands, or expose a general-purpose forwarder" (`adapters/roboco-tailcat/adapter.go:13-16`); `ApplicationPort = 7332` is the only remote port (adapter.go:33-34); every client dial is `DialTCPPort(ctx, ApplicationPort)` to the **one** server named by the invite's address (adapter.go:378-390). A Roboco `Client` is 1:1 with one engine's listener — there is no netmap, no per-peer endpoint, nothing PeerAPI-like. So a Taildrop-style direct peer HTTP channel would require widening the adapter (a second app port or tailcat's own file service — the upstream CLI has `recv`/`serve files`/`cp`, see Q3), which contradicts the adapter's deliberate minimalism and adds a new security surface.

**Files must therefore ride the existing WebSocket RPC upload path**, which is already Taildrop-shaped in several respects:

| Taildrop | Roboco today | Source (Roboco) |
| --- | --- | --- |
| `PUT /v0/put/{name}`, streaming, Content-Length | `UploadChunk {uploadId, seq, data}` (base64, **680 000 chars ≈ 510 KB binary**, multiple of 4, sized under Cloudflare's 1 MiB WS frame cap) → `UploadCommit` assembles | `crates/mobile-client/src/attachments.rs:50-54`; `crates/ui/src/attachments.rs:30-46` |
| 64 KiB-block SHA-256 checksums + Range resume | Positional `seq` writes are **idempotent** (retry overwrites the slot); commit rejects holes; per-chunk retries (3 attempts, staggered), 3-way concurrency, whole-file deadline ≤ 900 s | `crates/engine/src/uploads.rs:125-152` (`append`), `crates/mobile-client/src/attachments.rs:252-274` |
| `<name>.partial` inbox, 1-hour sweep | `uploads/tmp/{uploadId}/{seq}.b64` staging, **`STAGING_TTL` 10 min** sweep, survives engine restart | `crates/engine/src/uploads.rs:29, 99-104` |
| No size cap | Client cap **24 MB** (`MAX_ATTACHMENT_BYTES`), engine cap **32 MB** (`MAX_BYTES` in uploads.rs — the ticket's "24 MB" is the client-side number) | `crates/mobile-client/src/attachments.rs:51`; `crates/engine/src/uploads.rs:81` |
| `tailscale file get` inbox model | `ReadAttachmentChunk` 45 KB read-back loop + byte-budgeted LRU cache on the phone | `crates/engine/src/uploads.rs:83`; `crates/mobile-client/src/attachments.rs:250-261` |
| Pending-ref offload | `pending://{uploadId}/{fileName}` refs: a queued message names bytes by identity; any device resolves the ref against its own uploads dir (`{id8}-{sanitize(name)}`) — Roboco's cloud-relay-era attachment-transfer seam, now a client-side commit-first pattern | `crates/engine/src/uploads.rs:32-60` |

What Roboco lacks vs Taildrop: mid-file checksum resume (only whole-chunk idempotency), an unbounded streaming channel (24 MB cap), and any inbox for an **offline** engine — but "queue the message now, bytes follow" is exactly the `pending://` + message-queue design already present (`message-queue-attachments-v1` capability, remote-access.md §Gate catalogue).

### Reference peer file-transfer protocols

| System | Transport & discovery | Auth | Files | Distinct from Roboco's path |
| --- | --- | --- | --- | --- |
| **LocalSend** (v2.2 REST + v3 WebRTC draft) | LAN-only; UDP multicast 224.0.0.167:53317 announce + reply, or HTTP fallback scanning; HTTPS with self-signed cert (fingerprint = device id) | Optional PIN; receiver accepts per transfer | Two-phase: `POST /api/localsend/v2/prepare-upload` (metadata → sessionId + per-file tokens) then per-file binary POST; v3 adds optional WebRTC data channel with signaling server + nonce/token handshake | LAN-mcast discovery and human-approve-per-transfer model; no relay/offline story — assumes both on one LAN (localsend/protocol README.md §1-§4; v3 `webrtc-diagram.mermaid`) |
| **KDE Connect** | UDP 1716 broadcast / mDNS (Avahi) identity packets → TLS TCP 1716-1764 (`QSslSocket`), device cert per link | Pairing protocol over the same socket: pair request/accept packets with 30-min-fresh timestamp, cert SHA-256 shown to user | Files via `sftp` plugin: a per-transfer random port announced in the packet payload, SFTP subsystem over the same TLS socket | Same pattern as Roboco's TLS-less trust model minus tailnet; pairing is symmetric and interactive (`core/backends/lan/lanlinkprovider.h:67-69`, `core/backends/lan/avahidiscovery.cpp`, `core/backends/pairinghandler.cpp:10,32-60`) |
| **Warpinator** | UDP "cert-request" datagrams to each peer's port (default TCP transfer port **42000**, gRPC server, optional zlib), LAN discovery | TLS certs exchanged over UDP then pinned; both sides must share a **group code** (SHA-256 of the code is cert key material) | gRPC bidi streams, 1 MiB chunk reads | Group-code shared-secret = pre-shared fleet key (very close to tailcat's PSK-in-address), but discovery is LAN broadcast (linuxmint/warpinator `src/remote_registration.py:175-200`, `src/auth.py:81-110,150`, gschema `port=42000`, `src/transfers.py:47-63`) |

All three are LAN-discovery systems with a human-in-the-loop accept; Roboco's problem is different — the peer is an already-paired, already-trusted engine over an encrypted tunnel — so the interesting borrow from Taildrop is the **staging + resume + fetch** trio, not discovery or pairing.

## Q2 — "Many servers behind one connection" precedents

| System | One connection, many upstreams how? | Identity & credentials | Streams/latency | Maps to |
| --- | --- | --- | --- | --- |
| **Tailscale coordination** | Control plane is a "shared drop box for public keys"; nodes download peers' keys+endpoints, then **connect peer-to-peer** (data plane is a mesh); DERP is relay-of-last-resort for blocked networks | Each node owns its WireGuard key; the coordinator never sees traffic keys | Direct path preferred; relay only on traversal failure ("the so-called control plane is hub and spoke, but that doesn't matter because it carries virtually no traffic"; DERP "blindly forwards already-encrypted traffic") | **Model B** (introduce, then direct) with an A-style fallback — exactly the hybrid |
| **ZNC** (IRC bouncer) | Bouncer holds N "networks"; client connects once and selects network via `username/networkname`; bouncer keeps upstream connections alive and **buffers** channel history while clients are away | Bouncer stores upstream server host/port + password bouncer-side; client authenticates only to the bouncer | All traffic via bouncer, always | **Model A** (pure proxy + buffering) — but buffering is a data-replication step Roboco must not do |
| **soju** | Same shape, modern: multiple users each with own upstreams; `soju.im/bouncer-networks` IRC extension or `user/network` username suffix; per-client buffers + backlog replay on reconnect | Bouncer persists upstream credentials; NickServ/SASL creds captured at use and reused ("authenticating with NickServ, the credentials will be saved and automatically used") | All traffic via soju | **Model A**, with per-client buffer identity — the closest precedent for "one phone connection, several engines", minus the ADR 0004 problem: soju *is* a replica of history |
| **Matrix federation** | Rooms are replicated state machines: PDUs broadcast to every homeserver in the room, signed by origin, persisted everywhere; **state resolution** reconciles forks; backfill pulls history from peers | Homeserver key signatures at TLS + HTTP layer | Ongoing inter-server replication traffic per room | The **counter-example ADR 0004 rejects**: true cross-server rooms cost event/state replication — Roboco's answer is "the chat lives on one engine; clients are views" (spec.matrix.org server-server API §PDUs/EDUs/Queries) |
| **OAuth 2.0 Token Exchange (RFC 8693)** | Gateway A calls backend C for user B: A presents its own token as `subject_token` (or `actor_token`), receives a **delegated/impersonation token** for C; composite tokens carry an `act` claim naming the actor; `may_act` pre-authorizes who may act | STS mints the on-behalf-of credential; C can distinguish "A acting for B" from A alone | One extra round trip to the STS per flow | The **credential shape for Model A** if the hub must forward *as the phone*, not as itself: today Roboco session tokens are unscoped full-surface credentials, so "delegation" would mean new minting semantics on each target engine |
| **SSH ProxyJump** | Client connects to jump host, then "establishing a TCP forwarding to the ultimate target from there"; chained jumps; destination config not applied to jump host | Client authenticates to **both** hop and target with its own keys | All bytes via the hop; no buffering | The classic **hop pattern** — Model A's traffic shape with Model B's credential shape (end-to-end auth through the tunnel) — ssh_config(5) §ProxyJump (man7.org) |

Read together: the precedents split cleanly into *route bytes* (ProxyJump, Tailscale DERP) and *replicate state* (ZNC/soju buffers, Matrix). ADR 0004 only forbids the second category. Tailscale is the proof that "coordinator introduces, peers connect directly, relay as fallback" can be built with the coordinator holding no data and no traffic.

## Q3 — What Roboco already has to build on

### Pairing (engine side)

- `POST /pairing/redeem` on any listener; the pair code is the Bearer credential; reply grants a never-expiring `credential` (session). Codes: single-use (`DELETE … RETURNING` in one transaction), TTL 1–3600 s, default 300 s; **only SHA-256 verifiers are persisted**, never the secret (`crates/engine/src/pairing.rs:17-19, 86-127`). A redeemed session authenticates every WS's first `Auth` frame (`crates/engine/src/listener.rs:313-348`) and updates `last_seen`.
- **No scoping**: "Paired clients have the full engine capability surface" (`crates/engine/src/rpc.rs:49`). Revocation is by session id (`RevokePairingSession`; `roboco engine pairing list/revoke`, remote-access.md §Pairing administration).
- Note for what follows: the remote-access admin RPCs (`CreatePairingLink`, `CreateTailcatInvite`, `SetRemoteAccess`, `RevokePairingSession`) are served by the **same `EngineRpc` service on the paired listener** (`crates/engine/src/lib.rs:763-786` passes one `service`; `rpc.rs:1428-1447`) — i.e. any paired client can already ask an engine to mint *that engine's* pairing link or tailcat invite. This is the building block Model B needs (speculation: whether that was a deliberate policy or an unexamined consequence — nothing in the docs says paired sessions should be admins).

### How the desktop drives remote engines (client side)

- `EngineRegistry` holds one entry per paired engine: `SavedEngine {key, endpoint, credential, info}` in `paired-engines-v1.json` (desktop; frozen shape, ADR 0005). **The key is a client-minted random UUID, not the engine's deviceId** (`crates/engine-client/src/registry.rs:729`). `pair()` = resolve input → POST redeem → open authenticated WS → `EngineInfo` → persist (`registry.rs:672-760`). The paired-engine list is pure client state — an engine has no row for its clients beyond the session table.
- Client-side id scoping: every id leaving the registry is `engine:v1:<base64(engineKey, rawId)>` (`ScopedId`, registry.rs:34-64); the wire boundary decodes scoped ids back to raw and **strips `targetDeviceId`** before sending — "Routing ends at the socket; no engine forwards this request" (`crates/engine-client/src/routing.rs:20-50`).
- The engine side mirrors this as a fail-closed guard: a request whose `targetDeviceId` names another engine is rejected — "engine {target} is not connected; requests must use its own connection" (`crates/engine/src/rpc.rs:1413-1427`). Upstream zeron still has the full cloud-relay forwarder this guard replaced: `forward()` re-dials the target device's relay DO, proxies streams by re-subscribing, with per-method deadlines (`git show zeron/main:crates/engine/src/rpc.rs:1095-1165`; design in `rpc.rs:42-49`).
- Creating a chat on a chosen engine: the space palette lists devices (projected from all engines); the composer resolves the engine via `target_for_id` → `EngineTarget`, and the first send issues **`Mutate {op:"createChat", chatId, spaceId?, deviceId?, config, cwd, …}`** — `spaceId` fixes the host device, `deviceId` picks it for projectless chats (`crates/engine/src/rpc.rs:666-695, 1059-1090`; `crates/ui/src/state.rs:2498-2515`; `crates/ui/src/shell/spaces.rs:2-5`). Watches (`WatchChats/Spaces/Devices/Sessions`, per-chat `WatchDocMessages`) all ride the same per-engine client (`registry.rs` `drive()`, `state.rs start_chat_watches`).

### The big one: an engine can already be a relay to other engines — for browsers

`crates/engine/src/tailcat_relay.rs` (landed 2026-10-04, `e6fbfec28`) is a server-side pairing relay: a client already paired with engine A can `POST /pairing/tailcat-redeem {invite, label}` **on A's paired listener** with a `roboco-tailcat:` invite for engine B. Engine A then:

1. dials B through its own Tailcat client (`TailcatClient::start`), persisting tunnel state under `data_dir/tailcat-relays/{id}/` (survives restarts, `restore_from_disk`);
2. redeems the invite's pair code against B's `/pairing/redeem` over the tunnel;
3. returns B's session grant to the caller, with `baseUrl` rewritten to `…/tailcat-relay/{id}` on A's listener;
4. proxies **raw WebSocket frames** bidirectionally at `/tailcat-relay/{id}` (plain `Message::Text/Binary` pump — the caller's own `Auth` frame and all traffic pass through opaquely).

Sources: `tailcat_relay.rs:1-4` (doc), `:133-231` (`tailcat_redeem`), `:232-338` (`serve_relay_websocket`), routes in `listener.rs:139-168`, paired-gate at `listener.rs:142-147`.

This is Model B (introduction/handoff) already shipped: A vouches for nothing cryptographically, but *performs the redeem round-trip* and then stays a byte pipe; the browser ends up with its **own** session credential for B (minted by B, visible in transit to A), and B's remote listener stays loopback-bound. The caller needs no local `browser-helper` process. **The phone can reuse this endpoint as-is** — it is an HTTP route on the engine the phone is already paired with (the phone's route exposes `http_base()` for exactly such HTTP calls, `crates/mobile-client/src/engines/route.rs:128`).

Vestigial wire seams that matter for the synthesis: `RELAY_COMMAND` (→ `ingest_relayed_command`, dedupe/TTL/supersede + exactly-once ledger, `doc_host.rs:2220-2280`) and `WATCH_TRANSFERS` (a compatibility feed that is always empty — "local uploads do not use relay transfers", `doc_host.rs:110`, `queue_command_with_transfers` ignores its `_transfers` arg) survive from the cloud relay. The wire *shape* for forwarded commands and attachment transfers is still there; the transport is not.

### The wire & capability gate

- Method surface: ndjson-over-WS; full catalogue in `crates/rpc/src/lib.rs:35-282` (pairing/remote-access admin, `Mutate`, watches, queue ops, `UploadChunk`/`UploadCommit`/`ReadAttachmentChunk`/`ReadImageChunk`, workspace files, terminals, git…). First call on every connection is `EngineInfo`.

## Q4 — Synthesis: options and trade-offs

### Feature 1: reaching other engines' chats from one client

The status quo: the phone pairs with each engine separately (ADR 0009); the desktop does the same via its registry (client-side state, remote-access.md §Using several engines). Nothing server-side helps, by design.

**Model B — introduction/handoff (hub relays the pairing; phone ends up a first-class client of B).** Two variants:

- **B1 — relayed redeem + relay channel (already built, `tailcat_relay.rs`).** The phone pairs with the hub A only. To add engine B, it obtains a B invite (minted by B — via the desktop's Settings → Devices on B, or `roboco engine tailcat invite --json` on B's host, pasted/scanned once — *not* per-phone pairing), then POSTs it to A's `/pairing/tailcat-redeem` and stores the returned grant + `/tailcat-relay/{id}` base as a new `PairedEngine` with a new transport kind (relay-through-A). The phone then owns its own B session (B's session table sees one more client, labeled by the phone); A stays a transparent byte pipe; B's listener stays loopback-bound. Costs: every B byte transits A (latency, hub load — the DERP role); A is a single point of failure for B reachability; A sees B's session credential once at redeem time. ADR 0004: clean — no durable state about B beyond A's own tunnel client keys, which the relay already persists today (`tailcat-relays/`).
- **B2 — invite handoff, direct tunnel (true Tailscale shape).** The hub, as a *client* of B (it can become one — it already redeems B invites in the relay path), calls B's existing `CreateTailcatInvite` RPC (served to paired sessions, Q3) and hands the fresh `roboco-tailcat:…` invite to the phone, which dials B directly through its own in-process tunnel and redeems with its own label. Zero new engine-side code on B; the phone's per-engine `TailcatRoute` machinery works unchanged; B traffic never touches A again after the handoff. Costs: the hub must hold a usable session credential to B (persisting an engine's client-credentials to another engine inside an engine data dir — new class of durable state, though it is the *hub's own* client state, exactly like a desktop's `paired-engines.json`; the current relay deliberately does *not* persist the credential, only tunnel state — speculation: an ADR-level call); and the phone keeps N tunnels up (it already does — one per paired engine today, `route.rs:51-115`; no new cost vs status quo, only the pairing dance is removed).

**Model A — gateway/master (hub forwards RPC on behalf of the phone).** The hub holds sessions to every engine and forwards requests (upstream zeron's `forward()` shape, or byte-level like the relay but hub-authenticated). Identity: either the hub authenticates as itself (B's audit trail shows only the hub — no per-client attribution, no per-client revocation from the phone's perspective) or Roboco grows delegated credentials (RFC 8693 shape: B mints scoped on-behalf-of sessions when the hub presents an assertion — new minting semantics, new revocation surface, and today's tokens are deliberately unscoped full-surface). Latency: all traffic through A always (B1's cost without B2's escape hatch). Availability: hub down ⇒ all engines unreachable. It is strictly more machinery than B for no ADR-0004 advantage; its only win is that the phone holds exactly one credential — but the phone already manages N Keystore blobs fine.

**Hybrid (recommended shape): B2 for the data plane, B1 as fallback.** Hand off invites so the phone dials engines directly (Tailscale's coordinator→P2P); if a direct tunnel can't come up (firewalled network, DERP-blocked), fall back to the hub's `/tailcat-relay/{id}` channel — the same engine can expose both, and the phone's `EngineTransport` already models per-engine transports with reconnect logic. This mirrors Tailscale exactly: introduce, connect P2P, DERP as relay of last resort. Deployment: the always-on Linux server is the hub (it already runs `roboco engine tailcat invite` and a daemon); the desktop becomes *just another client* of the hub for reachability purposes (fixing "the desktop is asleep" — today a sleeping desktop engine is simply unreachable; under the hybrid it is still the owner of its chats, and the phone reaches it directly once introduced, or not at all if it's off — which is correct per ADR 0004, since its chats are its data).

Option mapping against the hard constraints:

| Option | ADR 0004 (route vs replicate) | Wire compat | Android | Security (ADR 0008) |
| --- | --- | --- | --- | --- |
| B1 relay reuse | Pure byte routing; no state about B's data; A persists only tunnel keys (today's behavior) | None needed (HTTP endpoints exist since `e6fbfec28`); add a `tailcat-relay-v1` capability so the phone can feature-detect, per the gate catalogue | New `EngineTransport` variant + Keystore blob for the relayed credential; foreground service already lingers for active runs | Invite is a secret end-to-end (relay never logs it; errors are shape-only); A glimpses B's credential at redeem — document it |
| B2 invite handoff | Routing only; **hub's durable client-credential to B is new engine-side state** (hub-as-client; needs an ADR) | Reuses `CreateTailcatInvite` as-is; a `hub-introductions-v1`-style capability if the hub gains a "list/mint for peers" RPC (new method ⇒ no gate needed, unknown-method hiding suffices) | Phone dials B via existing per-engine `TailcatRoute`; pairing UX collapses to one scan | The handed-off invite is a secret (0600-equivalent on the phone: Keystore `tc:` blob pattern); the hub must never log it; B's session table attributes the phone by label |
| A gateway (hub-credentials) | Routing, but attribution is lost; delegation à la RFC 8693 is a credential-semantics change on every engine | New forwarding path or delegated-token mint — wire additions on both ends, capability-gated | Simplest phone (one credential), but hub availability becomes the phone's availability | Hub becomes a credential concentration point (worse than B1/B2, where each engine's credential stays with its owner… on the hub's disk in B2 — hence the ADR) |
| Hybrid B2+B1 | As above per leg | As above | Two transports per remote engine; reconnect/backoff logic already handles transport rebuilds | As above; fallback relay must preserve invite secrecy |

Speculation flags: battery/memory cost of N concurrent in-process Go tunnels on a phone is asserted but unmeasured (the app already does this for every paired engine, so it is not a new cost class); whether paired clients being able to mint invites is acceptable policy (Q3) decides if B2 needs a policy gate rather than just code.

### Feature 2: taildrop

- **Ride the WS upload path (recommended).** The phone already streams attachments to the engine owning the chat (`UploadChunk`/`UploadCommit`, Q3). A "drop a file to engine X / into chat Y" is: resolve the engine that owns the target (feature 1's transport), upload, and queue a message with the attachment refs — the queue-by-default + `pending://` machinery already makes this survive offline engines, and `message-queue-attachments-v1` gates it. No new protocol; a "drop to engine, no chat" UX would surface the engine's inbox (the uploads dir) the way `tailscale file get` does — a client-side list over `ReadAttachmentChunk`-style reads (or a small new `ListInbox`-flavored method, no gate needed per the catalogue).
- **What would need borrowing from Taildrop:** raise/parameterize the 24/32 MB caps (a capability-gated `file-drops-v1`-style string if params change), add mid-file resume (Roboco has whole-chunk idempotency already — likely *enough* given 510 KB chunks), and an offline-receiver story: either hold bytes on the phone until the engine reconnects (the message queue's existing pattern, needs phone-side staging beyond the LRU cache) or accept "engine must be online to drop" (Taildrop's own behavior — it warns and fails, with a 1-hour resume window).
- **Direct peer channel (not recommended):** would require widening `roboco-tailcat` past its one-fixed-port design (a second application port for a PeerAPI-like HTTP file service, or wrapping upstream's `recv`/`serve files` SFTP modes). That breaks the adapter's stated security stance ("only one fixed Tailcat application port", adapter.go:13-16), adds a surface ADR 0008 never blessed, and duplicates what the WS path already does — base64-in-JSON costs ~33% overhead, but the 680 k-char chunks were sized for exactly this link and the 24 MB cap, not the framing, is the binding constraint.
- **Shaped by feature 1:** whichever transport wins for feature 1 is the transport for taildrop — uploads already go over the same per-engine WS (direct tunnel or relayed channel, both byte pipes). "Drop to a chat on engine B" is impossible without feature 1's reachability; "drop to the hub" needs nothing new.

### Bottom line

1. **Feature 1:** do Model B, hybrid. Ship B1 first (the `/pairing/tailcat-redeem` + `/tailcat-relay/{id}` machinery exists and is already the browser's story — the phone is just another paired WS client); then B2 (hub hands off invites it mints on peers via the existing `CreateTailcatInvite`), keeping the relay as the DERP-style fallback. Model A (on-behalf-of forwarding, upstream's `targetDeviceId` shape) is not worth its identity/credential cost. One ADR needed: engines acting as clients of other engines (B2's hub-side credential, and generalizing the existing relay's tunnel-state precedent).
2. **Feature 2:** ride the existing WS upload path, capability-gate a raised cap and (optionally) an inbox-listing method; borrow Taildrop's staging/resume/sweep vocabulary, not its peer HTTP protocol. A direct peer file channel would mean re-architecting the tailcat adapter against its own design rule — decline.
