# Research: how upstream Zeron lets agents work across devices (2026-10-28)

Read-only research side chat `a53396d3` (its full report, with every citation, is that chat's final reply). Mirror `zeron/main` @ `ab189159f`; roboco `main` @ `c4a3d84eb`. Citations are on `zeron/main` unless prefixed `roboco:`. **(guess)** marks inference.

## TL;DR

Upstream's cross-device agent features rest on **two** mechanisms. Only one of them is portable:

1. **Synced, account-scoped state (not portable, ADR 0004).** The WorkOS account registry holds devices, chats, spaces and session status, plus per-chat Loro docs that carry a command outbox and notices.
   - Creating a chat on device X writes a registry row with `deviceId = X` (`Mutate` is **not** forwarded).
   - Sends, interrupts and answers write a command into the local replica of the chat doc. The host picks it up through sync, a durable "nudge" (`/device/{id}/nudge`), or a `RELAY_COMMAND` fallback.
   - `wait_for_turn` watches the locally synced `WatchSessions`.
2. **Request/response relay (portable).** `targetDeviceId` → `forward()` (`crates/engine/src/rpc.rs:1559-1640`) over a per-device WebSocket through a Cloudflare Durable Object (`edge/src/device-room.ts`).
   - Allowlist: `forwardable()` (`rpc.rs:2115-2236`).
   - Streams are re-subscribed and piped: `is_stream_method()` (`:2238-2253`).
   - Per-method deadlines: `forward_deadline()` (`:2085-2110`), 30 s default and longer for model lists and installs.
   - Links are cached in `LinkCache` (`crates/rpc/src/device_room.rs:783-1080`): lazy dial, 3 attempts, a readiness probe, 5→60 s cooldown, keepalive and an end-to-end echo.
   - The receiving engine serves its full RPC surface on the relayed connection.

**Consequence for Roboco:** we must forward **more** than upstream. Everything upstream gets "for free" from sync has to become an explicit forward over the fleet session: createChat, QueueCommand, WatchChats, WatchSessions, and completion notices.

## Sync vs. relay

| Capability | Upstream | Needs sync? | Roboco plan |
|---|---|---|---|
| Device list, presence | registry rows + 15 s heartbeat presence | yes | fleet book + live link status |
| Chat list, parent links, create on device X | registry rows | yes | forward `WatchChats` / `Mutate` (chat ops) |
| Session status, `wait_for_turn` | registry rows | yes | forward `WatchSessions` |
| Send / steer / interrupt / respond | doc outbox + nudge; relay fallback | yes | forward `QueueCommand`/`QueueMessage` (idempotent ids) |
| Transcript read | forwarded `WatchDocMessages` (+ local replica fallback, #1076) | relay | forward |
| Catalogs, accounts, files, terminals, uploads | forwarded | no | forward |
| Completion reports (open PR #1079) | parent's host reads the child replica, writes the parent doc's notices | yes | push with idempotent ids + pull catch-up |

## Agent tools upstream

- Tools: `whoami, list_devices, list_projects, list_harnesses, list_models, list_chats, get_chat, create_chat(s), read_chat, send_message(s), wait_for_turn, interrupt_chat, respond_to_input, archive_chat` (`crates/mcp/src/tools.rs:66-260`). Upstream has no `fork_chat` and no `notify`.
- **`create_chat`** comes from PR #706, merged `01832f2ca`:
  - host-first resolution (device, then project filtered to that device), with ambiguity rejected before any write;
  - validates against the host's catalog;
  - mints a client-side UUID; idempotent on the chat id.
- **Batches:** `join_all`, per-request errors, no rollback.
- **Delegation:** one level deep, with the child's access capped at the caller's.
- `list_devices` has **no online flag**. Device names resolve case-insensitively, and a duplicate name errors with the ids.
- Chat ids are global UUIDs in one account namespace, so there's no scoping.
- **Security:** anything signed into the same WorkOS user can drive any device of that user. There's no per-device opt-out (#730 open) and no per-call authz on the host. The MCP authenticates to its local engine with an **IPC token**.
- **Failure:** a presence gate fails fast for dark devices; otherwise 3 dials + a probe, then cooldown. A timeout drops the link, and "the remote may still complete the forwarded work".

## Changes to our plan (adopted into the spec 2026-10-28)

1. **Engine-forwarded** control, exactly upstream's shape. The MCP adds `targetDeviceId`. The engine's fail-closed guard (`roboco:crates/engine/src/rpc.rs:1452-1457`) becomes `forward()` over the fleet session, for fleet members only.
2. **A wider forward allowlist than upstream's:**
   - chat ops in `Mutate` (createChat, rename, archive);
   - `QueueCommand`, `QueueMessage`, `ForkSideChat`, `AckSideChat`;
   - `WatchChats`, `WatchSessions`, `WatchSpaces`, `WatchDocMessages`, `WatchPreviews`;
   - `ListHarnesses`, `ListModels`, `ListAgentAccounts`.

   Admin, pairing and room RPCs never forward.
3. **Ids readable by agents.** Use the raw chat UUID plus `deviceId`/`deviceName` in every output, and accept an optional `device` or a `<chatId>@<device>` form on chat-addressed tools. Resolve by concurrent fan-out over members' `WatchChats` with a chat→device cache. Opaque `ScopedId` stays client-side only.
4. **Members are identified by `EngineInfo.deviceId`,** not by book address or label (a member reachable over LAN and Tailcat must appear once). Sessions are minted lazily on first use or on a book change, then reused; re-mints revoke the old session.
5. **Origin stamps carry the device:** `(originDeviceId, originChatId)` on `QueueCommand`/`QueueMessage`, and `parentDeviceId` next to `parentChatId` on a remote createChat. Without these, ticket 03 has no return address.
6. **Completion notices: push plus pull catch-up.**
   - The child's host pushes `RecordRemoteOutcome {noticeId, …}` from a durable outbox. The parent dedupes by deterministic `noticeId`.
   - The parent's engine runs a pull catch-up over the child host's `WatchSessions` whenever its link comes up.
   - Only delegated turns are reported. The catch-up window is 6 h.
   - Acks use the **child host's serials**, and Stop suppression uses the parent's own dispatch records. **Never cross-machine wall clocks.**
7. **IPC token first.** Roboco's loopback IPC has no credential (`roboco:crates/engine/src/listener.rs:43-47`). With forwarding, any local process could drive every fleet member. Wave-10 ticket 03 ("IPC token and sign-in URL guard") lands that token, so fleet-agents is blocked by it.
8. **Idempotent retries.** `createChat` is idempotent on the MCP-minted chat id, and `QueueCommand` on its command id. Retries reuse the same ids. Sends never depend on a transcript read (#1076 lesson).
9. **ADR wording.** The amendment must explain why engine-forwarded *on-behalf-of* control is acceptable for engines although the 2026-10-25 research rejected it for clients: attribution is per presenting engine and revocable, and agents aren't clients. It also states the allowlist and that loopback IPC trust becomes fleet-wide (hence the token).

## Risks

- **Credential concentration.** One engine's `pairing.sqlite3` holds full-surface sessions on every member. This is the same class of risk as the retained fleet secret.
- **Non-idempotent forwards on timeout.** Mitigated by item 8.
- **Duplicate notices** when a parent reads the result before the pushed outcome lands. Mitigated by serial-based acks.
- **Desktop grouping.** A child row whose `parentChatId` lives on another engine may be hidden or mis-grouped by the desktop's parent/child logic. Verify in ticket 05.
- **Stream fan-out.** Each remote `wait_for_turn` holds a forwarded `WatchSessions`.
