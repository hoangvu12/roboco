# 02 — Foundation tokens

**What to build:** Every other ticket in this effort writes `var(--rb-<role>)`
and assumes the role exists. Today several desktop color roles and derived
glass/selection formulas have no web variable at all, one formula
(`scrim()`) is implemented with the wrong shape, and one (the selected-wash
alpha) is wrong specifically in light mode. After this ticket, `@roboco/theme`
and `theme.ts` emit every missing `--rb-*` variable and derived alpha the
rest of the parity work needs, every `app.css` selector that hardcodes the
selection alpha reads the new variable instead, and light mode's selected
rows/chips/tabs/modals render at the desktop's correct, lighter weight instead
of reading "too dark" (selection) or "barely-there white" (scrims).

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

subsections, especially §3.1, §3.6, §3.20) and §5 (the full gap table).

## 1. Context a fresh session needs

- `@roboco/theme` is generated by `roboco-theme-export`
  (`cargo run -p roboco-theme --bin roboco-theme-export`) from the same Rust
  the desktop compiles (`crates/theme`). A CI gate, `theme-artifact.yml`,
  fails when the committed generated artifact
  (`web/packages/theme/src/generated/index.ts`) is stale relative to the Rust
  source — **any Rust-side change in this ticket must be followed by
  re-running the export and committing the regenerated file**, or CI fails.
- The web's three neutral ladders (`ink`, `wash`, `hairline`) are NOT
  per-variant artifact data — they're computed at runtime in
  `web/packages/app/src/theme.ts::inkCssVars(appearance)` as flat RGB triples
  (`"255 255 255"` dark / `"0 0 0"` light for ink/hairline; `"235 235 235"` /
  `"26 26 26"` for wash) plus a light-mode hairline multiplier
  (`INK_HAIRLINE_SCALE = 1.35`). Call sites write
  `rgb(var(--rb-wash) / <alpha>)`. This ticket's alpha-branching fixes
  (selected-wash, band, scrim) follow this exact pattern: a new
  `--rb-<x>-alpha` custom property set per-appearance by `theme.ts`, consumed
  as `rgb(var(--rb-wash) / var(--rb-<x>-alpha))` or `rgb(0 0 0 / var(--rb-<x>-alpha))`.
- Per-variant color roles (bg, shell, text, danger, etc.) DO come from the
  generated artifact (`themeArtifact.families[].variants[].colors`), applied
  via `variantCssVars()`/`applyThemeVariant()` in `@roboco/theme`. Adding a
  new role means: add the Rust field → the builtin authors it for both
  variants → the artifact schema carries it → `COLOR_VARS` in
  `web/packages/theme/src/index.ts` maps it to a `--rb-<kebab-role>` name →
  it appears automatically in every variant's CSS vars (the loop in
  `variantCssVars` is exhaustive over `Object.entries(COLOR_VARS)`, so no
  per-variant web code is needed once the artifact carries the value).
- Accent roles, syntax roles, terminal palette, motion catalog, icons, and
  fonts are already complete 1:1 (research file's §5 confirms MATCHES) — this
  ticket does not touch any of those.
- Vocabulary: "wash" is the desktop's soft-tinted neutral fill (never call it
  an "accent tint"); a "glass"/"frost" surface is one with
  `recommendedSurfaceTreatment: "frosted"` and `data-surface="frosted"` on
  `<html>`; "scrim" is the backdrop behind a modal/drawer, always neutral
  black, never the panel color.

### 2.2 New derived alpha formulas

These are NOT new color roles — they are per-appearance **alpha scalars**
that scale an existing neutral (`wash` or flat black), mirroring exactly how
`--rb-glass-overlay-alpha`/`--rb-glass-card-alpha` already work in
`theme.ts`/`index.ts` today.

| Name | Dark alpha | Light alpha | New web var | Formula / usage | Source |
| --- | --- | --- | --- | --- | --- |
| Selected-wash alpha | `0.11` | `0.06` (half — "11% black read too dark over the bright frost", explicit desktop comment) | `--rb-selected-wash-alpha` | `background: rgb(var(--rb-wash) / var(--rb-selected-wash-alpha))` — this is `glass_selected_bg()`/`card_selected_bg()` (theme.rs:1588-1616, both identical formulas) | `theme.rs:1588-1616` |
| Band alpha (recessed picker header/footer strip) | `0.16` | `0.045` | `--rb-band-alpha` | `background: rgb(0 0 0 / var(--rb-band-alpha))` — always literal black in BOTH appearances, unlike ink/wash/hairline which tone-flip; this is `band()` | `theme.rs:1567-1578` |
| Scrim alpha (modal/drawer backdrop) | `0.60` (`SCRIM_ALPHA_DARK` default) | `0.32` (= `0.32 * (alpha_dark / 0.60)`, which for the default `alpha_dark` reduces to the flat `0.32`) | `--rb-scrim-alpha` | `background: rgb(0 0 0 / var(--rb-scrim-alpha))` — always literal black in BOTH appearances; this is `scrim()`/`scrim(alpha_dark)` | `theme.rs:999,1552-1561` |

Add these three as `layout.glass` fields in the Rust artifact
(`GlassTokens`, `crates/theme/src/artifact.rs:99-110`) even though they are
appearance-branched pairs, not single scalars — follow the exact pattern
`overlayAlphaDark`/`overlayAlphaLight` already use in that same struct (two
fields per concept, one per appearance), so `theme.ts` picks the right one
the same way it already picks `layout.glass.overlayAlphaDark` vs
`overlayAlphaLight` at `theme.ts:44`.

`theme.ts`'s `applyAppearanceToDocument` gains three more
`root.style.setProperty` calls immediately after the existing
`--rb-glass-overlay-alpha` line, following the identical
`variant.appearance === "dark" ? layout.glass.xDark : layout.glass.xLight`
ternary shape already there for the overlay alpha.

### 2.4 `.user-bubble` RGB base fix (minor)

**Current** (`app.css:3444-3446`):
```css
.user-bubble {
  /* user_bubble_bg(): white 8% dark / black 4% light (colorScheme is set on root) */
  background: light-dark(rgb(0 0 0 / 0.04), rgb(255 255 255 / 0.08));
  ...
}
```

The alpha branch is already correct (`0.04` light / `0.08` dark — matches
`user_bubble_bg()`, `theme.rs:1599-1604`), but the RGB base is pure black/white
instead of the desktop's **softened** wash tone. Fix:

```css
background: light-dark(rgb(26 26 26 / 0.04), rgb(235 235 235 / 0.08));
```

(equivalently, reference `--rb-wash`'s resolved channels if a `light-dark()`-
compatible form is easier to keep consistent with `theme.ts`'s per-appearance
`--rb-wash` value — either form is acceptable as long as the rendered color
matches `wash(0.08)` dark / `wash(0.04)` light exactly, not `255,255,255`/`0,0,0`).

### 2.5 Scrim fix — `.modal-backdrop` / `.drawer-backdrop`

**Current** (`app.css:5065-5074` and `app.css:2568-...`):
```css
.modal-backdrop {
  background: color-mix(in srgb, var(--rb-overlay) 60%, transparent);
}
.drawer-backdrop {
  background: color-mix(in srgb, var(--rb-overlay) 70%, transparent);
}
```

Both tint toward `--rb-overlay` (the panel color — **white** in every light
theme), at a flat percentage with no appearance branch. The desktop's
`scrim()` is always literal black, appearance-branched by alpha only
(`0.60` dark / `0.32` light default). Fix both to:

```css
background: rgb(0 0 0 / var(--rb-scrim-alpha));
```

This is a **behavior change in light mode**: today a light-mode modal/drawer
backdrop renders as a barely-visible white-ish wash; after this fix it
correctly darkens the page behind it, matching the desktop. `.drawer-backdrop`'s
`70%` (vs `.modal-backdrop`'s `60%`) has no distinct desktop source found in
this research pass — both collapse to the same `--rb-scrim-alpha` per this
fix; if a future desktop-side difference between modal and drawer scrim
strength is found, split them into two vars then, not now.

### 2.6 `band()` — no consumer exists yet

`--rb-band-alpha` (§2.2) has no `app.css` selector to retrofit today — the
research file found no existing "recessed picker header/footer strip"
element on the web. Add the variable now (so later tickets that build one,
e.g. a picker/palette header, can consume `rgb(0 0 0 / var(--rb-band-alpha))`
immediately) but do not invent a UI element to prove it works. Acceptance for
this row is "the variable exists and resolves to the right value," not "some
selector uses it."

### 2.7 Frosted vs. opaque glass alpha selection (feature-detect)

The desktop picks its base frost alpha (`GLASS_ALPHA_FROSTED = 0.80` vs
`GLASS_ALPHA_OPAQUE = 1.0`) by OS-compositor guarantee (macOS/Windows have
guaranteed compositor blur → frosted; Linux does not → opaque, because an
unblurred translucent window leaks the raw desktop through). The browser has
a direct capability analog: `backdrop-filter` support.

**Logic to add** (in `theme.ts` or a small new helper it imports — implementer's
choice of file, but it must run before `applyAppearanceToDocument` sets
`root.dataset.surface`):

```ts
function supportsBackdropFilter(): boolean {
  return (
    typeof CSS !== "undefined" &&
    (CSS.supports("backdrop-filter", "blur(1px)") ||
      CSS.supports("-webkit-backdrop-filter", "blur(1px)"))
  );
}
```

When `supportsBackdropFilter()` is `false`, force the resolved surface
treatment to `"opaque"` regardless of the variant's
`recommendedSurfaceTreatment` or the user's `SurfacePreference` — the same
reasoning as the desktop's Linux branch: an unsupported browser must never
render a see-through-to-nothing shell. Wire this into
`resolveSurfaceTreatment` (`web/packages/app/src/lib/appearance-store.ts:83-92`)
as an additional forcing rule ahead of the existing `frosted`/`opaque`/
`themeDefault` switch, OR at the `applyAppearanceToDocument` call site right
before `root.dataset.surface = resolveSurfaceTreatment(...)` — either
location is acceptable as long as the forcing happens unconditionally when
the feature is unsupported, and the existing three explicit preference values
still behave identically on a browser that DOES support `backdrop-filter`.

## 3. Pure logic to port

None of this ticket's Rust-side additions are algorithmic — they are static
per-appearance constant pairs (see §2.1/§2.2's tables), authored the same way
every other builtin color/alpha in `crates/theme/src/builtins.rs` already is.
There is no new formula to unit-test beyond confirming the artifact round-trip
test (`crates/theme/tests/artifact.rs` or wherever the freshness/round-trip
test lives today) still passes with the three new `ThemeColors` fields and six
new `GlassTokens` fields present. Add one new web unit test:
`supportsBackdropFilter()`'s forcing behavior in `resolveSurfaceTreatment`
(mock `CSS.supports` to return `false`, assert the resolved treatment is
`"opaque"` regardless of input).

## 5. Do not

- Do not touch `card_glass_bg()`'s web analog (`--rb-glass-card-alpha`,
  already flat and matching per the research file) — it already MATCHES, no
  fix needed.
- Do not touch `glass_overlay()`'s web analog (`--rb-glass-overlay-alpha`) —
  already matches the non-contrast-raised shape; the contrast-raise itself is
  explicitly out of scope (only matters for theme import, not shipped yet).
- Do not implement `contrast_checked_glass_alpha`/`contrast_checked_tint_alpha`
  or any of the WCAG contrast-ratio math (`relative_luminance`,
  `contrast_ratio`, `oklch_to_srgb` as a *runtime* JS function) — the web
  artifact ships pre-baked hex for every builtin variant; this machinery only
  matters for imported/custom themes, which are out of scope until theme
  import ships on web.
- Do not build `input_glass_bg()`/`composer_sidebar_tint()` as new variables
  in this ticket — they are explicitly deferred to the composer/right-pane
  surfaces that will actually consume them (see §4's last two rows).
- Do not invent a new UI element just to give `--rb-band-alpha` a consumer —
  add the variable, leave wiring it up to whichever later ticket needs a
  recessed band.
- Do not change `--rb-glass-overlay-alpha`'s numeric values (`0.50`
  dark / `0.85` light) — those are unrelated to the selection-wash fix and
  already correct.
