# Desktop: paired (remote) engines vs the local engine — fixes

Date: 2026-10-27 · Branch `fix/desktop-remote-parity`, cut from `main` = `03aba762` (v0.13.0).
Research: `research-2026-10-27.md` (same directory). One commit per item, A → D.

**Toolchain.** This host's `stable` is Rust 1.93, and the pinned zui (`0966d06`) uses
`std::hint::cold_path`, which 1.93 does not have, so `gpui` fails to compile. Everything below was
built and tested with `cargo +1.99.0 …` (already installed; the sibling Roboco worktrees build with
it too). The global and repo toolchains were not changed.

`crates/ui/src/paired_fixture.rs` (test-only) runs the desktop's real bootstrap

## A — Settings → Devices lists paired engines

**Cause (verified).** `settings/devices.rs` only rendered "Other devices" when
`workspace_scope != Some(Local)`. The scope comes from the local engine's `EngineInfo`, and
Roboco's engine is always `Local`. Paired engines' rows were in `state.devices` (the projection
adds them), but neither they nor their Forget/Rename actions were ever drawn.

**Change.** The section now shows when there are other devices, when this client can pair (the
registry is up), or when the scope is not Local. With no paired engines it keeps the
"Pair another device to see it here." empty state. Forget and Rename get `debug_selector`s keyed
by device id.

**Test.** `settings::devices::tests::paired_engines_list_under_other_devices_with_forget` pairs a
real engine and checks:
- the scope is still Local;
- "Other devices", the remote row's Forget and Rename all render, and the local row has no Forget;
- clicking Forget unpairs the engine (the registry drops to one entry and the device row goes);
- the empty state stays afterwards.

**Not verified.** Only the elements' presence was checked; nothing visual (layout, copy) was
looked at in a GUI. Settings → Remote access is unchanged (out of scope, research 1b).

## B — Side chats and subagents for chats on paired engines

**Causes (verified).**
1. `RegistrySnapshot::projected()` scoped `chat.id` but not `parent_chat_id` or
   `agent_origin.chat_id`. A paired engine's side chat therefore never matched its scoped parent.
   It was missing from the lanes (`child_chat_rows`) and from the titlebar running count
   (`tabs.rs`). `visible_chats()` still hid it from the sidebar, because it had a parent.
2. `fork_chat` called the local engine's raw client with `targetDeviceId`, which the local engine
   refuses. Even a successful reply would then have been compared raw against scoped rows.
3. `create_child_chat` minted a raw uuid. Its first send routed to the local engine, and
   `wire_params` rejected the remote scoped `deviceId` and `spaceId`. Composer completions in that
   blank side chat failed the same way: `selected_target` resolved the local engine for a scoped
   parent id.
4. (Found in the sweep.) Completion notices (`MessagePart::CompletionNotice`) name side chats by
   their raw id, and `scope_transcript_entries` did not scope them. "Open side chat" in a paired
   engine's transcript therefore found nothing.

**Subagents (verified, already correct).**
- `scope_transcript_frame` scopes spawn chips' `subagent_ref` for every transcript frame, live
  and cached. The cache stores already-scoped entries, and scoping is idempotent per engine.
  `subagent_rows` / `SubagentLane` therefore carry scoped doc ids.
- `watch_subagent_doc` → `target_for_id(scoped doc)` resolves the paired engine, and
  `wire_params` decodes `chatId`.
- The frozen snapshot fetch resolves `target_for_id(chat)`, parses the raw chat and doc ids, and
  scopes the blob's entries with the owning key.
- `running_subagents_for` reads the session row by scoped `chat_id`; the projection already
  scoped `session.chat_id`.

What was broken around subagents was only the running count's side-chat half (cause 1).

**Sweep ("etc etc").**
- Every remaining `parent_chat_id` consumer compares ids inside the projected id space, so all of
  them are fixed by cause 1: `change_requests.rs:305`, `state.rs:1283` link roots,
  `composer.rs:7382` completion params, the rename surface (`shell.rs:5812`), fork-from-here
  (`shell.rs:3944`), notification pings, and the command palette.
- Lane row actions (rename, archive, delete, resume) go through `Shell::mutate` →
  `target_for_id`, which was already routed.
- `running_pill.rs` reads no chat ids.

**Changes.**
- `roboco_engine_client::registry::scope_chat`: one shared chat projection (id, device, space,
  checkouts, `parent_chat_id`, agent origin), used by `projected()` and by the fork reply.
- `scope_transcript_entries` also scopes completion-notice side ids.
- `fork_chat` routes through `state.target_for_id(&source.id)`, shows a resolution failure in the
  composer, and scopes the reply before the parent check.
- `create_child_chat` mints `ScopedId::encode(<parent's engine>, uuid)`.
- The titlebar count moved into `session_lanes::running_lanes` so a test can read it; behaviour
  is unchanged.

**Tests.**
- `roboco-engine-client`:
  - `projection_scopes_side_chat_parents_and_agent_origins`: local rows stay raw; remote rows
    point at the scoped parent.
  - `transcript_scoping_covers_subagents_and_completion_notices`: notice side ids are scoped,
    and scoping twice is stable.
- `roboco-ui` `shell::remote_lanes_tests::a_paired_engines_chat_lists_counts_opens_and_creates_its_lanes`
  uses two real engines. A paired engine holds:
  - a parent chat whose transcript has a running and a finished spawn chip;
  - a side chat;
  - a live subagent doc;
  - the finished subagent's frozen blob.

  It asserts:
  - the side chat lists under the scoped parent and is gone from the sidebar;
  - the running count is 2 subagents + 1 working side chat;
  - the lanes hold the active and finished subagent rows with scoped doc ids;
  - the live subagent tab streams the paired engine's doc, and its watch target is that engine;
  - the finished subagent tab reads the frozen blob from the paired engine;
  - an existing side chat opens in a tab whose own registry resolves and connects the paired
    engine;
  - Fork creates the copy on the paired engine and lists it under the parent;
  - "New side chat" mints a paired-engine id, and its first send creates the chat there with
    `parentChatId = parent`, lists it, and lands nothing on the local engine.
- Negative checks (temporary reverts, then restored). Each one makes the test fail at the
  expected step:
  - dropping the `parent_chat_id` scoping fails the listing assertion;
  - sending the fork to the local engine fails the fork step;
  - minting a raw uuid fails the engine-key assertion.

**What the test cannot cover, and why.** The two *working* session rows used for the running
count are applied client-side, in the same `AppState` update that counts, with ids scoped exactly
as the projection scopes them. An engine publishes live status only for its own harness runs:
workspace session rows are filtered to the engine's own device and then dropped in
`merge_sessions`. There is no seam to make a remote engine report "Working" without running a
real harness turn.

**Note (pre-existing, unchanged).** Every side-chat pane's `AppState` opens its own
`EngineRegistry` (`side_chat_state` → `attach_engine` → `spawn_registry_watch`), and with it its
own connections to every paired engine. D accounts for this (see below).

## C — Per-chat engine calls go to the owning engine

**Causes (verified).** Each of these called `state.engine()` (the local raw client) with
`targetDeviceId` or a scoped id. Roboco engines relay nothing, so all of them failed for a
paired engine's chat.

| # | Feature | Fix |
|---|---|---|
| 5a | Session card +/− totals (`shell/session_info.rs`, `WatchCheckoutDiffs`) | `target_for_id(chat)`; frames go through `scope_checkout_frame`, as the Changes pane already does |
| 5c | Files panel Git decorations (`files/git_status.rs`, `WatchWorkspaceGitStatus`) | `target_for_id(chat)`. The reported `device_id` is scoped with the owner key before `accepts()` compares it to the scoped chat device. That comparison was a second, independent bug. |
| 5d | Sidebar section "Archive all" (`shell/sidebar_sections.rs`) | Each session archives on its own engine (a section can mix engines). A session that fails to resolve counts as a failure. |
| 5e | Pasted `@file` / slash / skill resolution (`composer.rs`) | `request_routing::selected_target`, like typed completions |

- **5b** (session-info ports) does not exist on this base: `session_info.rs` has no previews
  list. The only `WatchPreviews` user, the browser tab, already takes an `EngineTarget`.
- `EngineTarget::same_target` (same key, same registry) replaces `EngineHandle::same_connection`
  in the Git-status source cache and in archive-all's "runtime replaced" guard.

**Guard.** `request_routing::tests::raw_local_client_calls_stay_on_the_allow_list` scans
`crates/ui/src` with whitespace stripped, so rustfmt line breaks cannot hide a chain. It counts,
per file:
- raw RPC chains (`.client().call…` / `.client().subscribe…`);
- captures of the local handle (`.engine().cloned()`).

It fails on any difference from an allow-list with reasons:
- `lib.rs`: quit;
- `state.rs`: bootstrap watches, the local-device probe, engine boot tests;
- the engine's own settings pages: auto-resume, completion, thread naming, remote access;
- `harness_updates.rs`;
- test teardown in `shell/spaces.rs` and `paired_fixture.rs`.

**Tests.**
- `shell::session_info::tests::a_paired_engines_chat_shows_its_diff_totals` uses real engines and
  a git repo on the paired engine with one modified file. The card's totals reach `(+2, −1)`.
- `shell::sidebar_sections::tests::sections_archive_all_reaches_each_sessions_own_engine` uses a
  section holding one local and one paired session. Both end up archived on their own engines,
  with no failure notice.
- `files::git_status::tests::a_paired_engines_status_matches_its_scoped_device` is a unit test:
  the owner-scoped device is accepted, a different owner's is rejected, and local stays raw.
- The existing `sections_archive_all_sends_every_request_and_reports_failures` now pumps its
  current-thread tokio runtime. `EngineTarget::call` writes the request from a tokio task (the
  composer tests' idiom).

**Not verified end to end.**
- Pasted-reference resolution: only the guard and code review. It now resolves its engine the
  same way the six typed-completion call sites do.
- Git decorations: unit test only. No `FilesSurface` was driven against a paired engine.

## D — Tailcat pairings survive a desktop restart

**Cause (verified).** `tailcat_pairing.rs` (old lines 33-36) documented that the saved endpoint
is the forwarder's loopback URL. The forwarder dies with the process. After a restart,
`supervise()` dialed a dead port forever, and nothing knew the Tailcat address needed to start a
new forwarder: only the URL and credential were saved.

**Change (≈ M, as estimated).**
- `roboco-engine-client`:
  - `SavedEngine.route: Option<String>`. It is additive (`serde(default)`, omitted when `None`;
    ADR 0005), and lives in the same `paired-engines-v1.json` as the credential, with the same
    atomic tempfile write (0600 on unix). `SavedEngine` has no `Debug`.
  - `ResolvedPairing.route`, so a resolver hands the route over at pairing time.
  - `PairingResolver::restore(route, data_dir) -> Option<Result<RestoredRoute>>`, a default
    method returning `None`, so other resolvers are unaffected.
  - `supervise` → `routed_endpoint`: for an entry with a route and no live transport, the
    resolver rebuilds it in `spawn_blocking`. The new keepalive is stored on the entry and the
    in-memory endpoint is updated.
  - A route no resolver claims keeps dialing the saved endpoint, as before.
  - When a connect fails and the forwarder's loopback no longer accepts TCP, the keepalive is
    dropped so the next pass rebuilds it. This mirrors the Android route's rule 1. A live
    loopback is left to recover by itself.
  - Errors carry fixed text, never the route.
- `roboco-ui` `TailcatResolver`:
  - Pairing saves `tailcat:<address>`.
  - `restore` starts a forwarder for it.
  - Forwarders are shared process-wide per address through a `Weak` map. Each side-chat pane
    opens its own registry, and without sharing every pane would start its own adapter process.
  - A shared forwarder whose loopback stopped accepting is replaced.
  - The address (a secret, ADR 0008) appears only in the store and in memory.

**Tests.**
- `roboco-engine-client`
  `registry::tests::resolver_routes_are_saved_and_rebuilt_after_a_restart` uses a fake resolver
  over a real engine. It checks that:
  - pairing saves the route and does not call `restore`;
  - the transport dies with the registry;
  - after the saved endpoint is rewritten to a dead loopback port (the restart), a reopened
    registry calls `restore` exactly once, reconnects, and serves RPC;
  - forgetting drops the rebuilt transport.

  Negative check: bypassing `routed_endpoint` makes it time out on the dead endpoint.
- `roboco-ui` `tailcat_pairing::tests::restore_claims_tailcat_routes_and_never_echoes_the_address`
  checks that only `tailcat:` routes are claimed, and that a failing restore's error text never
  contains the address.

**Not verified.**
- Nothing in D ran against a real `roboco-tailcat` adapter or a real Tailcat network. Source
  builds carry no adapter, and the adapter process cannot be faked in the UI crate.
- Also unexercised: forwarder sharing between registries, and rebuilding a forwarder that died
  mid-session.
- A real check needs a release build: pair over a `roboco-tailcat:` invite, quit, relaunch, and
  confirm the engine reconnects.

**Existing pairings.** Tailcat pairings made with v0.13.0 or earlier saved no route; the address
was never persisted anywhere durable. Those entries stay offline after a restart and must be
paired again once, after which they survive restarts. The user's servers fall in this group, so
they need re-pairing once after installing a build with this fix.

D is its own last commit, so it can be dropped.

## Deviations from the brief

- B also scopes completion-notice side-chat ids (found in the sweep).
- B's titlebar count moved into `session_lanes::running_lanes` for testability.
- B's running count uses client-side live session rows (see above).
- C's tests are spread over the modules that own the private code (`session_info`,
  `sidebar_sections`, `git_status`) instead of one two-engine file. `EngineTarget::same_target`
  was added to `roboco-engine-client`.
- No new dependencies.
