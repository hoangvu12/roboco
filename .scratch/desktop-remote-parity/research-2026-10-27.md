# Desktop: paired (remote) engines vs the local engine — parity research

Date: 2026-10-27 · Read-only code research; no GUI run, no `cargo check` (no code was changed).
Refs: tag `v0.13.0` (03aba762, what the user runs) and HEAD of `feature/fleet-follow` (5ce556fa).
Line numbers are `path:line` at **v0.13.0** unless marked HEAD. Where a file is byte-identical
between the two, the same line numbers hold on HEAD.

## Summary

The desktop **does** hold a live, routed connection to every paired engine. `EngineRegistry`
watches each engine's chats/spaces/devices/sessions and merges them into `AppState`. That is why
projects and chats appear and chatting works: transcript, send, queue and account rings all
resolve their engine through `request_routing` and `target_for_id`. Several other features break
remotely, for four separate reasons:

1. **Devices page.** Settings → Devices hides the whole "Other devices" section whenever the
   local workspace scope is `Local`, and in Roboco it always is. The paired servers' rows are in
   state but never rendered, and their **Forget** and **Rename** buttons are hidden with them.
   A port of upstream b782d043 (f1eaa892, 2026-09-28) brought this in.
2. **Side chats.** The registry projection scopes `chat.id` but not `chat.parent_chat_id`.
   A remote side chat's parent pointer therefore never matches its (scoped) parent. Remote side
   chats vanish from the parent's lanes, the running count and the sidebar. The Android core does
   scope this field; the desktop projection does not.
3. **Calls that skip routing.** A set of features call the **local engine's raw client** with an
   upstream-style `targetDeviceId` or a scoped id: fork-to-side-chat, the session-info diff
   totals, files-panel git decorations, bulk archive, pasted-reference resolution, and on HEAD
   the session-info ports list. Upstream zeron's engine relays `targetDeviceId` to the owning
   device. Roboco removed that relay, so the local engine refuses these calls
   (`engine/src/rpc.rs:1452`).
4. **Blank side chats.** A blank side chat on a remote parent gets an unscoped id. Its first
   send is routed to the local engine, and the client-side guard rejects it.

None of these causes was introduced by the wave-9 merge. All of them exist identically in
`v0.13.0` and on HEAD. HEAD adds one new instance (the session-info ports list). HEAD also lacks
two tag features that matter for remote engines: the 100 MB attachment deadlines and caps, and
the Rooms page. Its line simply never contained main's post-`758394ba` commits (see "Tag vs HEAD
topology").

I could not trace symptom 4 (context usage) to a client-side cause. The code path is
engine-neutral, so it is listed as unverified.

## Symptom 1 — added servers absent from Settings → Devices / Remote access

### 1a. Devices page: "Other devices" never renders (CONFIRMED, high confidence)

**Where the UI decides:** `crates/ui/src/settings/devices.rs:551-562`

```rust
// A local-only workspace never has other devices to list.
.when(workspace_scope != Some(WorkspaceScope::Local), |el| {
    el.child(widgets::section_label(&theme, "Other devices").mt(px(28.0)))
        .child(others_block)
});
```

**What data it reads:**
- `devices.rs:363-378`: `state.devices`, split into the local row and everything else.
- Remote rows **are** present. `RegistrySnapshot::projected()` (`engine-client/src/registry.rs:161-185`)
  pushes every paired engine's device rows, using scoped ids or a "Remote engine" placeholder.
  `spawn_registry_watch` then feeds them through `state.apply_devices(projected.devices)`
  (`ui/src/state.rs:3056`).

**Why they are hidden:**
- `state.workspace_scope` is set from the **local** engine's `EngineInfo`
  (`ui/src/state.rs:2611`; HEAD `:2593`).
- Production always opens `EngineProfile::local` (`engine/src/lib.rs:491-493`), and that profile
  is `WorkspaceScope::Local` (`engine/src/profile.rs:32-36`).
- So the gate is always false and the section is never shown.
- In upstream zeron, `Local` means "signed out, no cloud devices", where the gate makes sense.
  In Roboco the gate is wrong.

**Side effects:**
- The per-row **Forget** button (`devices.rs:393, 501-513`) and **Rename** (`:514-523`) for
  paired engines live only inside those hidden rows.
- On v0.13.0 there is no UI to forget or rename a paired server.
- The "Engines" connect field (`:605-662`) still renders, so pairing works but gives no visible
  result on this page.

**Origin:**
- Introduced by `f1eaa892` ("Port upstream b782d043 …", 2026-09-28).
- Before it (`f1eaa892^`), all devices rendered in one list with Forget, and Local scope only
  changed a badge.
- `git log -S` finds no other commit touching the gate.

**Status:** present in `v0.13.0` and identical on HEAD. Not merge-related.

### 1b. Remote access page lists only this machine's incoming clients (CONFIRMED, by design / UX gap)

`crates/ui/src/settings/remote_access.rs` is "Settings for this engine's listener and paired
clients" (line 1):
- Every call goes through `state.engine()` (the local engine's raw client, `:71-90`).
- The list is "Paired sessions" (`:429-497`). These are clients that paired **to this desktop**,
  not engines this desktop paired **to**.
- After the desktop pairs to a Linux server, the server appears under the server's own Remote
  access, not the desktop's.
- There is no UI to view or manage a remote engine's listener (for example, to mint a pairing
  link on a server for a phone).

On v0.13.0, Settings → Rooms (`settings/rooms.rs`, removed on HEAD) was the only page with
per-engine membership status. Fleet-follow ticket 03 adds a Fleet card to Remote access with
per-engine "In / Not in yet" state, which partly covers this.

**Status:** identical tag and HEAD.

### 1c. Related risk: Tailcat-paired engines do not reconnect after a desktop restart (CONFIRMED known limitation)

`crates/ui/src/tailcat_pairing.rs:33-36`:

> "A restarted desktop does not recreate the forwarder for an already-saved Tailcat entry."

- The saved endpoint is the forwarder's loopback URL (`:42-43`), so after a restart
  `supervise()` dials a dead port forever and the engine shows Reconnecting.
- Cached rows (`registry.rs:537-547`) keep that engine's projects and chats visible, but
  read-only.
- This does not match "I can chat normally", so it is probably not what the user hit. It is
  listed because "after a restart, servers look present but are offline" would be the next
  report.

**Status:** identical tag and HEAD.

**Fix outline (1a):**
- Change the gate to "the registry is present, or the scope is not Local". Simplest: drop the
  gate and show the "Pair another device…" empty state.
- Add a UI test that pairs a fake engine and asserts the remote row and Forget render.
- Size: **S** (about 5 lines plus one test).

**Fix outline (1b):**
- The ticket-03 Fleet card covers per-engine status.
- Optionally add a device selector to Remote access that routes the five remote-access RPCs
  through `request_routing::device_target`. The engine already serves them on any authenticated
  connection; check that a paired session is allowed to call them.
- Size: **M**.

**Fix outline (1c):**
- Persist the Tailcat invite address, not just the forwarder URL.
- On `open_with`, have the resolver restart a forwarder for saved Tailcat entries.
- Size: **M**.

## Symptom 2 — side chats not shown for chats on a remote engine (CONFIRMED, high confidence)

### 2a. Projection does not scope `parent_chat_id`

**The projection:** `crates/engine-client/src/registry.rs:145-153` (HEAD `:143-151`) rewrites
these fields to `engine:v1:…`:
- `chat.id`
- `device_id`
- `space_id`
- `checkout_id`
- `source_context.checkout_id`

It does **not** rewrite `parent_chat_id`, and `agent_origin.chat_id` is not scoped either.

**How the UI uses that field:**
- **Lanes list:** `child_chat_rows` (`ui/src/shell/session_lanes.rs:181-189`) filters on
  `chat.parent_chat_id.as_deref() == Some(chat_id)`. For a remote parent, `chat_id` is scoped but
  the child's `parent_chat_id` is the remote engine's raw id, so it never matches.
- **Running count:** the titlebar's running-lanes count (`ui/src/shell/tabs.rs:372-380`) uses the
  same comparison.
- **Sidebar:** `visible_chats()` (`ui/src/state.rs:1851-1855`; HEAD `:1841-1845`) hides any chat
  whose `parent_chat_id` is `Some`.

**Result:** every side chat on a remote engine is invisible. This covers agent-created ones
(`create_chat` via the MCP server on the server) and user-created ones. They are hidden under the
parent and absent from the sidebar.

**Proof the omission is local to the desktop:** the Android core's projection scopes the field,
`crates/mobile-client/src/workspace/view.rs:583`:
`chat.parent_chat_id = chat.parent_chat_id.as_deref().map(&scope);`.
The outbound direction is already handled: `routing.rs:42` decodes `parentChatId`.

### 2b. "Side chat" (fork) on a remote chat goes to the local engine

`ui/src/shell/side_chats.rs:57-104` `fork_chat`:
- Takes `state.engine()` (`:69`) and calls `engine.client().call_as(FORK_SIDE_CHAT, …)` (`:85-87`).
  This is the local engine's raw client, which bypasses the registry.
- `fork_dialog::fork_params` (`shell/fork_dialog.rs:63-68`) sends `sourceChatId` and
  `parentChatId` as scoped ids, and `targetDeviceId` as the remote device.
- The local engine fails closed (`engine/src/rpc.rs:1450-1459`):
  "engine … is not connected; requests must use its own connection".
- The fork dialog's harness list *is* routed (`fork_dialog.rs:250` via `selected_target`). The
  dialog therefore populates correctly and only the confirm fails.
- Even if routed, the reply check at `side_chats.rs:93-99` compares the unscoped reply
  `parent_chat_id` against scoped `state.chats` ids, so the new side chat would not open.

### 2c. Blank side chat on a remote parent goes to the wrong engine on its first send

**Where the id comes from:**
- `side_chats.rs:122-146` `create_child_chat` mints `chat.id = uuid::Uuid::new_v4().to_string()`
  (`:130`). The id is raw, not `ScopedId::encode(remote_key, …)`.
- The device id and space id are copied from the scoped parent.

**What happens on send:**
- `Composer::send` resolves `request_routing::selected_target` (`ui/src/composer.rs:8768`).
- `target_for_id(raw uuid)` resolves to the **local** engine.
- `wire_params` then rejects the scoped `deviceId`/`spaceId` of another engine
  (`engine-client/src/routing.rs:21-26`): "Request identity belongs to another engine".
- The canvas's new-chat path does this correctly (`composer.rs:8784`,
  `ScopedId::encode(engine.key(), uuid)`).

I did not verify in the GUI what error text the user would see.

**Status:** all of 2a–2c are identical at tag and HEAD. Not merge-related. Never implemented
for remote engines on the desktop. Upstream zeron has no client-side engine registry (one cloud
registry, global ids), so there is nothing to port.

**Fix outline:**
1. Scope `parent_chat_id` and `agent_origin.chat_id` in `RegistrySnapshot::projected()`, the same
   way mobile does. Add a projection unit test in `engine-client/src/registry/tests.rs`.
   Size: **S**. This alone restores listing, the running count and sidebar hiding.
2. `fork_chat`: route through `state.target_for_id(&source.id)` (an `EngineTarget`) instead of
   `state.engine().client()`. The registry strips `targetDeviceId` and decodes the ids. Scope the
   reply before the parent check. Size: **S**.
3. `create_child_chat`: mint `ScopedId::encode(parent_engine_key, uuid)`. Size: **XS**.
4. Add a two-engine UI regression in the style of `request_routing.rs:41`
   (`two_real_engines_…`): fork, create blank and list for a remote parent. Size: **M**.

## Symptom 3 — "device picker" not offering remote engines (PARTLY CONFIRMED, medium confidence)

**What the code does:**
- The new-chat device chip lists `Pickers::device_rows` (`ui/src/pickers.rs:2642-2687`; HEAD
  `:2892-`).
- **Without a project picked:** it offers every row in `state.devices`, which includes paired
  engines' rows (same data as symptom 1). This looks correct; I found no gate.
- **With a project picked:** it offers only `state.project_members(space)` (`:2651-2668`,
  `state.rs:1974-1993`), meaning spaces sharing the `repository_id` (`proto/src/view.rs:264-269`).
  If the selected project exists only on this PC, the picker shows only this PC. This is by
  design ("one row per device holding a checkout"), but it reads as "remote engines are missing".
  To target a server, the user must pick "No project" or a project that lives on the server.
- **With an existing chat open:** there is no device picker at all. The selectors render only on
  the new-chat canvas (`composer.rs:11492-11496`), for local and remote chats alike.

**Other device pickers (no remote-specific gate found):**
- The Add-project flow lists all `state.devices` (`shell/spaces.rs:5583-5593`).
- The fork dialog offers harnesses, not devices.

**Unverified:** I could not trace which picker the user means. If they saw remote devices
missing with "No project" selected, I have no code explanation, and it would need a repro.

**Status:** identical tag and HEAD (the HEAD `pickers.rs` diff is typed-path and checkout-kind
work only).

**Fix outline:**
- With a project selected, also list the other devices as "Run without this project on …" rows,
  which switch to that device and No project (`select_device` already does this fallback,
  `state.rs:1927-1946`).
- Or add a hint row. Size: **S–M** (UX decision needed).

## Symptom 4 — context usage not shown for remote chats (NOT REPRODUCED IN CODE, low confidence)

**Traced path:**
- The context ring (`ui/src/account_usage.rs:917-928`, `context_usage.rs:113-117`) reads
  `state.context_usage`.
- That value is set only in `receive_transcript_update` (`state.rs:1554-1557`) from
  `TranscriptUpdate.context_usage`.
- Those frames come from the routed transcript watch (`state.rs:3283-3400`,
  `handle.subscribe_checked(WATCH_DOC_MESSAGES)` on the chat's own `EngineTarget`). This is the
  same stream that makes remote chats work.
- The engine stamps `context_usage` into every frame for any subscriber (`engine/src/rpc.rs:1375-1390`
  live, `:1409-1412` opening tail). The value is written from harness `ContextUsage` events
  (`engine/src/sessions.rs:4506-4510`).

I found no local-only gate.

**Hypotheses, unverified:**
- (a) The ring shows only once a window is known (`has_window` needs `window > 0`). The Claude
  harness reports the window only at turn end (`harness/src/claude/normalize.rs:854`). A remote
  chat with no completed turn since the engine started would show nothing.
- (b) The user may mean the session-info card's other numbers, such as the +/− diff totals,
  which really are broken remotely (symptom 5).
- (c) A harness or version difference on the servers.

**Status:** identical tag and HEAD.

**Next step:** ask the user (see open questions), or reproduce with one paired engine and a
completed turn.

## Symptom 5 — other features that work locally but not for paired engines (CONFIRMED unless noted)

**Common root cause:** these call `state.engine()` (the local engine's raw client) and either
pass `targetDeviceId` or put a scoped id in the params. In upstream zeron, the engine relays
`targetDeviceId` to the owning device (`upstream/main crates/engine/src/rpc.rs:45-47, 885`), and
upstream's `session_info.rs:127,143` and `side_chats.rs:124,141` use exactly this pattern. Roboco
removed the relay, and its engine refuses a foreign `targetDeviceId` (`engine/src/rpc.rs:1450-1459`).
The correct Roboco pattern is `state.target_for_id(id)`, `request_routing::selected_target` or
`device_target`, which resolve an `EngineTarget` whose `wire_params` strips `targetDeviceId`.

| # | Feature | Evidence (tag; HEAD same unless noted) | Effect for remote chats |
|---|---|---|---|
| 5a | Session-info card: uncommitted +/− totals next to the branch | `shell/session_info.rs:78-139` (HEAD `:98-160`): `state.engine()` + `targetDeviceId` → `WATCH_CHECKOUT_DIFFS` on the local client | Never shows; retries every 2 s forever |
| 5b | **HEAD only:** session-info ports / previews list | HEAD `shell/session_info.rs:164-200`: `state.engine().client().subscribe(WATCH_PREVIEWS, {chatId: <scoped>})` (port of upstream #1023, `55b30edd`) | Empty for remote chats. **New on HEAD, not in v0.13.0** |
| 5c | Files panel git decorations (modified/untracked badges) | `files/git_status.rs:298` takes `state.engine()`; `:183-196` subscribes `WATCH_WORKSPACE_GIT_STATUS` on the local client with the **scoped** `space_id` (`:322-326`) | No git badges in remote file trees. Reading and editing files works (it is routed by `FilesRequestContext.engine`, `files/client.rs:26-48`) |
| 5d | Sidebar section "archive all" | `shell/sidebar_sections.rs:222-249`: local client `Mutate setChatArchived {chatId: <scoped>}` | Remote chats fail: "Could not archive N sessions" |
| 5e | Pasted `@file` / slash-reference resolution in the composer | `composer.rs:7476-7530`: local client `LIST_COMMANDS` / `LIST_SKILLS` / file search with the remote `targetDeviceId` | Pasted references are silently not resolved. Typed completions are routed and fine (6 routed call sites in `composer.rs`) |
| 5f | Fork to side chat | see 2b | Fails |
| 5g | Harness update banner/checks | `shell/harness_updates.rs:214, 702` (HEAD `:233, 722`): local only | Servers' harness updates are never surfaced (design gap) |

These work for remote chats and need no change: transcript, send, queue, account-usage ring,
model and harness catalogs, fork-dialog harness list, terminals, file read and write, uploads,
change requests, Settings → Harnesses and Accounts. They all resolve via `target_for_id`,
`selected_target` or `device_target`; see `request_routing.rs` and its two-engine test at
`:41-246`.

**Fix outline (one PR, "route every engine call", size M overall):**
- 5a, 5b, 5c, 5d, 5e: replace `state.engine()` + `targetDeviceId` with the owning
  `EngineTarget`:
  - `target_for_id(chat.id)`;
  - for git status, `target_for_id(&context.engine)` by key: the `FilesRequestContext` already
    carries `engine`.
  - Then drop `targetDeviceId`, since `wire_params` strips it anyway, and scope any reply rows
    with `scope_checkout_frame`.
  - Each is XS–S.
- Add a lint-style test asserting no `state.engine()` / `.client()` RPC calls outside an
  allow-list (settings that are intentionally local, quit, bootstrap). Size: **S**.
  This catches the next upstream port that carries the relay pattern in; 5b shows it already
  happened once in wave 9.
- 5g, 5h: optional device tabs in the existing pattern of Harnesses and Accounts. Size: **M** each.
- 5j: re-land `4ba44e09` and `32644102` onto the trunk; arguably part of the fleet-follow "re-land
  from v0.13.0" work. Size: **S**.

## Open questions for the user

1. **Which page?** Settings → **Devices** (which has the "Engines" Connect field) or Settings →
   **Remote access**? On v0.13.0, Devices *should* list servers but cannot (1a). Remote access
   never will (1b). Did they also try Settings → **Rooms**?
2. **How were the servers paired?** A `http(s)://…/pair#token=…` URL, or a `roboco-tailcat:`
   invite? Was the desktop restarted after pairing? If it was restarted and the pairing used
   Tailcat, the servers should show as offline (1c), so the answer helps separate 1c from the
   rest.
3. **Side chats:** were the missing side chats created by an agent (MCP `create_chat` on the
   server), by "Side chat"/fork in the desktop UI, or by "New side chat"? Did fork or create show
   an error in the composer? The code predicts an error for fork and for a blank side chat's first
   send.
4. **Device picker:** which one? The new-chat device chip next to the project chip, or the
   Add-project device step? Was a project selected at the time? If the remote engines are missing
   with "No project" selected, I need a repro, because the code says they should be listed.
5. **Context usage:** is the ring missing in the composer footer for remote chats even after a
   turn has *completed* in that chat? Which harness (Claude Code, Codex, …)? Or did they mean the
   session-info card's numbers (+/− totals, side chats, ports)?
6. **Both Windows PCs:** does each PC's desktop show the *other PC* the same way? Expected: the
   same as the servers. Each desktop's local engine is `Local` scope, so 1a hits every paired
   engine regardless of OS.
