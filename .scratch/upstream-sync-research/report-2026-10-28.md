# Why upstream syncs take so long, and what to do about it (2026-10-28)

Research only. Nothing in the repo was changed, apart from this folder.

**Files in this folder**
- `report-2026-10-28.md`: this report.
- `translate-proto.py`: the rename-translation prototype.
- `presence-proto.py`: the "already ported?" check.
- `proto-sample.tsv` / `proto-results.tsv`: the 30-commit sample and its results.
- `external-practices.md`: the full write-up of how other forks do it, with sources.

## The short answer

- **The rename is not what costs us time.** It touches 1.6% of upstream's changed lines. In a 30-commit test, translating names changed the result for only 3 commits.
- **Time goes to two places.**
  - Re-checking work we already did. The wave-10 audit re-verified 568 commits, and 88% of them turned out to be already ported, policy skips, superseded or declined.
  - Porting into files that both sides have rewritten heavily.
- **Recommended fix:**
  - Keep a permanent ledger of every upstream commit and what we decided about it.
  - Triage new commits automatically.
  - Run a translated cherry-pick as the first step of every port.
  - Sync in small weekly batches instead of big waves.
- None of this changes ADR 0003. It is still "cherry-pick only", just done better.

Waves 1–2 ported more than 300 upstream commits in a week, when Roboco and zeron were still close. Since then, waves have shrunk to 10–30 commits each and still take days to weeks. Divergence grows, so each port costs more. GitLab saw the same curve before it merged CE and EE (see section b).

### Paperwork vs code

- **Planning text:** about 20,000 lines.
  - 7 drift reviews plus the full re-audit: about 5,900 lines.
  - Wave specs and 203 tickets: about 14,000 lines.
  - 127 commits touched these folders.
- **Code in port commits:** about 276,000 changed lines, 37,600 of them tests.
- **A typical small case:** upstream `970f41fa7` was a 24-line change ported "byte-for-byte" (the commit's own words). It still got a wave spec entry, a ticket, and a 35-line ticket update.

### The full re-audit mostly confirmed work already done

| Audit class | Commits | Share |
|---|---|---|
| PORTED (already in Roboco) | 348 | 61% |
| SKIP / SUPERSEDED / DECLINED | 150 | 26% |
| MISSING or PARTIAL (the actual targets) | 70 | 12% |

The audit was needed because nothing trustworthy recorded what had been done:
- Waves 1–2 left no records.
- Ticket labels drifted.
- One ticket (wave-9 06, #977) was marked "all landed" while 14 slices were missing.

A permanent ledger removes that need.

### The rename is small

Measured over all 533 upstream commits that touch non-iOS, non-cloud code:
- Lines containing `zeron`, `Zeron` or `ZERON` (ignoring `zeronsh`): **7,422 of 479,258 changed lines (1.55%)**.
- Files on renamed paths (`apps/zeron/...`): **28 of 4,262 (0.66%)**.
- About half the commits contain at least one such line. The median commit has 0.24% renamed lines.

So the rename is a small tax spread over half the commits. It is not the bottleneck.

The other main source is code Roboco never took. Some upstream commits sit on top of earlier upstream work we skipped (#677 panels, #1018 settings search, upstream's mobile `client` crate). The patch then has nothing to land on.

### CI

| Android | 39 min | 22 of 29 |

One PR per small port would be expensive. Batching ports (lanes today, weekly batches below) is right.

### Best estimate of the split

This is inferred from the artifacts above, not timed.

| Bucket | Share | Basis |
|---|---|---|
| Audit, triage, planning, ticket writing | ~40–50% | Wave 9 and wave 10 so far are 100% planning. 88% of the last audit re-confirmed known state. About 20k lines of planning text. |
| Real porting (diverged files, missing prerequisites) | ~30–40% | 18 of 30 sampled commits need real porting. |
| CI and verification | ~15–20% | 64–76 min Windows runs, flaky Android and UI jobs. |
| Mechanical renaming | <5% | 1.55% of lines. Changed the outcome for 3 of 30 commits. |

### Is ADR 0003 right to rule out merging or rebasing? Yes.

- A merge of 579 commits would hit every conflict in the hot files at once. In the sample, a plain cherry-pick conflicts or misses its target for 24 of 30 commits, before any deleted cloud code comes into it.
- Upstream still has `edge/`, `apps/ios/` and cloud/account code in shared crates. ADR 0004 removed those on purpose, and a merge would keep putting them back.
- Rebasing Roboco (1,639 commits since the split) onto upstream is worse: each of our commits would replay against upstream's rewrites of the same files.
- Vivaldi and Igalia document weeks of work per Chromium rebase, even with a small downstream (see `external-practices.md`).

## (c) Prototype results (30 commits)

**How it works** (`translate-proto.py`):
1. List the files the upstream commit changed.
2. Drop files on the skip list: `apps/ios`, `apps/landing`, `apps/www-redirect`, `edge`, upstream's own `apps/android`, and `crates/zatex`.
3. Map paths: `apps/zeron` → `apps/roboco`, `crates/mcp` → `crates/roboco-mcp`, and `crates/client` → `crates/mobile-client`, which is a low-confidence mapping.
4. Rewrite names per AGENTS.md, keeping `zeronsh` and `ZERON_GPU_STATS`.
5. Run a 3-way merge per file: Roboco's file, upstream's file before the commit, and upstream's file after it.

This is exactly what `git cherry-pick` would do against an already-renamed upstream. It writes nothing to the repo.

**What was tested:**
- **Ported commits** were replayed onto Roboco as it was just before our real port. I then measured how much of our real port the output already contained.
- **Missing commits** were applied to today's `main`.
- Every commit was also run as a plain cherry-pick with no translation, to isolate what the rename map buys.

**Classes:**
- CLEAN: no conflicts.
- TRIVIAL: at most 3 small conflict regions, or only `Cargo.lock`.
- REAL: anything else, or a file with no Roboco counterpart.

### End-to-end check

I wrote the output for the 6 clean missing commits plus #13 into a throwaway worktree on `main`.
- Each clean result changed exactly as many lines as the upstream commit.
- No `zeron` token leaked through.
- `git diff --check` only flagged #13's one conflict. Upstream's context there includes a #677 panels block we never took, and the fix is to keep one line (`session_info_snap = …`).

The worktree was removed afterwards. The other worktrees were not touched.

### Caveats

- Nothing was built. "Clean" means the text merged, not that it compiles. A clean commit can still depend on an upstream commit we skipped.
- The sample leans hard. Missing commits are partly missing *because* they are hard, and they land on today's more diverged `main`.
- The `diff3` regions overstate conflict size when Roboco rewrote the surrounding block. Count regions, not lines.

### Second experiment: "is it already in Roboco?" (`presence-proto.py`)

The check translates each upstream commit's added lines and counts how many already exist in the mapped Roboco file on `main`. Scored against the audit's own labels:

| Audit class | n | Median score | Score ≥ 0.6 ("probably ported") | Score < 0.3 ("probably missing") |
|---|---|---|---|---|
| PORTED | 325 | 0.93 | 279 | 23 (rewritten ports) |
| MISSING | 38 | 0.08 | **0** | 36 |
| PARTIAL | 22 | 0.52 | 6 | 7 |
| SKIP / SUPERSEDED / DECLINED | 103 | ≤0.08 | 1 | 100 |

It never mistakes a missing commit for a ported one. PARTIAL commits are the weak spot: a high score cannot prove that no slice was lost. That is why the ledger, not the score, is the source of truth.

### Third experiment: path-based auto-triage against the same audit

Rules:
- **Auto-skip:** all files under landing, www-redirect, edge, upstream `apps/android`, zatex, or Apple CI workflows, or a "Bump version" subject.
- **Android-parity lane:** iOS-only commits.
- **Review:** everything else.

| Lane | Commits | What the audit said |
|---|---|---|
| Auto-skip | 80 | 80 SKIP (100% correct) |
| Android-parity lane | 18 | 8 ported to Android, 3 missing, 1 partial, 6 skip/superseded/declined |
| Review | 464 | everything else |

iOS commits **must not** be auto-skipped. 12 of the first draft's 107 auto-skips were iOS commits that matter for Android under ADR 0009. Routing them to their own lane fixes that.

## (d) Recommendation: a continuous, ledger-driven sync with a translated cherry-pick first

Replace audited waves with a small weekly loop. Every upstream commit is decided once and recorded. Every port starts from a translated merge instead of a blank page. ADR 0003 is unchanged: still cherry-pick only, never merge.

### The weekly loop, once adopted

1. Refresh the mirror, as today.
2. A script lists the new upstream commits, about 95 a week, and fills the ledger:
   - auto-skip by path rules;
   - send iOS-only commits to the Android lane;
   - run the presence check;
   - run the translated cherry-pick to get CLEAN, TRIVIAL or REAL.
3. One short triage page per week. Only the commits needing a decision appear, grouped by upstream PR. You mark take / skip / later.
4. One batch branch per week:
   - CLEAN and TRIVIAL takes go in as one commit each, with an `Upstream-Commit:` trailer. No ticket file.
   - REAL takes get an agent port seeded with the conflict-marked merge, and a short ticket only when the port needs a design decision.
5. One PR and one CI run per batch. The ledger rows flip to `ported <sha>`.

### Phases

| Phase | When | Work | Done when |
|---|---|---|---|
| 0. Seed | 1 day | Turn `audit-2026-10-28/part-*.md` into `ledger.tsv` (568 rows exist). Add the trailer rule to `docs/reference/upstream-ports.md`. | Every upstream commit up to v0.2.127 has a status |
| 1. Use it on wave 10 | during wave 10 | Run `translate-proto.py` as the first step of each wave-10 ticket that cites a merged upstream SHA. Fold CLEAN and TRIVIAL ones into a single batch, with no per-ticket ceremony. Time a few tickets before and after. | Measured time per ticket, old way vs new |
| 2. Weekly loop | after wave 10 | Harden the scripts into a triage-report generator. Cover open PRs too (`git fetch upstream pull/N/head`). Switch to weekly batches. | Two weekly batches shipped with no full audit |
| 3. Optional upgrades | later, if wanted | A persisted renamed mirror (filter-repo, regenerated deterministically) so plain `cherry-pick`, rerere and mergiraf work. Trial mergiraf on `Cargo.toml` and Rust conflicts. Move Roboco-only code out of the five hot files. Send Windows fixes upstream first. | Conflict rate in the hot files drops |

### Expected effect

These are estimates, not measurements.
- **Audit and triage:** down about 70–80%. No more full re-audits; only about 95 new commits a week, most of them pre-sorted.
- **Porting:** down about 20–30%. 40% of sampled commits land clean or near-clean, and the rest start from a merge holding 70% of the files already done.
- **Calendar:** waiting time drops from weeks (wave 9 was planned and never ran) to days.
- The hard ports stay hard. Nothing here makes `shell.rs` and `spaces.rs` merge themselves. Phase 3's hotspot work is the only lever on that.

## (e) Decisions you would need to make

1. **Waves or weekly batches?** Recommended: weekly batches once wave 10 is done. Alternatively, one batch per upstream release.
2. **The ledger.** Where should it live, and is the wave-10 audit its seed? Suggested: `.scratch/upstream-ledger.tsv`, or `docs/reference/` if you want it to outlast `.scratch`.
3. **Less ceremony for small ports.** Today the rule is one ticket per change and one commit per ticket. The proposal: CLEAN and TRIVIAL ports skip the ticket file; the commit trailer and ledger row are the record.
4. **The auto-skip list.** Confirm: landing, www-redirect, edge, upstream `apps/android`, zatex, version bumps, Apple CI. iOS goes to the Android lane, not skip.
5. **Where the tool lives.** It can be checked into the repo (e.g. `scripts/upstream/`) or kept in `.scratch`. Should CI run the weekly triage report?
6. **Shrinking the rename surface (option 8).** Recommended: no. Keep the current naming. The gain is about 3 commits in 30.
7. **Upstream-first for portable Windows and Linux fixes.** Each one zeron accepts is one fewer future conflict. PR #313 is the precedent.
8. **Later:** a persisted renamed mirror branch next to `zeron/main` (option 4), and a mergiraf trial.
