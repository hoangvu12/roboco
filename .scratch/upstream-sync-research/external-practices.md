# How heavily diverged downstreams stay in sync: external practices and tools

Research date: 2026-10-28. Verification markers: **[V]** means checked against the cited page in this session. **[K]** means it comes from prior knowledge and was not re-checked this session, so treat it as likely but unconfirmed.

Framing that matters for everything below: most famous downstreams (Brave, Electron, Vivaldi, VSCodium, LibreWolf, GrapheneOS) are **soft forks**. They keep a *small* delta on top of upstream and take *all* of upstream on every release. Roboco is the inverse: a *large* delta (rename, deleted subsystems, Windows, Android) that takes *selected* upstream changes. Structurally that is closer to Neovim taking patches from Vim, distro stable kernels backporting mainline fixes, and YugabyteDB/Neon on Postgres. Much of the patch-queue tooling therefore transfers only partly. The academic "patch porting / backporting" literature transfers directly.

## 1. Brave (brave-core)
- **What:** A Chromium-based browser that keeps all of its own code in `src/brave`. Chromium itself is never forked as a git branch.
- **Mechanism [V]:** The preference order is (1) code only in brave-core, (2) `chromium_src` overrides or subclassing, (3) direct patches. Files in `brave/chromium_src/<same path>` shadow upstream includes and `.cc` files during compilation. `#define` tricks rename upstream functions (`DoSomething` -> `DoSomething_ChromiumImpl`) so Brave can wrap them, inject `virtual`, or add `friend` hooks. The remaining edits live as `.patch` files in `brave/patches`, regenerated with `pnpm run update_patches`. The stated rule: "the only patches required [should be] trivial changes, and not nested logic changes." Avoid copying whole upstream files, because copies go stale at rebase time. https://github.com/brave/brave-core/blob/master/docs/patching_and_chromium_src.md
- **Rebase [V]:** Each Chromium bump follows a checklist. Bump the tag, `pnpm run sync`, fix failing patches (rename, re-context, or drop with a link to the upstream change), run `check_chromium_src.py` to find broken overrides, build, run tests, run a network audit, then QA. https://github.com/brave/brave-browser/wiki/Chromium-rebases
- **Applies to us:** The *seams* idea applies: Roboco-only code goes in its own crates/modules, and upstream-shaped code keeps upstream shape. Rust has no include-shadowing equivalent. The nearest analogues are cfg/feature gates, trait extension points, and keeping Windows and Android code in separate files.
- **Cost / risk:** Restructuring is high-cost and long-term. Low risk.

## 2. ungoogled-chromium; Vanadium / GrapheneOS
- **ungoogled-chromium [V]:** Patches in GNU quilt format, ordered by `patches/series`, must apply *without fuzz*. Updates run `quilt push -a --refresh`, fix failures with `quilt edit`, then `validate_patches.py`. Patches are split into `core` (must keep up with upstream) and `extra` (may be dropped). The key point for us is **domain substitution**: a regex list (`domain_regex.list`) applied to a file list *at build time* rewrites every Google domain. It is a mechanical, reversible-by-regeneration transform kept *out of* the patches, and patches must be refreshed *before* substitution runs. https://github.com/ungoogled-software/ungoogled-chromium/blob/master/docs/design.md , https://github.com/ungoogled-software/ungoogled-chromium/blob/master/docs/developing.md
- **GrapheneOS [V, secondhand]:** Changes are kept as a clean patch set on the latest AOSP tag with "zero merge commits". Each major release is a fresh port ("no merging process but rather porting and submitting the changes to the new source tree"). Release notes say "rebased onto UP1A.231005.007". The Android 14 port took roughly July to October 2023. https://discuss.grapheneos.org/d/7875-grapheneos-android-14-experimental-release , https://nobsbitcoin.com/grapheneos-v2023100800
- **Applies:** Treating the rename as a *generated transform* rather than hand edits (see items 11 and 14) is the most transferable idea here.

## 3. VSCodium
- **What [V]:** No source fork. `get_repo.sh` fetches the VS Code tag, and `prepare_vscode.sh` applies `patches/*.patch`, then `patches/<os>/`, `insider/`, and `user/`. It then rewrites `product.json` with `jq`: `nameShort`, `nameLong`, `applicationName`, `dataFolderName`, `urlProtocol`, `darwinBundleIdentifier`, the win32 AppIds and mutex names, the Open VSX gallery URL, and so on. Broken patches are fixed with `dev/update_patches.sh` and `dev/patch.sh`, which stop at `*.rej` for a manual fix and then re-save. https://github.com/VSCodium/vscodium/blob/master/prepare_vscode.sh , https://github.com/VSCodium/vscodium/blob/master/docs/howto-build.md
- **Applies:** Only partly. Upstream VS Code centralised its branding in one JSON file, which Zeron has not done for crate names, env vars, or bundle IDs. We could still centralise *our* runtime branding (app name, env prefix, deep-link scheme, bundle ids) in one module or const table, so upstream code that references them needs fewer edits. Crate and package names stay a source-level rename.
- **Cost:** Low to medium. **Risk:** Low.

## 4. LibreWolf / Floorp / Waterfox
- **LibreWolf [V, partial]:** The `source` repo holds `patches/` plus `assets/patches.txt` (the active list), branding under `themes/browser/branding/librewolf`, and a Makefile that fetches the Firefox tarball and applies patches. https://codeberg.org/librewolf/source (README mirrored at https://ark.sudovanilla.org/Korbs/LibreWolf/raw/branch/gitea_actions/README.md)
- **Floorp [V, secondhand]:** Floorp 10.5 moved its code from "overwriting and adding files to the Firefox code" into a separate folder in the tree. Floorp 12 then *discarded the Floorp 11 codebase and rebuilt it* (via the Noraneko project), separating upstream from Floorp features, after ESR 128 reached end of life. https://newreleases.io/project/github/Floorp-Projects/Floorp/release/v10.6.1 , https://github.com/nyanrus/noraneko
- **Waterfox:** Not researched in depth this session.
- **Applies:** Floorp is a cautionary data point. Interleaved edits to upstream files eventually forced a rewrite. Separation pays off.

## 5. Microsoft Edge and Electron
- **Edge [V]:** The "OSS Principles for Microsoft Edge" say: "our default position will be to contribute", contributions must be "consistent with the architectural design", and Microsoft will maintain what it upstreams. https://github.com/MicrosoftEdge/MSEdge/blob/master/README.md
- **Electron [V]:** `patches/<project>/` holds patch files ordered by a `.patches` file. Electron uses a list rather than numbered names to cut merge conflicts. `config.json` maps patch dirs to repos. `git-import-patches` (with `-3`) turns patches into commits and `git-export-patches` turns commits back into files. Every patch message *must* state why it exists, in one of three categories: (1) temporary, with an upstream link or removal procedure; (2) Electron-specific build need, explaining why subclassing won't work; (3) functionally incompatible with upstream. https://www.electronjs.org/docs/latest/development/patches . The `e patches` wrapper is in electron/build-tools [K].
- **Applies:** (a) Upstream-first: we already PR Windows support to zeron (#313). Every Roboco change that upstream accepts is one fewer divergence. (b) Electron's *mandatory justification categories* map onto a per-divergence ledger (see synthesis).

## 6. Android ROMs: LineageOS, GrapheneOS
- **LineageOS [V, partial]:** Gerrit plus `repo` manifests. Only repos that LineageOS modifies are forked; the manifest points everything else at AOSP [K]. Each Android version gets new `lineage-XX.Y` branches and "rebasing all of its changes" forward. https://www.osnews.com/story/141456/lineageos-22-1-based-on-android-15-qpr1-released/ , https://en.wikipedia.org/wiki/LineageOS
- **Applies:** The manifest idea of *not forking what you don't change* has a Cargo analogue. Any upstream crate that Roboco has not modified, apart from the name, could in principle be consumed less invasively. In practice the rename touches every crate, so this applies weakly.

## 7. Linux distro kernels and Debian packaging
- **Debian 3.0 (quilt) [V]:** `debian/patches/series` sets the order. DEP-3 headers (`Forwarded:`, `Applied-Upstream:`, `Origin:`) record each patch's upstream status. https://documentation.ubuntu.com/project/how-ubuntu-is-made/concepts/patches/ , https://dep-team.pages.debian.net/deps/dep3/ [K for the DEP-3 URL]
- **Ubuntu kernel [V]:** Patches are either cherry-picks or backports of upstream commits, or `UBUNTU: SAUCE:` patches (not upstream yet, or never). The subject prefix is the classification, which makes rebases scriptable. https://documentation.ubuntu.com/kteam-docs/public/reference/kernels/uknext/ubuntu_code_patches.html
- **SUSE / Fedora [K]:** SUSE `kernel-source` keeps `series.conf` plus `patches.*/` with mandatory `Patch-mainline:` and `References:` tags (https://github.com/SUSE/kernel-source). Fedora's `kernel-ark` rebases an `os-build` branch on each upstream release (https://gitlab.com/cki-project/kernel-ark).
- **stgit / quilt / `git rebase --onto`:** These are the standard patch-stack tools. They assume the stack is small relative to the base, which is not true for Roboco.
- **Applies:** The *metadata convention* (an origin/upstream-status tag on every carried change) is cheap and directly useful. The stack mechanics are not.

## 8. Molly (Signal-Android fork)
- **[V, inferred]:** Updates every two weeks, with security fixes immediately (https://github.com/mollyim/mollyim-android). Commit titles such as "Merge tag 'v7.44.2' into molly-7.44" suggest per-version branches that *merge* upstream tags. That is inferred from mirrored history, not from documentation (https://zff.dev/egecelikci/mollyim-android).
- **Applies:** Molly is a soft fork with no rename, which is why plain merging works for it. That is not our case.

## 9. GitLab CE/EE; Discourse
- **GitLab [V]:** CE and EE were separate repos. They went from manual merges per release, to daily merges by "seven (brave) developers" in 2016, to automated merges "every three hours" in 2017–18, to "thousands of commits in some cases" by end of 2018, at which point automation failed. "Days of engineering time" went to busy work, and a CE spec change broke EE master for hours. The fix was a single codebase with proprietary code under `/ee`, where removing `/ee` still leaves a working app. https://about.gitlab.com/blog/merging-ce-and-ee-codebases/ , https://about.gitlab.com/blog/a-single-codebase-for-gitlab-community-and-enterprise-edition/
- **Discourse [V, partial]:** Customisation goes through plugin APIs (`add_to_serializer`, `register_modifier`, plugin outlets), not core patches. Where a hook is missing, the advice is a *core PR adding a modifier point*. https://meta.discourse.org/t/overriding-include-methods-in-serializers/268138
- **Applies:** GitLab's history is the best-documented cost curve for two diverging repos: sync cost grows with commit volume until it breaks. Their fix (one codebase) is unavailable to us. The Discourse lesson is that you upstream *extension points*, not features.

## 10. Database forks
- **Neon [V]:** Uses `vendor/postgres-v14..v17` submodules pointing at `REL_N_STABLE_neon` branches in neondatabase/postgres. `docs/core_changes.md` lists each core patch, grouped by purpose, with a "**How to get rid of the patch**" section. The stated goal is to eliminate all of them via upstream submissions and extensions (`pgxn/neon`). https://github.com/neondatabase/neon/blob/main/docs/core_changes.md . The rebase procedure itself is not documented publicly.
- **YugabyteDB [V]:** Stayed on PG11 for about five years. The PG15 merge needed a dedicated team, and YB changes "interleaved with Postgres changes" had to be "carefully examined, sometimes rewritten". Meanwhile the PG11 mainline kept moving and had to be forward-merged continuously ("we've had to build everything"). The target is now new PG versions within about six months. https://www.yugabyte.com/blog/yugabytedb-moves-beyond-postgresql-11/ , https://www.yugabyte.com/blog/how-yugabytedb-keeps-pace-with-postgresql-innovation/
- **Citus [V]:** "Unforked" in Citus 5.0 (2016) by becoming an extension built on Postgres planner, executor, and utility hooks. Supporting each new PG major is still "a significant amount of effort", but now bounded. https://www.citusdata.com/blog/2016/03/24/citus-unforks-goes-open-source/ , https://www.citusdata.com/blog/2017/10/25/what-it-means-to-be-a-postgresql-extension/
- **Lesson:** Deferring sync makes the eventual catch-up a project (Yugabyte). A written inventory of divergences, each with an exit plan, keeps the delta shrinking (Neon).

## 11. Copybara (google/copybara)
- **What [V]:** Google's tool for moving code between repos with transformations. It is stateless and records the origin revision as a label in destination commit messages. Transforms include `core.move` (paths) and `core.replace`, with parameters `before, after, regex_groups, paths, first_only, multiline, repeated_groups, ignore`. `core.replace` is automatically reversible. Workflow modes include `SQUASH`, `ITERATIVE` (one destination commit per origin commit), and `CHANGE_REQUEST`. There is a `merge_import` mode with `core.merge_import_config` and a workflow `consistency_file`, intended for preserving destination-only changes (I did not read that parameter's full text). https://github.com/google/copybara , https://raw.githubusercontent.com/google/copybara/master/docs/reference.md
- **Real users [V]:** Google internally. AOSP `external/scudo` imports from llvm-project with a `copy.bara.sky` (https://android.googlesource.com/platform/external/scudo/+/6e5ed2b1ed4afbb7af9d3a76f773385a808488ba/copybara/README). There are forks under replit and 10gen (MongoDB). I could not confirm usage by Envoy, Kubernetes, TensorFlow, or Bazel.
- **Fit for us:** Technically yes, one way. `git.origin(zeron main)` -> `git.destination(zeron-renamed branch)`, `ITERATIVE`, with `core.move("apps/zeron","apps/roboco")`, `core.replace` for `zeron_`/`zeron-`/`ZERON_`/`sh.zeron.`/`zeron://`/`Zeron` type names, and excludes for iOS, edge, and WorkOS paths. That produces a *renamed mirror*, one commit per upstream commit, that we can cherry-pick from.
- **Cost:** Java 21 plus Bazel, or weekly snapshot jars released "without any manual testing … or correctness guarantees". Docker support is "experimental". Windows is not documented. Thin community (mailing list). **Risk:** Medium tooling risk. Running it on Linux CI avoids the Windows question.

## 12. Josh (josh-project)
- **[V]:** A proxy and CLI that serves *filtered projections* of a repo (subdirectory, workspace) as standalone repos, with "fast, reversible" history transformation. It does not do content rewriting or identifier renames. Some features are "not yet fully mature." https://github.com/josh-project/josh
- **Relevance:** Low. It solves monorepo/subrepo splitting, not renaming.

## 13. git-imerge; rerere at scale
- **git-imerge [V]:** Breaks a merge or rebase into a grid of pairwise commit merges, so each conflict is minimal. State is saved in `refs/imerge/NAME`. Goals are merge, rebase, rebase-with-history, or full. Latest release is v1.2.0 (2021 per my knowledge [K]). It is Python and effectively dormant. https://github.com/mhagger/git-imerge
- **rerere [K]:** Records each conflict-hunk-to-resolution pair and replays it when the *identical* conflict text recurs. It helps with repeated rebases and repeated rename conflicts. It cannot help with a first-time conflict on new upstream code.
- **Applies:** Low for us. Merging is ruled out, and imerge's value is in merges or rebases. Keep rerere on as we do now. A renamed mirror removes most of the repeated conflicts rerere exists to absorb.

## 14. git-filter-repo `--path-rename` / `--replace-text`
- **[V]:** `--path-rename old:new` renames paths, and `--replace-text FILE` takes literal, `regex:`, or `glob:` lines with `==>` replacements. `--replace-message` does the same for commit messages. Re-runs are supported as "continuations" via `$GIT_DIR/filter-repo/already_ran` and chained commit-maps. The manual does **not** promise stable rewritten commit IDs across later runs, and `--refs`/`--partial` are flagged "use with caution". https://github.com/newren/git-filter-repo/blob/main/Documentation/git-filter-repo.txt
- **Fit:** It is the cheapest way to build a renamed mirror *once* (for example, all 677 upstream commits since the split). Incremental updates are awkward. The robust pattern is to regenerate the whole renamed mirror from scratch each time, which is deterministic if the expression file is fixed. Commit IDs then stay identical between runs as long as inputs are identical, since filter-repo is deterministic [K, reasoned rather than documented]. A ~50-line script also works (`git format-patch` -> apply the rename map to paths and content -> `git am -3`) as a "poor man's Copybara".
- **Cost:** Low (pip install, works on Windows). **Risk:** Over-eager replacement (for example `zeronsh` org links, `ZERON_GPU_STATS`, `docs/research`). These need explicit exclusions mirroring our rebrand boundaries.

## 15. Custom merge drivers / .gitattributes
- **[K]:** `.gitattributes` `path merge=<driver>` plus `git config merge.<driver>.driver "cmd %O %A %B %P"`. Cherry-picks and reverts use the same merge machinery, so drivers apply. Useful drivers: `Cargo.lock` regenerate (accept ours, then `cargo update -w`), `merge=ours`-style handling for Roboco branding files. Note that built-in `merge=ours` only takes effect when both sides changed the file. https://git-scm.com/docs/gitattributes#_defining_a_custom_merge_driver
- **Cost / risk:** Low cost. Medium risk of silently dropping upstream intent, so limit drivers to generated files.

## 16. mergiraf and structured merge
- **mergiraf [V]:** A tree-sitter-based git merge driver, registered via gitattributes, covering merge, rebase, cherry-pick, and revert. It supports **Rust, Kotlin, TOML**, and about 40 other formats. It is conservative: it keeps conflict markers when unsure, and `mergiraf review` audits automatic resolutions. It is active (Codeberg; v0.17.0 on Snap, May 2026), still pre-1.0. https://mergiraf.org/ , https://mergiraf.org/languages.html . A 2025 evaluation (LastMerge, Duarte et al.) reportedly describes it as a generic re-implementation of Spork with fewer false negatives. Not verified against the primary paper.
- **Spork / jDime / IntelliMerge [K]:** Java-only research tools (Spork and jDime are AST merge; IntelliMerge is refactoring-aware). None of them handle Rust.
- **Applies:** Good and cheap for the textual-adjacency conflicts (imports, `use` lists, match arms, struct fields) that dominate cherry-picks. It does not understand renames, so pair it with a renamed mirror.

## 17. Rust semantic tools: rust-analyzer SSR / rename, ast-grep, comby
- **rust-analyzer SSR [V]:** `foo($a, $b) ==>> ($a).foo($b)`, with path-aware matching. It has a CLI implementation (`cli/ssr.rs`; `rust-analyzer ssr`; exact flags unverified). https://rust-lang.github.io/rust-analyzer/ide_ssr/index.html
- **ast-grep [V]:** YAML rules with a `fix:` key, `sg run --rewrite`, and `-U` to apply. Supports Rust and Kotlin. https://ast-grep.github.io/guide/rewrite-code.html
- **comby [K]:** A lightweight structural search/replace that works across languages (https://comby.dev). Not re-verified.
- **Applies:** Our renames are *lexically uniform* (crate, path, env, and type-name prefixes), so regex or literal maps (items 11 and 14) cover about 95% of them. Semantic tools earn their place for *API-shape* adaptations, where an upstream commit calls something Roboco has refactored. ast-grep is the most practical of these (single binary, Windows OK). Keep a small rule library per known divergence.

## 18. LLM-assisted patch porting / backporting
- **FixMorph (ISSTA 2021) [V]:** A transformation-rule-based Linux backporter. 75.1% correct on 350 mainline patches. https://www.comp.nus.edu.sg/~abhik/pdf/ISSTA21.pdf
- **TSBPORT [V]:** PDG-based semantic matching. 87.44% (1,587/1,815) of kernel security patches. https://sites.google.com/view/tsbport
- **PPatHF (ISSTA 2024) [V]:** LLM porting between *hard forks* (Vim -> Neovim), the closest analogue to us. 131/310 (42.3%) fully correct, with about 57% of manual edits automated. Pipeline: reduce the target function to patch-relevant code, then have the LLM apply the patch. https://arxiv.org/abs/2404.17964
- **PortGPT (arXiv 2510.22396) [V]:** GPT-4o agent with code-navigation tools. 89.15% on existing kernel benchmarks, 62.33% on its own 146 harder cases. 9/18 real Linux 6.1 backports, and 9 patches were merged upstream. https://arxiv.org/abs/2510.22396 . An independent 2026 benchmark (arXiv 2608.17671; abstract only, not verified) reports best success falling from 85.2% on simple to 24.0% on structurally complex patches.
- **Google [V]:** "How is Google using AI for internal code migrations?" (arXiv 2501.06972) is an experience report: about 80% of migration edits were AI-authored, with deterministic AST tooling to locate and validate edits. "Migrating Code At Scale With LLMs At Google" (arXiv 2504.09691; FSE 2025 industry) covers 39 migrations and 595 CLs: 74.45% of changes LLM-generated and about 50% estimated total time reduction. https://arxiv.org/abs/2501.06972 , https://arxiv.org/abs/2504.09691
- **Applies:** This is the strongest evidence-backed lever for hand-porting by intent. Published success is high for simple or local patches and drops sharply for structural ones. All successful systems combine a deterministic localiser and validator (build plus tests) with the LLM, and do not trust raw LLM output.

## 19. Other relevant practice and studies
- **Vivaldi [V]:** Switched from merging to **rebasing** a work branch after about two years, because "merging got rather messy". About 10% of patched files conflict per update. The rebase plus build fixes take one to two-plus weeks (Chromium 104 took "just over two weeks"), and testing takes weeks more. Vivaldi tracks 8-week Extended Stable because the 4-week cadence "would require at least two full teams". Advice: put independent code in a separate module with Chromium as a submodule, and don't edit upstream string files. https://vivaldi.com/blog/lets-go-under-the-browser-hood-with-vivaldis-yngve/
- **Igalia (Dapena) [V]:** Rebase gives smaller, simpler conflicts than merge. Frequent updates mean smaller change sets but repeated fixes for in-flight upstream refactors. Keep the downstream small, upstream generic work, and invest in automation and test coverage. https://blogs.igalia.com/dape/2024/09/13/maintaining-chromium-downstream-update-strategies/
- **Studies [V]:**
  - Zhou, Vasilescu & Kästner (ICSE 2020) studied 15,306 hard forks plus 18 interviews and found hard forks are increasingly seen as non-competitive alternatives that grow out of social forks. https://www.cs.cmu.edu/~shuruiz/paper/icse20-hardfork.pdf
  - Businge et al. (EMSE 2022) studied 38 Android, 526 .NET, and 8,837 JS fork families and found "little code integration" across families. https://research.chalmers.se/en/publication/529213
  - **PaReco** (Ramkisoen, Businge et al., ESEC/FSE 2022) classifies upstream patches as *missed*, *duplicated effort*, or *split*. On 364 variant pairs and 8,323 patches it reported 91% precision and 80% recall, and missed patches typically trailed by about 52 weeks. https://github.com/unlv-evol/PaReco , https://2022.esec-fse.org/details/fse-2022-research-papers/34/PaReco-Patched-Clones-and-Missed-Patches-among-the-Divergent-Variants-of-a-Software- . The follow-up MOVis visualises the output (arXiv 2604.01494).

## Synthesis: what maps best to Roboco

1. **A generated, renamed upstream mirror (ungoogled-chromium "domain substitution" plus Copybara or git-filter-repo).** Keep `zeron/main` pristine as now, and derive `zeron-renamed/main` by a *deterministic, regenerated-from-scratch* transform. The transform applies our existing rename map (paths, crate/lib names, `ZERON_`, bundle ids, `zeron://`, `Zeron*` types, `-PzeronSkipCore`) and explicit exclusions (`zeronsh`, `ZERON_GPU_STATS`, `docs/research/`). It can optionally drop iOS, edge, and WorkOS paths. Cherry-picks from this mirror then conflict only on *real* divergence, and rerere becomes nearly redundant. Start with filter-repo or a format-patch/sed/`am -3` script (cheap, Windows-friendly). Move to Copybara `ITERATIVE` only if we want commit-for-commit labels (`GitOrigin-RevId`-style provenance) and can live with Java 21 on Linux CI. This is the one change that attacks the bulk of the current re-typing cost.

2. **A divergence and disposition ledger (Electron justification categories, DEP-3 `Forwarded:`, Ubuntu `SAUCE:`, Neon "how to get rid of the patch", PaReco's missed/duplicated/split classes).** Record each upstream commit as `ported <roboco sha> | skipped: <reason: cloud/iOS/edge/superseded> | pending`, and add a trailer such as `Upstream-Commit: <sha>` on Roboco port commits. That makes "what haven't we taken?" a query instead of an audit wave, and it is the input an LLM porter needs. Cost is low, and it partially formalises the `.scratch/upstream-drift` audits we already run.

3. **Smaller, more frequent ports with an LLM-plus-verifier loop (Google migrations, PortGPT, PPatHF), with mergiraf as the merge driver.** The evidence is consistent. Big waves resemble Yugabyte's five-year gap or GitLab's "thousands of commits" breakdown. Local patches port automatically at high rates (75–89% on kernel benchmarks), while hard-fork and structurally complex ports drop to roughly 24–42%. A per-commit loop fits our setup: cherry-pick from the renamed mirror with mergiraf, have an agent resolve remaining conflicts by intent, then gate on `cargo build`/tests plus the Android build. Humans review the structurally complex fraction. mergiraf supports Rust, Kotlin, and TOML and is conservative by design.

4. **Shrink the touch surface over time (Brave seams, Citus/Discourse extension points, Edge upstream-first, Floorp/Vivaldi module separation).** Keep Windows, Android, and engine-local pairing code in Roboco-owned modules or crates. Centralise runtime branding constants. Upstream portable fixes and extension points to zeron, as with PR #313. The payoff is slow, but every accepted upstream change and every isolated module permanently reduces future port conflicts.

Not recommended as primary levers: patch-queue stacks (quilt, stgit, Electron-style patches/ dirs). They assume a small delta on a fully taken upstream, which is the opposite of our shape. Josh solves a different problem. git-imerge needs merges or rebases we have ruled out. Semantic rename tools (rust-analyzer SSR, ast-grep) are better kept as a small rule library for known API divergences than used for the uniform rename.
