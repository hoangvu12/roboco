# 04 — Desktop client-side preview proxy on 7332 + remote browser open

**What to build:** The desktop client's half of the session relay. A GPUI-free client-proxy module (in or beside `crates/engine-client`, so ticket 05 can share it): binds `127.0.0.1:7332` (unclaimed — engine owns 7331, browser-helper 7333) only while a remote preview is viewed (lazy start, idle shutdown, inline error if the port is busy — mirror the 7331 failure mode, `crates/preview/src/service.rs:196-201`); routes by Host header against the remote engine's preview hostnames, sourced from the `WatchPreviews` snapshot the browser pane already receives (`crates/ui/src/browser/mod.rs:261-320`) — drive the dormant `catalog.set_remote` ingestion (`crates/preview/src/catalog.rs:187/236`) with it; and dials the remote engine's `/preview-relay` (ticket 03) over the transport the client already holds: the engine registry's dial (`connect_ws_authenticated`, `crates/rpc/src/client.rs:472-475`) for LAN engines, the Tailcat tunnel's loopback baseUrl for tunneled engines. Each accepted HTTP connection opens a mux stream (`Mux::start(transport, connector, initiator: true)` — the client never serves OPENs) and relays HTTP with the same header hygiene the engine proxy applies (hop-by-hop stripping, Host/Origin preserved, localhost redirect rewrites — factor from `crates/preview/src/proxy.rs` rather than duplicating). Then rewire the desktop: for non-local engines, `service.url()` renders against 7332 (`crates/ui/src/browser/view.rs:128`, macOS `register_preview` `mod.rs:286-289`) and the "Open this engine preview through a tunnel URL" degradation (`mod.rs:279-281`) becomes a real open; macOS extends the per-domain WebKit CONNECT registration to 7332. Linux: add a WebKitGTK proxy configuration for preview hostnames pointing at the client proxy (the macOS pattern's sibling — verify the WebKit API in-ticket; `webkit_network_proxy_settings_*`) with external-browser fallback, since stock resolvers do not synthesize `*.localhost` and the WebKitGTK helper has no `.localhost` handling today (`crates/ui/src/browser/linux/`).

**Why now:** the visible payoff — a chat on another engine gets first-class previews in the browser pane.

**Blocked by:** 03 — engine preview relay route.

**Status:** implemented
**Parent:** `.scratch/agent-previews/spec.md`

**Verification budget:** `cargo test -p roboco-engine-client` (client proxy tests: hostname routing from a snapshot, mux round-trip against a test relay, bind-conflict error), `cargo test -p roboco-ui` (browser pane tests with a fake remote engine), the `preview-fixture` example extended to a two-engine variant if cheap.

- [x] A remote chat's preview opens from the browser pane and renders the remote dev server, HMR/WebSocket intact *(data path fully verified against a real remote engine — see evidence; a live rendered page in WebKit needs a desktop runtime)*
- [x] Hostnames route only to services present in the live remote snapshot; stale hostnames 502 with the existing "not running" shape
- [x] 7332 binds only while a remote preview is viewed; a busy port surfaces an inline error, never a URL change
- [x] Revoking the remote engine's session kills the open preview stream and the pane degrades to the reconnect state
- [x] macOS CONNECT registration covers 7332; Linux loads previews via the WebKit proxy configuration (or documented external fallback) *(both code-verified only — no macOS/Linux-desktop runner here; see residuals)*
- [x] No engine-side changes (ticket 03 owns those); no changes to 7331 behavior *(zero-line `crates/engine` diff; the 7331 regression suite is green)*

## Implementation record (2026-10-27)

**Module placement — a new crate, `crates/preview-relay` (`roboco-preview-relay`), *beside* `crates/engine-client`** (the ticket's "in or beside" — beside). It holds the mux frame protocol, the HTTP relay hygiene, and the client proxy, and is the one GPUI-free, engine-free, WebRTC-free module every client links: the desktop through `roboco-engine-client`, the Android core (ticket 05) through `roboco-engine-client` too (it already links it), the engine side through `roboco-preview`'s re-export. The mux could not stay in `roboco-preview` because that crate carries the dormant WebRTC peer stack and process discovery — a client linking it would drag webrtc into the mobile core; and the client proxy could not live *inside* `roboco-engine-client` for the same reason it needs the mux. `mux.rs` moved **verbatim** (`git mv`; zero content changes) with `pub use roboco_preview_relay::mux;` in preview's lib.rs, so every `roboco_preview::mux` / `crate::mux` path — engine, tests, peers — resolves unchanged: the `crates/engine` diff is **zero lines**.

**What landed where:**

- `crates/preview-relay/src/client.rs` (new, ~1000 lines) — the client proxy: `ClientProxy` (lazy 7332 bind, idle shutdown, busy-port inline error with the 7331 message shape, restart on the same address), the routing table implementing the dormant `set_remote` ingestion semantics (validation, ≤256, unique ids, distinct persistent labels on device-name collision — `preview-relay-labels.json`), one shared relay mux per (engine, chat, service) with singleflight dialing (`Mux::start(transport, Refused, initiator: true)` — the client never answers OPENs), per-connection mux streams with the engine proxy's three entry shapes (origin-form by Host, absolute-form by authority for WebKitGTK's proxy mode, CONNECT self-tunnels), and the shared header hygiene. `dial_relay` + `WebSocketRelayStream` (the client twin of the engine's `WsTransport`, mirroring the frame-per-binary-message shape — the engine's type was not moved because that would touch `crates/engine`).
- `crates/preview-relay/src/http.rs` (new) — the hygiene **factored from** `crates/preview/src/proxy.rs`: `strip_hop_headers`, `rewrite_location`, `connection_has`, `forward_request_headers` (Host/Origin preserved, `X-Forwarded-Host`/`-proto`, proxy-credentials dropped), `forward_response_headers`, `error`, `tunnel_slot`, `AbortOnDrop`, `GuardedBody`. One implementation, two proxies (7331 and 7332).
- `crates/engine-client/src/preview_proxy.rs` (new) — `PreviewProxy`, the registry-backed manager every client needs: dials each engine's relay over the *saved endpoint and credential the supervise loop redials the RPC socket with* (LAN `ws://`, or a Tailcat forwarder's loopback base — both are just the saved endpoint), folds the local engine's hostnames into the Linux bypass list, drops routes for forgotten engines, and publishes `PreviewProxyStatus { port, error, bypass }`. `registry.rs` gained `relay_dial()` + `runtime_handle()` (2 small public accessors).
- `crates/proto/src/preview.rs` — `PREVIEW_CLIENT_PROXY_PORT = 7332` beside 7331 (Rust-only: the web client never binds 7332 — ticket 06's loopback framing is untouched, so wiregen's constants are unchanged and its freshness gate stays green).
- `crates/ui/src/browser/mod.rs` — `watch_previews` gained the manager parameter; a remote snapshot is rewritten exactly as the spec's "Desktop URL rewrite" says: services ingested (the pane renders the *effective* hostnames), `proxy_port` set to 7332, the "Open this engine preview through a tunnel URL" degradation replaced by the real open; a bind error rides `snapshot.error` (rows disable, URL stays 7332 — never a URL change); the watcher lifetime is the pane's (unwatch on task exit → idle shutdown); status changes (bind success/failure) update the pane and push the Linux browser configuration. Local panes leave their snapshot untouched and only feed the bypass list.
- `crates/ui/src/browser/view.rs` — the remote-loopback banner no longer covers preview pages (7331 *or* 7332); `service.url(snapshot.proxy_port)` renders 7332 for remote panes via the snapshot rewrite.
- `crates/ui/src/browser/macos.rs` — the per-domain WebKit CONNECT registration is now per-port (`BTreeMap<u16, BTreeSet<String>>`): one `nw_proxy_config` per preview port, 7331 and 7332 alike, each matching only its own hostnames; `register_preview` accepts both ports.
- `crates/ui/src/browser/linux/helper.c` + `linux/mod.rs` — the WebKitGTK proxy configuration (see verification below): `proxy` command → `webkit_network_proxy_settings_new(NULL, bypass)` + `add_proxy_for_scheme("http"/"ws", "http://127.0.0.1:7332")` → `webkit_website_data_manager_set_network_proxy_settings(manager, WEBKIT_NETWORK_PROXY_MODE_CUSTOM, …)`; port 0 resets to DEFAULT. Re-applied before preview loads (settings apply to sessions created after the call). `BrowserData::set_preview_proxy` sends it without spawning a worker.
- `crates/ui/src/state.rs` / `shell.rs` — `AppState.preview_proxy` + `ensure_preview_proxy()` (labels file beside the session store); `add_browser_surface` hands the manager to every pane (remote panes ingest/watch, local panes feed the bypass list).
- `docs/preview-networking.md` — new "Client-side preview proxy" section (routing, lifecycle, platform browser stories, the Linux scoping honesty, revocation inheritance) + validation entries; `CONTEXT.md` gains the session-relay/client-proxy vocabulary.

**WebKitGTK API verification (the in-ticket item):** verified against the *installed* webkit2gtk-4.1 headers (2.52.6, `/usr/include/webkitgtk-4.1/webkit/WebKitNetworkProxySettings.h` + `WebKitWebsiteDataManager.h`) and the upstream reference: `webkit_network_proxy_settings_new(default_proxy_uri, ignore_hosts)`, `webkit_network_proxy_settings_add_proxy_for_scheme`, `webkit_website_data_manager_set_network_proxy_settings(manager, WEBKIT_NETWORK_PROXY_MODE_CUSTOM, settings)` all exist and are current (the context-level variant is deprecated, the data-manager one is not). The **presumed per-hostname scoping does not exist**: `ignore_hosts` is a bypass list (GSimpleProxyResolver semantics — hostname/`*.domain`/IP/CIDR entries), and there is no per-host proxy mapping, so the macOS match-domain idiom has no Linux sibling. The landed scope is therefore per-scheme (http/ws proxied; https/wss direct) with an explicit bypass list (the local engine's live preview hostnames — fetched from the local panes' snapshots — plus `localhost`/`127.0.0.1`/`::1`), applied only while the proxy runs. Collateral: plain-http *external* sites in the embedded pane are refused with a dedicated message while remote previews are watched — the pane's "Open in default browser" is the fallback (documented in `docs/preview-networking.md`). `helper.c` compiles against the real headers (`cc -fsyntax-only $(pkg-config --cflags webkit2gtk-4.1 json-glib-1.0)` → exit 0).

**Test evidence for each criterion:**

- *Remote preview opens and renders*: the pane lists the remote engine's service (real `WatchPreviews` over a paired session), renders `http://<device>.<project>.localhost:7332`, and that URL returns the remote dev server's bytes through the relay (ui pane test + engine-client test, both against real engines). HMR/WebSocket passthrough rides the engine proxy's exact machinery (hyper `with_upgrades`, CONNECT tunnels, the same tunnel budget and hygiene — one implementation now); a tunnel round-trip is covered, but a live Vite HMR session in an embedded WebKit view needs the desktop runtime (residual).
- *Snapshot-scoped routing + 502 shape*: removal from the snapshot stops routing; unknown `.localhost` hostnames answer 502 with the engine proxy's exact "This preview is not running. Start the project's dev server and try again." message; non-preview hosts get the external-browser message instead (never a relay attempt).
- *Lazy 7332 + busy port*: the listener binds only after the first watcher (tests assert "port None before, Some after"), idles out after the last watcher leaves, rebinds on the same address; a squatted port yields "Remote previews could not listen on port 7332: …" with `port: None`, and the rendered port stays `PREVIEW_CLIENT_PROXY_PORT` regardless.
- *Revocation*: revoking the session and stopping the remote bind turns the open relay into a 502 (the refused dial fails promptly, never an unauthenticated direct dial — pinned both against the test engine's 401 and the real engine's revoked credential) and the pane degrades to the reconnect state within its retry loop.
- *macOS/Linux*: code + API verification as above; runtime rendering in WebKit is macOS/Linux-desktop-only (residual).
- *No engine-side changes*: `git diff HEAD -- crates/engine` is empty; `roboco-preview`'s mux re-export keeps the engine compiling unchanged, and the 7331 regression suite plus the mux-move relay suite are green.

**Residuals / known gaps:**

1. **macOS runtime verification**: the per-port CONNECT registration is code-verified only — no macOS machine exists here or in CI (per AGENTS.md), and cross-checking `aarch64-apple-darwin` fails earlier in the graph (`ring`'s build script needs the Apple toolchain). The change is a minimal restructuring of the shipped pattern (one `nw_proxy_config` per port instead of one fixed at 7331).
2. **Linux runtime verification**: `helper.c` compiles against the real installed WebKitGTK 2.52.6 headers and the API is verified, but loading a preview through the configured proxy needs a display + WebKitGTK runtime (the fixture/browser-fixture harness); the external-browser fallback is documented and always available. Also: the WebKitGTK proxy scoping is per-scheme, not per-hostname — the API has no per-hostname proxy (the in-ticket verification outcome); plain-http external sites in the embedded pane are refused with the fallback message while remote previews are watched.
3. **Live HMR/Vite through 7332**: the upgrade/tunnel machinery is the engine proxy's shared implementation, but no live Vite HMR session was driven through the client proxy (the preview-fixture needs `VITE_BINARY` + a display).
4. **preview-fixture two-engine variant: skipped as not cheap** (the ticket said "if cheap"). It would need a second real engine + pairing + a second pane inside an example that already requires a display, Vite and screenshot tooling to validate — while the two-engine data path and the pane rewrite are covered by real-engine tests at both layers (`roboco-engine-client` + `roboco-ui`).
5. **Mid-connection session revocation** cuts the next dial, not already-open relay sockets — inherited from the listener's RPC-socket semantics (ticket 03's residual, unchanged here); the pane still degrades because its `WatchPreviews` subscription is cut.
6. `discovery`'s `backgrounded…` test hangs on this host at the base commit too (verified); CI is the authority for that suite.
7. A tunneled engine whose forwarder died before an app restart cannot be dialed (the registry's pre-existing Tailcat restart behavior) — the pane shows the reconnect state, as with any offline engine.

**Deviations from the ticket (each with a reason):**

1. **New crate `roboco-preview-relay` beside `crates/engine-client`** instead of the module living inside it: the client proxy needs the mux and the hygiene, and sharing them via `roboco-preview` would put webrtc + process discovery into the Android core. The mux moved verbatim with a re-export (engine diff: zero lines).
2. **The client's own `WebSocketRelayStream`** instead of reusing the engine's `WsTransport`: moving the engine's type would modify `crates/engine`, which the ticket forbids; the ticket itself says the client transport "mirrors the engine's frame-per-binary-message shape".
3. **Linux proxy scope is per-scheme with a bypass list**, not "for preview hostnames" as the ticket presumed: `webkit_network_proxy_settings_*` has no per-hostname proxy mapping (verified in-ticket — the ticket's own verification item). The bypass list scopes what stays direct (local engine hostnames + loopback), https/wss are never proxied, and the configuration lives only while the proxy runs, with the external-browser fallback documented.
4. **`watch_previews` gained a manager parameter** (shell, fixture and tests updated): the pane needs the app-level manager both to ingest remote snapshots and to feed the Linux bypass list from local ones.
5. **Label persistence** (`preview-relay-labels.json` in the app's data dir): the `set_remote` semantics allocate distinct labels on device-name collisions; persisting them keeps remote preview URLs stable across client restarts (spec story 7).
