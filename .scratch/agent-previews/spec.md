# Agent previews: local parity, Windows discovery, session-relayed remote access

Status: ready-for-human
Spec date: 2026-10-26

## Problem Statement

The engine already detects HTTP dev servers its agents start and serves them at stable `*.localhost:7331` hostnames through a loopback reverse proxy (`crates/preview`, wired in `crates/engine/src/lib.rs:273-283`, rendered by the desktop browser pane). Three gaps keep it from being the product feature upstream zeron ships:

1. **Attribution is the pre-#1023 design.** A listener is attributed by process ancestry + project cwd, so a server *the user* started inside a project still lists (ranked below agent servers), servers survive attribution across `nohup`/double-forks/engine restarts only if ancestry holds, and nothing records *which chat* started a server. Upstream fixed this in PR #1023 (`a9e6c48b7`) with an inherited `ZERON_ORIGIN` env marker and a Ports card beside the chat; roboco has neither.
2. **Windows discovery does not exist.** `discovery.rs` enumerates `/proc` (Linux) and `lsof`/`ps` (macOS); on Windows it returns nothing — while Windows is roboco's flagship platform. Upstream never implemented it, so this is roboco-original work.
3. **Remote devices can see previews but cannot open them.** A chat on another engine streams its preview list fine (`WatchPreviews` rides the client's authenticated engine session), but the data plane is dormant: `browser/mod.rs:279-281` degrades to "Open this engine preview through a tunnel URL", `Peers::signal()` and `catalog.set_remote()` have no production caller (`service.rs:169-173` drops the signaling output), and the web panel is state-layer only with the Android app lacking any preview surface. Upstream closes this gap with a WorkOS-authenticated Cloudflare Worker coordinating WebRTC DataChannels; roboco removed the cloud (ADR 0003/0004) and must close it another way.

Research basis: `docs/research/agent-port-forwarding.md` (upstream architecture, WorkOS role, prior art, roboco code map).

## Solution

Three phases, in order:

**A — Port upstream #1023** (origin stamping + Ports card). The engine stamps `ROBOCO_ORIGIN` (`chat:<id>` / `terminal:<id>`) into the environment of everything it launches; discovery lists a listener only when its process (or nearest marked ancestor) carries an origin owned by a chat this device hosts; each `PreviewService` gains `chatId`. The session card gains a Ports section (rows per server this chat can preview, opening a browser tab). Pure port of `a9e6c48b7` across the rebrand per `docs/reference/upstream-ports.md`, minus the 2-line edge hunk. **Rider (ticket 07):** an MCP tool exposes the calling chat's preview URLs to the agent, so it can tell the user where its dev server is running — the link itself is minted automatically by the engine's catalog on discovery; nobody creates it, the agent just gets to see it.

**B — Windows discovery** (roboco-original). A Windows `listeners()` that enumerates listening TCP sockets with owning pid (IP Helper `GetExtendedTcpTable`) joined to process parent/start-time/cwd/cmd/environ, feeding the same origin-marker attribution as Phase A. Crate choice per the design-research findings (sysinfo / netstat2 or raw `windows-sys` calls).

**C — Remote previews over the client's own session** ("session relay", the roboco-native replacement for upstream's cloud-coordinated DataChannel). The remote engine exposes a session-authenticated `/preview-relay` WebSocket route on its existing listener (the tailcat-relay pattern: opaque byte pump, no RPC protocol change); the mux frames travel over that socket to the engine's `LocalConnector`. Clients run a small client-side proxy binding `127.0.0.1:7332` that routes by the preview hostname (fed from the `WatchPreviews` snapshot they already receive) and dials the relay over the session transport they already hold (LAN direct, or the Tailcat tunnel's loopback baseUrl). The desktop rewrites `service.url(proxy_port)` to 7332 for non-local engines instead of showing the tunnel-URL error; the Android app gains a preview panel (WebView) backed by the same Rust client-proxy in the mobile core; the web app ships the loopback-framing panel and keeps an honest off-machine note. Preview bytes never leave an authenticated session; no WebRTC, no signaling, no cloud in v1.

The dormant WebRTC stack (`peer.rs`/`mux.rs` peer side, `catalog.set_remote` peer ingestion) stays in-tree untouched — it is the upgrade path (Phase D) if relayed previews ever need a direct data plane, specced separately.

## User Stories

1. As an agent user, I want only servers my agents/terminals started to appear as previews, so my own dev servers never masquerade as agent output.
2. As an agent user, I want a Ports card beside the chat listing every server that chat started, so I can open the agent's work without hunting for a browser tab.
3. As a Windows user, I want the same automatic detection macOS/Linux get, so previews are not a two-platform feature.
4. As a user with a second computer, I want a preview of a chat running on my other engine to open from that machine's browser pane as if it were local, so remote chats are first-class.
5. As a phone user, I want to open a preview of a dev server my desktop's agent started, so I can check the agent's work from the couch.
6. As a user, I want remote previews to work over whatever transport already reaches the engine (LAN or my tailnet), so no new network setup exists.
7. As a user, I want preview URLs stable across dev-server restarts and port changes, so bookmarks and muscle memory survive (already true locally; now remotely too).
8. As a user, I want HMR/WebSocket passthrough to keep working (Vite hot reload), so live previews behave like local dev servers.
9. As a user, I want a remote preview to stop working the moment its engine session is revoked, so a lost device loses previews with everything else.
10. As a user, I want nothing exposed to the public internet, so sending a preview URL to someone else remains a dead link.
11. As a web client user on the same machine (or over SSH), I want previews framed in the app, so the browser experience matches the desktop.
12. As a developer, I want the engine to resolve only its own live service ids over the relay, so remote metadata never authorizes an arbitrary TCP dial (upstream's invariant, preserved).
13. As an agent, I want to ask which preview URLs my own chat's servers are serving, so I can tell the user where to look instead of leaving them to find the Ports card.

## Implementation Decisions

- **Vocabulary/ADRs:** governed by ADR 0003 (port-by-intent, no cloud restoration) and ADR 0004 (engine-local data). ADR 0011 is untouched by Phase C: the room's role ends at minting sessions; preview bytes ride a per-engine session the client already holds. No room carries data at runtime; no engine acts as a client of another engine; no ADR amendment required.
- **Phase A is a port, not a redesign:** mirror `a9e6c48b7`'s semantics exactly (marker inherited so `nohup`/`setsid`/double-forked servers and engine-restart survivors stay attributed; marker read once per process identity; unreadable process table keeps the previous list; terminals' chats remembered after close; agent CLI control ports excluded via the harness reservation registry; servers started outside the checkout list under the starting chat). Rename mapping: `ZERON_ORIGIN` → `ROBOCO_ORIGIN`, `ORIGIN_ENV`/`chat_origin`/`terminal_origin` in `crates/proto/src/preview.rs`, `zenon_owned` → `roboco_owned` (already rebranded). Wire change: `PreviewService.chat_id` → **wiregen gate**.
- **Phase B keeps the platform split honest:** the Windows enumerator produces the same `Listener`/`Process` shapes the Linux/macOS scanners do; the origin-marker attribution from Phase A is platform-independent; cwd remains the project-matching input (deepest-match wins), read best-effort (access-denied processes degrade to origin-only attribution). No elevation: enumerate same-user processes only; loopback-reachability from the bind address (`127.0.0.1`/`::1`/`0.0.0.0`/`::` all count as loopback-reachable). Stack (design-research-verified): `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL)` via the already-pinned `windows-sys` for sockets+pids, `sysinfo` (already in the lockfile) promoted to a direct dep for parent/start-time/cwd/cmd/environ — no new crates in the graph; PEB-denied processes degrade to pid+parent (attribution resolves through the nearest marked readable ancestor).
- **Phase C data plane: engine route, not RPC method.** A new `/preview-relay` (exact path TBD by ticket) upgrade on the engine listener, authenticated by the existing session gate exactly like the RPC WebSocket (`Bearer` header or first-frame `Auth`, `crates/engine/src/listener.rs:197-234`), speaking the existing mux frame protocol (`mux.rs`) over the socket, with `Mux::start(transport, LocalConnector, initiator=false)` on the engine side. `Mux` is symmetric and transport-agnostic (`mux.rs:84-90`, `148-183`) — no mux changes. No base64, no RPC envelope changes; this is the tailcat-relay shape (`tailcat_relay.rs:469-561`).
- **Authorization scoping:** the relay request carries `{chatId, serviceId}`; the engine resolves only service ids in its live catalog **and** attributed to that chat (Phase A's `chatId` makes this enforceable — hence C is blocked by A); `LocalConnector` re-verifies process identity before dialing (`service.rs:285-313`), so stale port reuse is rejected server-side, and remote metadata never names an arbitrary TCP address.
- **Client-side proxy is one Rust module used by every client:** binds `127.0.0.1:7332` (unclaimed; engine owns 7331, browser-helper owns 7333 — `apps/roboco/src/tailcat_browser_helper.rs:18`), routes by Host header against the remote snapshot's hostnames (the dormant `catalog.set_remote` ingestion, `catalog.rs:187/236`, driven from `WatchPreviews` instead of peer signaling), and dials the relay over the transport the client already uses (`EngineTarget`/engine registry on desktop, `PairedEngine` records in the mobile core). It lives GPUI-free (in or beside `roboco-engine-client`) so the desktop app and the Android core share it.
- **Desktop URL rewrite:** for non-local engines, `service.url()` renders against 7332 (sites: `browser/view.rs:128`, macOS `register_preview` `mod.rs:286-289`), replacing the tunnel-URL degradation (`mod.rs:279-281`). The snapshot's `proxy_port` stays authoritative for local engines.
- **Platform browser stories (explicit, resolution-verified):** `*.localhost` synthesis is guaranteed only in Chromium-family and Firefox surfaces — Chromium resolves `*.localhost` → loopback in-process before any OS resolver (Android WebView included; WebView2 would be, if a Windows browser pane ever ships), Firefox since 84 — while WebKitGTK inherits the system resolver (only systemd-resolved ≥ 253 synthesizes it) and Safari/macOS cannot be assumed. Consequences per platform: macOS — existing WebKit per-domain CONNECT registration, extended to 7332 (the reason upstream built it). Linux — the ticket adds a WebKitGTK proxy configuration for preview hostnames pointing at the client proxy (the macOS pattern's Linux sibling — verify `webkit_network_proxy_settings_*` in-ticket) with external-browser fallback. Windows — no embedded browser today; previews open externally in the user's Chromium/Edge (synthesis works). Android — plain WebView loads `http://{hostname}:7332` against the in-app proxy; native Chromium resolution means no `shouldInterceptRequest`, no ProxyController, and real-socket WebSockets/HMR. The engine's own Rust HTTP paths dial `SocketAddr`es, never `*.localhost` hostnames.
- **Web client v1 is loopback framing only:** build the panel on the existing `lib/preview.ts` gate (engine endpoint loopback = shares the loopback namespace, SSH included). Off-machine web stays an honest "not available from this browser" note. The off-machine paths (origin-engine HTTP relay or ServiceWorker fetch bridge) are Phase D, specced separately.
- **Lifecycle:** the client proxy binds 7332 only while a remote preview is being viewed (lazy start, idle shutdown); the engine's 7331 behavior is unchanged. A busy 7332 produces an inline error, mirroring the 7331 failure mode.
- **Revocation semantics are inherited, not new:** cutting the engine session (Settings revoke, pairing expiry, listener teardown) must tear down the relay socket with it — the existing listener/gate machinery already does this for RPC and tailcat-relay sockets; the ticket asserts it for the preview relay.

## Testing Decisions

- **Phase A:** port `a9e6c48b7`'s test additions to `crates/preview/tests/discovery.rs` (origin is the nearest marked process and never the engine; unreadable environment retried not remembered; whole-name marker matching; procargs parsing) plus `crates/engine/tests` for env stamping in sessions/terminals; ports-card UI tests in `crates/ui`. wiregen freshness gate (`web-codegen.yml`).
- **Phase B:** Windows discovery tests run on the Windows runner (`windows.yml`): a spawned loopback HTTP listener attributed through a marked child process; user-started (unmarked) servers excluded; access-denied process degrades gracefully. Linux/macOS tests unchanged (no behavior change).
- **Phase C:** engine tests for the relay route: unauthenticated dial rejected; session-authenticated dial streams a real HTTP round-trip through the mux (large bodies, slow reader, cancellation, half-close — the `transport.rs` idiom); service-id/chat scoping enforced (foreign chat's serviceId refused, dead service refused); revocation cuts an open relay. Client-proxy tests: hostname routing from a snapshot, 7332 bind conflict surfaces the inline error. Android: JVM unit tests for the panel state; the emulator flow suite gains a preview open against the `android_fixture` engine when the WebView surface lands. Web: vitest for the loopback-framing panel state.
- **Cross-cutting:** no test may probe a listener lacking an origin marker (auth-command exclusion regression, PR #763 heritage).

## Out of Scope

- **WebRTC direct data plane and its signaling** (client-shuttle or otherwise) — the dormant `Peers` stack stays unwired; revisit if relayed previews need a direct path (latency, tailnet-less WAN).
- **STUN/TURN policy** — no WebRTC in v1, so no ICE posture to choose.
- **Public share URLs** — sending a preview link to an unpaired person remains a dead link (deliberate; see research file's prior-art section for the tunnel-shaped alternative).
- **Cloud machines / publisher-only rooms** (upstream PR #966, `afcf0864a`) — roboco has no cloud (ADR 0003/0004).
- **Off-machine web previews** (origin-engine HTTP relay, ServiceWorker fetch bridge) — deferred; the web panel ships loopback framing with an honest note.
- **Windows embedded browser surface** — previews open externally on Windows; a browser pane is its own future feature.
- **iOS** — removed from roboco entirely.

- Phase D note (deferred WebRTC): LAN-first ICE pairs host candidates directly with **zero STUN/TURN infrastructure** (RFC 8445 host candidates; `rtc-ice` — the ICE crate behind the pinned `webrtc 0.20.5` — gathers host-only when no server URLs are configured); loopback addresses are excluded from host candidates, and a public STUN server only becomes necessary for cross-network reachability.
