### 2.5 Cache behaviour (the biggest hidden cost)

`gh api …/actions/cache/usage` on 2026-10-28: **10.90 GB in 14–16 entries against the 10 GB repo limit**. Every `Swatinem/rust-cache` step without a `key`/`shared-key` writes its own ~0.5–1.6 GB entry per job id (ui-tests 1.07, mobile-core 1.40, engine-local 0.94, android-emulator 1.59, engine-client 0.66, web-smoke 0.66, freshness 0.65, networking 0.52, export-check 0.34, release windows-arm64 1.05, linux 1.03/1.01) plus 3 `setup-go` caches (0.24–0.70 GB). GitHub evicts LRU above 10 GB, so entries live **hours**. At the moment of the snapshot the Windows `tests` cache and both `android` caches were already gone.

Restore step ≤ 0.15 min ≈ nothing restored. Miss rate and its cost (successful jobs, p50 minutes):

| job | restores | misses | p50 hit | p50 miss |
|---|---|---|---|---|
| windows `tests` | 28 | 8 | 75.0 | ≈ 87–95 (Build application +11) |
| ui `engine-local-regressions` | 33 | **22** | 4.6 | **15.2** |
| ui `mobile-core` | 33 | 14 | 10.4 | 19.1 |
| ui `ui-tests` | 33 | 13 | 21.0 | 23.3 |
| android `android` ubuntu | 30 | 16 | 16.1 | 26.0 |
| android `android` windows | 28 | 19 | 22.4 | 35.3 |
| android `android-emulator` | 30 | **23** | 26.1 | 37.9 |
| preview `networking` | 30 | **28** | 1.5 | 3.3 |
| web-codegen `freshness` | 30 | 22 | 1.7 | 6.2 |
| release linux x64 | 23 | 19 | 9.7 | 15.6 |
| release windows x64 | 19 | 15 | 17.2 | 24.4 |

Three structural reasons on top of the size cap:

1. **`windows.yml` never runs on `main`**, so there is never a `main`-scoped Windows cache; a new PR branch can only restore from its own previous runs (PR-ref scope) — every new PR's first Windows run is cold.
2. Every PR run **saves** (no `save-if`), each save (0.3–1.8 min) pushes main's entries out; PR-scoped entries are useless to any other branch.
3. `preview-tests.yml` uses `dtolnay/rust-toolchain@stable` instead of `rust-toolchain.toml`, so its key never matches anything else (28/30 misses).

## 3. Top time sinks

Ranked by how much PR wall time or runner time they burn (per PR push that touches `crates/**`, warm unless stated):

1. **Cache thrash** (§2.5): ~60 % of Rust jobs restore nothing. Miss penalty per job: +11 (Windows), +10.6 (engine-local), +8.7 (mobile-core), +9.9 / +12.9 (android ubuntu / windows), +11.8 (emulator). This alone explains the "9 vs 20 min" `Build application` variance and the 90→120 timeout bump.
2. **The serial Windows job** (75 min): ~10 separate `cargo nextest`/`cargo build` invocations with different `-p`/feature sets, each re-resolving features and rebuilding shared crates in thin-LTO-off release; the whole job is one runner, so nothing overlaps.
3. **Hidden Windows rebuild** (≈ 8 min + a second rebuild): `package-windows.ps1` sets `ROBOCO_TAILCAT_EMBED`; `crates/engine/build.rs:74` has `rerun-if-env-changed=ROBOCO_TAILCAT_EMBED`, so the engine and everything above it are rebuilt in packaging, then rebuilt again when "Application and updater tests" runs without the variable.
4. **Android-only work on Windows** (≈ 21 min): "Mobile core crates" (11.7; `roboco-text`/`roboco-mobile`/`roboco-mobile-client` are not linked by the desktop — `cargo tree -p roboco -i`) and "Mobile core host build and bindings" (9.2; the same xtask host path runs in `android.yml`'s windows leg via Gradle).
5. **Release-mode thin-LTO Linux UI build** (`ui-tests`, 21.8): `cargo test --release` with the committed thin LTO (no `CARGO_PROFILE_RELEASE_LTO=false` override, unlike windows.yml), two separate builds (UI lib, then the `roboco` CLI tests).
6. **Emulator job builds the core twice over** (§2.6) and runs on any `crates/{engine,harness,rpc,proto,syntax}` change.
7. **Duplicate Android core builds**: `ui-tests/android-core` (15.3, mobile-dist, **no rust-cache**, `cargo install cargo-ndk` from source) duplicates the Gradle core build + `--check` (16 KB PT_LOAD, Kotlin contract) in `android.yml`, and the mobile-dist profile is built on main by the R8 smoke and on tags by `release.yml`.
8. **Red suites** (§2.2): 1,264 runner-min of failed Android runs and 241 of ui-tests in 5 days, plus the reruns and re-pushes they cause. Not a speed fix, but a large share of the time people wait on CI is waiting for a result that is red for reasons unrelated to the PR.

## 5. Unnecessary work

Duplicate steps / jobs:

- `windows.yml`: "OpenCode wire integration tests" re-runs `--test opencode`, already in "Portable harness integration tests"; "Native harness integration tests" re-runs exactly step 1's `--test codex_availability --test windows_native`.
- `windows.yml` "Build application" + the build inside `package-windows.ps1` (§3.3).
- `ui-tests/android-core` vs `android.yml/android` (both build the Android core with `--check`).
- `windows.yml` "Mobile core host build and bindings" vs `android.yml` windows leg (both run the xtask host path on Windows).
- `ui-tests/mobile-core` "Mobile core benches compile" + "Mobile layout bench (informational)" (5.4 min `--release` build that never gates) on every PR.
- "UI native font geometry test" pays the entire `roboco-ui` test compile for one test; fine once all UI tests share one build.

Tests on Linux **and** Windows without a platform reason:

- `roboco-text`, `roboco-mobile`, `roboco-mobile-client` (Android core; not linked by the desktop). Keep `roboco-engine-client` and `roboco-markdown` on Windows — the desktop links them.
- Everything else run on both has a Windows reason (process spawning / ConPTY / paths / DirectWrite / updater / installer / preview listener table).

Jobs on every PR that only matter for some paths:

- `ui-tests.yml` triggers on `apps/**`, which includes `apps/android/**`: an Android-only PR pays ≈ 68 runner-min of desktop/engine jobs.
- `android.yml` triggers on `crates/{engine,harness,rpc,proto,syntax}/**` and runs the 34-min emulator suite for engine-only changes; `android (windows-2022)` (30 min) proves a bash-free Gradle build on every PR.
- `windows.yml` triggers on `crates/**` including Android-only crates.

Release-only checks on PRs: `android-core` mobile-dist sizes; the layout bench. (Windows packaging/installer on PRs is cheap once deduped — keep.)

Feature/profile combos: harness built with and without `native-fixture` in the same Windows job; `roboco-syntax --no-default-features --features mobile-languages` (small, keep); `ui-tests` in release thin LTO; `mobile-core` bench in `--release`.

Cache waste: per-job keys (no `shared-key`), PR and tag saves, `cache-workspace-crates: true` (bigger entries), `release.yml` saving 4 tag-scoped caches per release (only that tag can read them), `setup-go` caching 0.24–0.70 GB per OS/ref.

Concurrency: every workflow uses `cancel-in-progress: true` for all refs, so rapid merges cancel **main** runs too (e.g. 39919392832 / 39919392882 cancelled at 3 min) — and a cancelled main run never seeds a cache.

Unused artifacts: none significant in time (uploads are seconds). `android-core-sizes` disappears with `android-core`.
