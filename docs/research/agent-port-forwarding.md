# Agent port forwarding (research)

*Researched 2026-10-26 against `zeron/main` @ `4443e6b58` (pristine upstream mirror), the `gh` CLI as `hoangvu12`, and live web fetches. All `git show` references are against the local mirror; PR links point at [zeronsh/zeron](https://github.com/zeronsh/zeron) (formerly `zeronsh/comet` — releases still link `zeronsh/comet/pull/…`, e.g. [v0.2.55](https://github.com/zeronsh/zeron/releases/tag/v0.2.55)).*

## Summary

- Upstream zeron auto-detects HTTP listeners started *by zeron itself* (agent runs and its terminals), attributes each to the chat that started it via an inherited `ZERON_ORIGIN` env marker, and exposes every one at a stable `http://<device>.<project>.localhost:7331` hostname through a loopback proxy — with WebSocket/HMR passthrough so it behaves like a local dev server ([PR #1023](https://github.com/zeronsh/zeron/pull/1023), [docs/preview-networking.md](https://github.com/zeronsh/zeron/blob/main/docs/preview-networking.md)).
- Viewing a preview on *another* device rides a direct WebRTC DataChannel between the two devices; zeron's cloud edge (a Cloudflare Worker with Durable Objects) only authenticates and relays *signaling* (presence, service catalogs, SDP/ICE) — never HTTP bytes ([PR #290](https://github.com/zeronsh/zeron/pull/290), `git show zeron/main:crates/preview/src/peer.rs` head comment).
- Cloud machines (upstream's hosted sandboxes) publish their own services into the same rooms as "publisher-only" members, so phone/desktop clients can preview a dev server running in the cloud sandbox (commit `afcf0864a`, [PR #966](https://github.com/zeronsh/zeron/pull/966)).
- **WorkOS is identity, not infrastructure.** The edge is zeron's own Cloudflare Worker (`edge.zeron.sh`, worker `comet-native-edge`, Durable Objects + R2 — `git show zeron/main:edge/wrangler.jsonc`). WorkOS AuthKit issues the access-token JWTs; the Worker verifies them against WorkOS's JWKS and uses the `org_id`/`sub` claims to derive the preview room name (`git show zeron/main:edge/src/auth.ts`, `edge/src/preview-route.ts`). No WorkOS-hosted component carries preview traffic.
- The exact marketing phrasing "automatically detects ports started by a zeron agent and lets you access them as if they were local" was **not found** in upstream's README, site, release notes, or PR bodies (see below for the closest verified quotes); the feature is documented in-repo in `docs/preview-networking.md`, not on zeron.sh.

## The upstream feature: what the user sees

The feature shipped 2026-09-09 in [PR #290](https://github.com/zeronsh/zeron/pull/290) ("Add automatic project previews with stable URLs and P2P networking", release [v0.2.55](https://github.com/zeronsh/zeron/releases/tag/v0.2.55)) and was refined 2026-10-25 in [PR #1023](https://github.com/zeronsh/zeron/pull/1023) (release [v0.2.123](https://github.com/zeronsh/zeron/releases/tag/v0.2.123)). Verified user-facing quotes:

- PR #290: *"Running a project dev server now makes it appear in a new Browser tab, with one-click opening through a persistent `device.project.localhost:7331` address. Restarting on a different port keeps the address."*
- PR #1023: *"Preview discovery listed every listener whose working directory was inside a project, so your own dev servers, and anything else running there, showed up as previews. Now it lists only what Zeron started, and a Ports card beside the chat shows them."* and *"Clicking a port opens it in a browser tab through its stable preview address."*
- Repo doc (`git show zeron/main:docs/preview-networking.md`): *"Run an HTTP development server in a project and open a Browser tab in that session. The empty tab lists its running services. **Open** navigates to `http://<device>.<project>.localhost:7331`; additional services receive persistent names such as `<device>.<project>-api.localhost:7331`."*

Concretely, a user opens a session (a chat driven by Claude Code/Codex/etc.), the agent runs `npm run dev`, and:

1. The service appears automatically in the session's Browser tab list and in a **Ports card** stacked beside the session card (3 ports shown, "Show N more" pages 10 at a time; the card is absent when nothing runs — `git show a9e6c48b7:crates/ui/src/shell/session_info.rs`, "The ports card: a row per server this chat can preview").
2. Clicking it opens `http://<device>.<project>.localhost:7331` in an in-app browser tab with full WebSocket/HMR passthrough (Vite hot reload works — PR #290 demo recording).
3. The address is *stable*: a dev server restarting on a different port keeps its hostname; identities persist in the profile's `previews.json` (`git show zeron/main:docs/preview-networking.md`, "Discovery and identities").
4. The same address works from the user's *other* signed-in devices (phone, second computer): the loopback proxy forwards frames over the P2P link to the hosting device. A server the *user* started themselves is deliberately not listed (PR #1023 screenshot captions: *"A server the user started in the same project (`:4000`) runs throughout and is never listed."*).
5. Open follow-ups users have filed: skip the local loopback proxy entirely and always use the relay ([issue #343](https://github.com/zeronsh/zeron/issues/343)), bring live previews to iOS ([issue #342](https://github.com/zeronsh/zeron/issues/342)), and preview static workspace HTML through the same path ([issue #326](https://github.com/zeronsh/zeron/issues/326)).

No public docs site covers this: zeron.sh serves only a landing page (fetched 2026-10-26 — no `/docs`, no previews copy; only downloads/testimonials), and the README doesn't mention previews (`git show zeron/main:README.md`). `docs/preview-networking.md` in the repo is the authoritative description, plus issue #342 quoting it: *"The desktop client (macOS/Linux) has a 'Preview workspace' feature: open a Browser tab in a session, it discovers running dev servers in the project … and opens them at a friendly `<device>.<project>.localhost:7331` address with full HMR/WebSocket passthrough (see `docs/preview-networking.md`)."* **I could not locate the phrase "automatically detects ports started by a zeron agent"** in any upstream material — treat it as a paraphrase of PR #1023's "lists only what Zeron started".

## How upstream implements it

All in the `zeron-preview` crate (`git ls-tree zeron/main crates/preview/src/`): `discovery.rs`, `catalog.rs`, `proxy.rs`, `mux.rs`, `peer.rs`, `signaling.rs`, `viewer.rs`, `service.rs`, plus `crates/proto/src/preview.rs` (wire types) and `crates/engine/src/lib.rs` (wiring).

### Detection (engine-local, no cloud involvement)

- **Origin marking.** The engine stamps `ZERON_ORIGIN` into the environment of *everything it launches* — `chat:<id>` for agent runs, `terminal:<id>` for its terminals (project actions run in a terminal) — in `crates/engine/src/sessions.rs` (`wire_request.env.insert(zeron_proto::ORIGIN_ENV …)`, `git show a9e6c48b7:crates/engine/src/sessions.rs`) and `crates/engine/src/terminals.rs`. Because children inherit the variable, `nohup`/`setsid`/double-forked servers and servers surviving an engine restart stay attributed; a launcher that scrubs its environment (`env -i`) is attributed through the marked ancestor; one variable means the nearest zeron launch always wins (nested engines don't leak the outer chat) — `git show zeron/main:crates/proto/src/preview.rs` (`ORIGIN_ENV` doc comment) and PR #1023 body. #1023 *removes* the old `mark_descendants` ancestry walk from `discovery.rs` entirely, replacing it with `resolve`/`attribute`/`origin_marker` (nearest marked process wins, never the engine itself) — the Windows `listeners(_origins)` stub upstream also returns the empty case, confirming upstream ships no Windows discovery.
- **Scanning.** Linux joins the current user's `/proc` process cwd, ancestry, creation time and socket descriptors to listening TCP sockets; macOS uses `lsof`/`ps` (PR #917's libproc/`/proc`-descendants-only approach — closed unmerged, its substance landed in #1023: *"Reads only the engine's descendants (agent runs, terminals and what they start) through libproc on macOS and `/proc` on Linux. No subprocesses."* and *"Parks with no timer while none of them is alive"*). Discovery runs every 2 s while a run/terminal is alive; a failed scan keeps the previous list rather than clearing it (macOS `lsof`/`ps` time out after 10 s) — `git show zeron/main:docs/preview-networking.md`, PR #1023.
- **What counts.** Only loopback-reachable listeners whose cwd belongs to a known local project (deepest match wins), confirmed HTTP by bounded HEAD probes; commands with authentication arguments (`login`, `auth`, `sso`, … before `--`) are excluded *before* connecting because they may be one-shot browser callbacks (PR #763, [release v0.2.103](https://github.com/zeronsh/zeron/releases/tag/v0.2.103) — *"Fix preview discovery aborting CLI browser logins"*). Ancestors are resolved to the owning chat only if that chat is hosted by this device; the agent CLI's own control port (e.g. `opencode serve`) is excluded via a reservation registry (`crates/harness/src/agent_ports.rs`, `git show zeron/main:crates/harness/src/agent_ports.rs` head comment: *"Such a server carries its run's origin marker like everything the agent starts, but it is the agent itself, never a dev server to preview."*).
- **Catalog.** `crates/preview/src/catalog.rs` + profile `previews.json` keep persistent identities (project/service IDs, hostname labels) separate from observed PIDs/ports; framework commands are labeled (Vite/Next.js/Astro/Miniflare/Node — `git show zeron/main:crates/preview/src/discovery.rs` `framework()`); `WatchPreviews` RPC re-resolves the session's cwd on each catalog/workspace change and selects the local or the advertised-remote services for the session's owning device (`git show zeron/main:docs/preview-networking.md`).

### Local proxy and "as if local" routing

- The daemon binds a loopback proxy on port **7331** (`crates/proto/src/preview.rs`: `PREVIEW_PROXY_PORT = 7331`). It validates the `Host` against the catalog, then opens an opaque service ID through a transport-independent multiplexer: locally frames travel over a socket pair; remotely the *identical frames* travel over one ordered, reliable WebRTC DataChannel — *"Remote metadata never authorizes an arbitrary TCP address: the hosting device resolves only its own live service IDs"* (`git show zeron/main:docs/preview-networking.md`).
- On macOS 14+ WebKit gets a per-domain HTTP CONNECT configuration for preview hostnames, so `<device>.<project>.localhost:7331` works without hosts-file changes; the CONNECT endpoint admits only known preview names (`git show zeron/main:crates/preview/src/proxy.rs` `connect_loopback`).
- The mux frame protocol (one-byte kind, 32-bit stream ID, bounded payload; OPEN/DATA/END/CANCEL/WS_OPEN/WS_DATA/WS_CLOSE/READY/CREDIT; 8 KiB DATA, 64 KiB windows, ≤64 streams) carries HTTP/1 with hop-by-header hygiene, `Host`+`Origin` preserved (Next.js Server Actions), `X-Forwarded-Host` set, absolute-localhost redirects rewritten, and WebSocket upgrades passed through byte-for-byte so Vite HMR works (`git show zeron/main:crates/preview/src/mux.rs`, `docs/preview-networking.md` "HTTP and stream transport").
- Engine wiring: `core.previews.start(projects, preview_signaling)` in `crates/engine/src/lib.rs` with `Scope { chats, terminals, reserved_ports }` (which chats this device hosts, which terminal belongs to which chat) and `signaling::Config { edge_url, org_id: profile.org_id(), tokens: Arc<Auth> }` only when the edge is enabled (`git show zeron/main:crates/engine/src/lib.rs` around `preview_signaling`).

### Cross-device P2P and the edge

- `crates/preview/src/signaling.rs`: each device opens a WebSocket to `<edge_url>/preview/{org_id}/ws?device=<id>` with `Authorization: Bearer <access token>` (the token source is the engine's `Auth` — `impl zeron_preview::signaling::TokenSource for Auth { … self.access_token() }`, `git show zeron/main:crates/engine/src/auth.rs` around line 1669). It advertises its local catalog, relays pairing SDP, heartbeats with a 40 s lease, and clears remote routes/peers on disconnect.
- `crates/preview/src/peer.rs` head comment: *"Authenticated signaling supplies SDP/DTLS fingerprints. Preview bytes only use the resulting reliable, ordered DataChannel; there is no edge byte relay."* ICE uses host candidates + public STUN, **no TURN** — *"Networks that prohibit direct ICE connectivity return a bounded connection error"* (`docs/preview-networking.md`). Only the lexicographically-lower device creates offers; DataChannels open lazily per preview request.
- Engine-free clients (the phone): `crates/preview/src/viewer.rs` `ViewerPeers` — *"Direct connections for a device that only reaches out — a phone. It joins the same signaling as every engine (advertising no services) and pairs with the user's other devices on demand"* — used by `crates/client/src/live/direct.rs`. The same DataChannel fabric now also carries terminals (service `terminal/{id}`) since PR #975 and #1007.
- Terminal reuse: PR #975 — *"A terminal on another device streams over the existing WebRTC peer connection (the preview peers' DataChannel, service `terminal/{id}`, binary frames)"* — so the preview P2P mesh is general infrastructure, not just HTTP.

### Cloud machines

Commit `afcf0864a` "Edge: Cloud previews, credit checks, subscription handling" (follow-up to [PR #966](https://github.com/zeronsh/zeron/pull/966), 2026-10-22): *"Cloud machines publish previews of their own services."* A Cloud sandbox runs the same headless engine (ARCHITECTURE.md: *"an ordinary headless engine provisioned per session"*), whose preview signaling connects with a **runner JWT** (zeron-minted, not WorkOS) — the route then marks it publisher-only: *"A Cloud machine joins only as itself, and only to publish: it never sees the other devices' services nor opens a connection to one"* (`git show afcf0864a:edge/src/preview-route.ts`, and `edge/src/preview-room.ts`: *"A publisher only responds to a device that contacted it … it never starts a pairing"*). So a chat on a Cloud machine can serve its dev server to the user's phone/desktop exactly like a self-hosted device, minus the presence leaks.

Timeline: #290 (2026-09-09, v0.2.55) → #763 (v0.2.103) → #966 + `afcf0864a` (2026-10-22, Cloud) → #917 closed unmerged (2026-10-23) → #975/#1007 (2026-10-24, terminals over the same peers) → #1023 (2026-10-25, v0.2.123, zeron-started-only + Ports card). PR #1023 also added an optional `chatId` field to relayed catalogs: *"Without the deploy, other devices still match ports by project."*

## The WorkOS / edge role — what is cloud vs engine-local

**What is WorkOS (identity only):**

- `git show zeron/main:edge/src/auth.ts` head comment: *"Edge auth: verify WorkOS AuthKit access-token JWTs (jose against the WorkOS JWKS) before any DO forwarding or R2 access. WebSocket upgrades carry the token as `?token=`… Workspace rooms authorize on the token's WorkOS organization claim (`org_id`, present when the session was refreshed scoped to an org)."* Runner JWTs (the Cloud device's bearer) are *"accepted alongside WorkOS JWTs"* and verified against zeron's own key.
- `git show zeron/main:edge/src/workos.ts` head comment: *"Minimal WorkOS User Management REST client… This is the one place that holds the WorkOS **API key** (a Worker secret). Device backends build the public authorize URL themselves and delegate the secret-bearing steps here, so the key never lands on a device."* (code exchange, refresh, org listing).
- So: WorkOS AuthKit authenticates users, issues the JWT access tokens, and supplies the `org_id` claim that scopes rooms. The token's shape matches WorkOS's documented access token — `iss: https://api.workos.com`, `sub` (user), `org_id`, verified via `https://api.workos.com/sso/jwks/{client_id}` ([WorkOS session tokens docs](https://workos.com/docs/reference/authkit/session-tokens), fetched 2026-10-26).
- What authenticates preview signaling specifically: the **WorkOS access token** (Bearer header / `?token=`) of the signed-in user, verified by the Worker; the Worker checks the token's `org_id` claim equals the org in the URL path and derives the room as `preview1/{orgId}/{userId}` — *"Route identity comes exclusively from verified JWT claims"* (`git show zeron/main:edge/src/preview-route.ts`). Client-side, `Config { edge_url, org_id, tokens }` with `TokenSource` = the engine's `Auth` (`git show zeron/main:crates/preview/src/signaling.rs`, `crates/engine/src/auth.rs`).
- Public-source status: searches for `site:workos.com zeron` / "zeron workos" (DuckDuckGo, 2026-10-26) returned **no** WorkOS-published mention of zeron; WorkOS's role here is established entirely by upstream's own code and ARCHITECTURE.md. DeepWiki's generated wiki agrees: *"Built on Cloudflare Workers and Durable Objects (DOs), the edge routes requests, enforces WorkOS authentication…"* ([deepwiki 6. Edge](https://deepwiki.com/zeronsh/zeron/6), snapshot c914b319).

**What is zeron's own cloud (Cloudflare, not WorkOS):**

- `git show zeron/main:edge/wrangler.jsonc`: worker `"comet-native-edge"`, routes `edge.zeron.sh` (custom domain on the zeron.sh zone), Durable Object bindings including `{ "name": "PREVIEW_ROOMS", "class_name": "PreviewRoom" }`, R2 buckets, deployed by CI on pushes touching `edge/`. The default engine edge URL is `https://edge.zeron.sh` (`git show zeron/main:apps/zeron/src/lib.rs`: `DEFAULT_EDGE_URL`), overridable with `ZERON_EDGE_URL` for dev/self-hosting.
- The PreviewRoom Durable Object stores per-device service catalogs in SQLite, stamps sender identity, validates every catalog/signal payload (hostnames match `<x>.<y>.localhost`, SDP must carry a DTLS fingerprint, binary frames and arbitrary proxy protocol messages rejected, 120 msgs/10 s rate cap, 16 devices/room) — `git show zeron/main:edge/src/preview-room.ts` (*"One authenticated user's devices in one organization. Only presence, service metadata and SDP/ICE coordination live here; binary preview frames are rejected."*).

**What is engine-local (no cloud at all):** discovery (process table scanning, origin attribution), the catalog, the loopback proxy, HTTP/WebSocket proxying, DTLS/WebRTC data transport, and the stable `.localhost` URLs. *"local previews work independently of edge availability"* (`git show zeron/main:docs/preview-networking.md`); the edge is only needed to learn another device's catalog and to exchange SDP. This maps to Roboco's ADR 0004 (engine-local data) cleanly: even upstream, preview *bytes* never leave the devices.

## Feasibility for Roboco

**Verdict: yes — roughly 70% is already in the tree, the rest is three bounded work items, and none of it needs WorkOS or any cloud.**

1. **Local parity (port #1023):** carry the intent of `a9e6c48b7` across the rebrand per `docs/reference/upstream-ports.md` — `ROBOCO_ORIGIN` env stamping in `engine/src/sessions.rs`/`terminals.rs` (+ rename `ORIGIN_ENV` in proto), origin-based hard attribution + `chatId` in `crates/preview` (discovery/service/catalog), the harness agent-CLI port reservation (`crates/harness/src/agent_ports.rs`), and the Ports card in `crates/ui/src/shell/session_info.rs`. Blast radius measured on the mirror: ~1,100 lines over 24 files, of which ~5 are `edge/` (skip). This also removes the current false-positive risk (user-started servers in a project cwd currently rank below agent-started ones but still list).
2. **Windows discovery (roboco-original, upstream never had it):** `discovery.rs` needs a Windows `listeners()` — enumerate listening TCP sockets with owning pid (IP Helper API `GetExtendedTcpTable`), process cwd + ancestry + start time (NT query / `toolhelp32` snapshot), all engine-local. This is the only piece with no upstream code to port; it gates the feature on roboco's flagship platform.
3. **Cross-device data plane (the "as if local" remote half):** the P2P stack is present and idle; what upstream got from the WorkOS-authenticated Worker, roboco can get from **sessions it already mints**. Recommended shape: **client-shuttled signaling** — desktop/phone/web clients already hold authenticated sessions on every engine a room introduced them to; two small session-authenticated RPCs (`PreviewAnnounce`/`PreviewSignal`) let a client relay each engine's `OutgoingSignal` (presence + bounded catalog + SDP, the exact payload class upstream's DO carried) into the other engine's dormant `Peers::signal()`/`catalog.set_remote`. Preview bytes then ride the engine-to-engine WebRTC DataChannel exactly as upstream designed — no relay, no cloud, DTLS end-to-end. An ADR 0011 amendment should note the rejected "on-behalf-of forwarding" concerned chat traffic, not this control-plane shuttle (the room itself still carries no data at runtime; sessions do, and sessions are the authorized channel). Alternative (simpler, heavier): relay preview frames over the engine session like `tailcat_relay` byte-pumps — works everywhere rooms work, but puts HTTP bytes on the session channel and forgoes the already-built DataChannel path.
4. **Out of scope by design (ADR 0003/0004):** the Cloud tier — zeron-hosted sandboxes publishing previews as publisher-only room members with credit checks. Roboco has no cloud; nothing here depends on it (upstream: "local previews work independently of edge availability").

Sequencing suggestion: #1023 port first (pure port, immediately useful on macOS/Linux), Windows discovery second (unblocks the platform), client-shuttled signaling last (new design surface, wants an ADR + spec in `.scratch/` per the issue-tracker convention).

## Prior art

- **VS Code** — automatic forwarding and manual internet forwarding. In remote workspaces VS Code auto-forwards ports by two mechanisms: the default historically watched *listening processes* on the remote, and `"remote.autoForwardPortsSource": "output"` switches to parsing terminal/debug *output* (shell-integration-assisted) — *"By default, VS Code will find ports to automatically forward for you by looking at the currently running processes on the remote system… To look for ports to forward based on terminal and debug output (instead of running processes) set `"remote.autoForwardPortsSource": "output"`."* ([vscode-docs v1.54 release notes](https://github.com/microsoft/vscode-docs/blob/main/remote-release-notes/v1_54.md)); v1.78 added `"hybrid"` — *"discovers ports by watching terminal and debug output… However, process watching is still used so that when a process that listens on a port exits, the port is no longer forwarded"* ([v1_78](https://github.com/microsoft/vscode-docs/blob/main/remote-release-notes/v1_78.md)). Separately, the built-in **Port Forwarding** feature exposes local services over the internet via Microsoft dev tunnels (GitHub/MS account auth, private by default, "VS Code makes outbound connections to a service hosted in Azure") ([VS Code docs](https://code.visualstudio.com/docs/debugtest/port-forwarding), fetched 2026-10-26), and the integrated browser proxies localhost traffic for remote workspaces ([integrated browser docs](https://code.visualstudio.com/docs/debugtest/integrated-browser)). Contrast: detection is output/process-based with no agent attribution, and forwarded addresses are tunnel URLs, not stable local hostnames.
- **Claude Code / Codex — no equivalent found.** Neither [docs.anthropic.com](https://docs.anthropic.com) (`llms.txt`, fetched 2026-10-26 — no port-forwarding/tunnel feature) nor the Codex docs ([learn.chatgpt.com](https://learn.chatgpt.com/docs/sandboxing), fetched 2026-10-26) document auto-detection or forwarding of agent-started dev servers; Codex workflows tell the agent to *"Start the dev server and tell me the local URL/route to view the prototype"*, and its sandbox *blocks* loopback/private destinations by default (`allow_local_binding = false`). Their remote sandboxes have no "as if local" routing layer — a gap zeron explicitly fills.
- **Cursor** — background/cloud agents run in remote VMs, but current docs (docs.cursor.com, fetched 2026-10-26) could not be scraped (SPA shell; search engines rate-limited from this host), so no verified statement about dev-server exposure could be collected; treat "Cursor background agents expose dev servers at public URLs" as **unverified** here.
- **Tailscale** — the routing-only model zeron's P2P most resembles: *"Tailscale Serve lets you serve local directories, files, plain text, or local ports with other devices in your tailnet. For example, you can proxy requests to a web server running at http://127.0.0.1:3000 using `tailscale serve 3000`"* ([Tailscale Serve docs](https://tailscale.com/docs/features/tailscale-serve), fetched 2026-10-26); Funnel exposes the same to the public internet. Detection is fully manual (explicit command), routing is WireGuard-overlay with HTTPS and identity headers — "as if local" via tailnet DNS names rather than a browser-side proxy.

## Design research (round 2, implementation)

*2026-10-26, for `.scratch/agent-previews/`. Findings returned by a research agent against primary sources (Microsoft Learn, Android/Chromium/Firefox source, RFCs, docs.rs + the pinned crate sources).*

- **Windows discovery stack:** `GetExtendedTcpTable` with `TCP_TABLE_OWNER_PID_ALL` (both AF families) needs **no elevation** for same-user rows and distinguishes wildcard (`dwLocalAddr == 0`) from explicit `127.0.0.1`/`::1` binds; types are in the already-pinned `windows-sys` ([Learn: GetExtendedTcpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable), [MIB_TCPROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcprow_owner_pid)). `sysinfo` 0.31.4 — already in our lockfile via the zui stack — provides pid/parent/start_time/cwd/cmd/environ on Windows via `NtQuerySystemInformation` + PEB/`ReadProcessMemory` ([docs.rs](https://docs.rs/sysinfo/latest/sysinfo/struct.Process.html)); unopenable processes degrade silently (pid+parent remain, start_time 0, env/cwd empty). `netstat2` rejected (not in lock, duplicates windows-sys types). Prior art (TCPView, `Get-NetTCPConnection -OwningProcess`) joins table→pid→exe but never env — the env join is the novel half.
- **`*.localhost` resolution:** Chromium resolves `localhost`, `localhost.`, and **any `*.localhost`** to `127.0.0.1`/`::1` inside its own resolver, before any OS/DNS path ([Chromium `host_resolver_manager.cc`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/dns/host_resolver_manager.cc), [RFC 6761 §6.3](https://www.rfc-editor.org/rfc/rfc6761)) — so Android WebView, WebView2, Chrome/Edge need zero OS configuration. Firefox ≥ 84 does the same ([bug 1220810](https://bugzilla.mozilla.org/show_bug.cgi?id=1220810)). WebKitGTK inherits the system resolver (only systemd-resolved ≥ 253 synthesizes `*.localhost`); Safari/macOS cannot be assumed — which is why upstream's macOS per-domain HTTP CONNECT exists.
- **Android WebView:** `shouldInterceptRequest` can serve `http://` documents but **cannot carry WebSockets** (they ride the separate `NetworkContext::CreateWebSocket` path), redirect chains, or POST bodies — so HMR needs a real socket; the in-app `127.0.0.1:7332` proxy + Chromium's native `*.localhost` synthesis makes interception layers unnecessary. Cleartext to loopback is already permitted by the app's base network-security-config; the explicit shape if tightened: `localhost` `<domain-config cleartextTrafficPermitted="true" includeSubdomains="true">` ([Android docs](https://developer.android.com/privacy-and-security/security-config); the API 37 implicit localhost exemption does not cover `foo.localhost`).
- **LAN-first WebRTC (Phase D):** host candidates pair with **zero STUN/TURN** (RFC 8445; [`rtc-ice` docs.rs](https://docs.rs/rtc-ice) — the ICE crate behind the pinned webrtc 0.20.5 — gathers host-only when no URLs are configured); loopback addresses are excluded from host candidates; public STUN only matters cross-network.

## Open questions

1. **STUN/TURN posture:** upstream ships public STUN (`stun.l.google.com:19302` is hardcoded in roboco's `peer.rs:70-75`) and no TURN — direct-ICE-hostile networks (hotel/cellular NAT) get a bounded error. Roboco on Android-over-cellular will hit this; accept the error (upstream parity), make STUN configurable, or add a relay (which reintroduces a byte path somewhere)?
2. **Client-shuttle vs relay:** the feasibility section recommends client-shuttled signaling over existing sessions; the relay-shaped alternative (preview frames over the session, `tailcat_relay`-style) is simpler and uniform across desktop/web/Android but abandons the built DataChannel path. Worth a short ADR before building.
3. **Web preview panel:** `web/packages/app/src/state/preview.ts` is state-layer only; browsers cannot bind 7331 — the web data plane must ride the origin engine's relay (same shape as `room-redeem`), or a `browser-helper` local process (one exists: `apps/roboco/src/tailcat_browser_helper.rs`).
4. **Agent-attribution edge cases** carry over from upstream: auth-command exclusion (already ported), agent CLI control ports (`opencode serve` — arrives with the #1023 port), and the terminal-chat memory for backgrounded servers.
5. **The exact user-facing phrasing** ("automatically detects ports started by a zeron agent and lets you access them as if they were local") was not found upstream; if it was seen somewhere specific (an X post? a DeepWiki summary?), point me at it and I'll pin the citation.

Resolved by the code map: origin attribution is portable engine-local (`ROBOCO_ORIGIN`, upstream `a9e6c48b7`); signaling needs no WorkOS (client-shuttle over room-minted sessions; see Feasibility); Windows discovery is roboco-original work, not an upstream port; the cloud tier stays out per ADR 0003/0004.
